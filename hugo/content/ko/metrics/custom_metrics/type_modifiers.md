[메트릭 유형][1]은 메트릭으로 나타내려고 하는 것과 메트릭의 전송 소스를 알려줍니다. `COUNT` 및 `RATE` 메트릭 유형은 시간 경과에 따른 메트릭 값의 변화라는 동일한 개념을 나타내므로 서로 매우 유사합니다. 하지만 이들은 서로 다른 논리를 사용합니다.

* `RATE`: 시간 경과(_초당_)에 따른 정규화된 값 변화.
* `COUNT`: 주어진 시간 간격 동안 값의 절대적 변화.

사용 사례 및 제출 방법에 따라 한 메트릭 유형이 다른 유형보다 제출에 더 적합할 수 있습니다. 예를 들어, 다음과 같습니다.

| 제출된 메트릭 유형 | 사용 사례                                                                                                                                                                               |
|-----------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `RATE`                | 시간 경과에 따라 여러 호스트에서 수신된 요청 수를 모니터링하려고 합니다.                                                                                                    |
| `RATE`                | 소스 전반에서 시간 간격별 카운트 데이터가 일관되게 제출되도록 제어할 수 없으므로, 업스트림에서 비교할 수 있도록 각 시간 간격별로 정규화합니다. |
| `COUNT`               | 함수가 호출된 횟수를 계산하려고 합니다.                                                                                                                            |
| `COUNT`               | 주어진 시간 동안 발생한 수익을 계산합니다.                                                                                                        |

`RATE`와 `COUNT`는 동일한 메트릭 유형이 아니므로 Datadog 그래프 및 모니터 내에서 동작이나 형태가 동일하지 않습니다. `RATE`와 `COUNT` 표현 간에 메트릭을 즉석에서 변경하려면 그래프와 모니터 내에서 Datadog의 인앱 수정자 함수를 사용하세요.

## 인앱 수정자 {#in-application-modifiers}

2가지 주요 인앱 수정자는 `as_count()`와 `as_rate()`입니다.

| 수정자    | 설명                                                                                                                                                                                                                                                                   |
|--------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `as_count()` | 주어진 메트릭을 `COUNT` 형식으로 표시하는 데 필요한 작업을 설정하여 [롤업 간격][2] 동안 메트릭 값의 절대적 변동을 보여줍니다. **참고:** 롤업 간격에 따라 달라지므로 [더 긴 시간 간격을 그래프로 표시하면 그래프 모양이 달라집니다][3]. |
| `as_rate()`  | 주어진 메트릭을 `RATE` 형식으로 표시하는 데 필요한 작업을 설정하여 초당 메트릭 값의 절대적 변동을 보여줍니다.                                                                                                                                     |

적용한 메트릭 유형에 따라 동작이 달라집니다.

{{< tabs >}}
{{% tab "COUNT" %}}

* `as_count()`의 효과:
  * 모든 [보간][1]을 비활성화합니다.
  * 시간 애그리게이터를 `SUM`으로 설정합니다.
* `as_rate()`의 효과:
  * 모든 [보간][1]을 비활성화합니다.
  * 시간 애그리게이터를 `SUM`으로 설정합니다.
  * 결과를 정규화하기 위해 집계 이후 샘플링 간격으로 나눕니다. 예를 들어, 매초 제출된 `[1,1,1,1].as_rate()` 포인트의 롤업 간격이 20초라면 `[0.05, 0.05, 0.05, 0.05]`가 생성됩니다.

**참고**: 아주 짧은 간격(시간 집계가 발생하지 않는 경우)에서는 정규화가 수행되지 않으므로 원시 메트릭 값의 개수가 반환됩니다.

[1]: /ko/metrics/guide/interpolation-the-fill-modifier-explained/

{{% tab "RATE" %}}

* `as_count()`의 효과:
  * 모든 [보간][1]을 비활성화합니다.
  * 시간 애그리게이터를 SUM으로 설정합니다.
  * 집계 후 결과에 샘플링 간격을 곱합니다. 예를 들어, 매초 제출된 `[0.05, 0.05, 0.05, 0.05].as_count()` 포인트의 롤업 간격이 20초라면 `[1,1,1,1]`이 생성됩니다.
* `as_rate()`의 효과:
  * 모든 [보간][1]을 비활성화합니다.
  * 시간 애그리게이터를 `SUM`으로 설정합니다.
  * 쿼리 롤업 간격의 최솟값을 메트릭의 메타데이터 간격으로 설정합니다. 메트릭의 제출 간격보다 짧은 롤업 간격으로 요청된 쿼리는 메타데이터 간격과 일치하도록 자동으로 상향 조정됩니다.
  * 집계 후 각 전체 버킷의 크기를 `min(metadata_interval, rollup_interval) / rollup_interval`로 재조정합니다. 롤업 간격이 메타데이터 간격과 같으면 아무 작업도 수행하지 않으며, 버킷 값은 집계 후 `SUM`과 같습니다. 롤업 간격이 메타데이터 간격보다 크면 해당 값은 해당 버킷에 있는 `per-second` 비율 샘플의 시간 평균이 됩니다. 예를 들어, `60 seconds`마다 제출되는 메트릭을 `1800 second` 롤업 간격으로 쿼리하면 `as_rate()`는 각 전체 버킷에 대해 `post_aggregation / 30`을 반환합니다.
  * 가장 오른쪽의 부분 버킷(쿼리 종료 시간이 롤업 경계와 일치하지 않는 경우)을 재조정하여 인위적으로 낮은 값 대신 해당 부분 구간에서 실제로 관찰된 샘플의 평균을 나타내도록 합니다.

  **참고**: `RATE` 메트릭에 설정된 메타데이터 간격이 없으면 위의 재조정 단계가 적용되지 않으며 시간 애그리게이터는 `SUM` 대신 `AVG`를 사용합니다.

  **참고**: 예를 들어, 이를 검증할 때는 [고급 그래프 작성][2]의 공식 `(post_aggregation / rollup_interval) * min(metadata_interval, rollup_interval)`을 사용하세요. 이 표현식은 활성 롤업 간격을 숫자 값으로 사용하므로 기본 시계열 쿼리 위젯에서 직접 플로팅할 수 없습니다.

[2]: /ko/dashboards/querying/#advanced-graphing

{{% tab "GAUGE" %}}

`GAUGE` 메트릭 유형은 메트릭의 최종 절대값을 나타내며, `as_count()` 및 `as_rate()` 수정자는 게이지가 Metrics Explorer에 저장되거나 표시되는 방식에 영향을 주지 않습니다.

**참고**: 모니터에서 게이지 메트릭에 `as_count()`를 적용하면 `pct_change()`와 같은 롤업 종속 함수의 평가 경로가 변경됩니다.
- `as_count()` 미적용 시: 버킷별로 함수가 적용되고 해당 값이 평가 기간 동안 합산되므로, 데이터가 드문드문 수집되는 게이지 큰 음수 값이 생성될 수 있습니다.
- `as_count()` 적용 시: 함수가 적용되기 전에 시계열이 버킷화되어 집계되므로, 의도한 윈도우 수준 계산과 일치하게 됩니다.

### `weighted()` 수정자 {#the-weighted-modifier}

`pod name` 또는 `container_name`과 같은 태그는 특히 컨테이너화된 애플리케이션의 비용 관리, 용량 계획 또는 자동 확장을 위한 쿼리를 생성할 때 높은 태그 변동을 일으킵니다. 태그 변동과 관계없이 게이지 쿼리의 수학적 정확성을 보장하려면 인앱 수정자 `.weighted()`를 사용할 수 있습니다. 수정자 `.weighted()`를 사용하면 Datadog이 자주 변동되는 이러한 태그의 수명을 기준으로 메트릭 값의 가중치를 적절하게 조정할 수 있습니다. 

`.weighted()` 수정자는 다음 두 조건이 모두 충족되는 경우에만 게이지 쿼리에 자동으로 추가됩니다.

- 게이지 메트릭이 정기적으로 제출되어 데이터 공백 구간에 보간이 발생하지 않습니다.
- 제출 간격이 올바르게 정의된 후 설정되어 있습니다. 

Datadog Agent 또는 통합이 수집 시점에 메트릭에 대한 제출 간격을 설정합니다. 제출 간격은 [Metrics Catalog 페이지][4]에서 수정할 수 있습니다.

## Datadog 내에서 메트릭 유형 수정 {#modify-a-metrics-type-within-datadog}

일반적으로는 필요하지 않지만 메트릭 유형은 [Metrics Catalog 페이지][4]에서 변경할 수 있습니다.

{{< img src="metrics/custom_metrics/type_modifiers/metric_type.png" alt="메트릭 유형" style="width:70%;">}}

사용 사례 예시:

1. 처리된 요청 수를 세는 `app.requests.served`라는 메트릭이 있는데 실수로 StatsD에서 `GAUGE`로 해당 메트릭을 제출했습니다. 따라서 해당 메트릭의 Datadog 유형은 `GAUGE`입니다.

2. 시간 집계를 위해 `app.requests.served`를 StatsD `COUNT` 메트릭으로 제출하려고 했습니다. 이 메트릭은 _"지난 하루 동안 총 몇 개의 요청이 처리되었나요?"_와 같은 질문에 답하는 데 도움이 됩니다. 이때, `sum:app.requests.served{*}`를 쿼리합니다(이는 `GAUGE` 메트릭 유형에는 적합하지 않음).

3. `app.requests.served`라는 이름을 유지하고 싶어 더 적절한 `COUNT` 유형으로 새 메트릭 이름을 제출하는 대신 다음과 같은 업데이트를 수행하여 `app.requests.served`의 유형을 변경할 수 있습니다.
  * N개의 요청이 처리된 후 `dogstatsd.increment('app.requests.served', N)`를 호출하는 제출 코드 업데이트
  * Metrics Catalog 페이지에서 Datadog 인앱 유형을 `RATE`로 업데이트

이로 인해 `app.requests.served`에 대한 유형 변경 전에 제출된 데이터가 잘못 작동하게 됩니다. 이는 해당 데이터가 `RATE`가 아닌 인앱 `GAUGE`로 해석되는 형식으로 저장되었기 때문입니다. 3단계 이후에 제출된 데이터는 올바르게 해석됩니다.

`GAUGE` 유형으로 제출된 과거 데이터를 잃고 싶지 않다면 `app.requests.served`의 유형은 변경하지 않은 상태에서 새로운 유형으로 메트릭 이름을 새로 생성하세요.

**참고**: AgentCheck의 경우 `self.increment`는 단조 증가 카운터의 델타를 계산하지 않고, 대신 검사 실행 시 전달된 값을 보고합니다. 단조 증가 카운터에 대한 델타 값을 보내려면 `self.monotonic_count`를 사용하세요.
