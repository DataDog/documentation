## 개요 {#overview}

이 4가지 구현 템플릿은 사용되는 메커니즘, 역할과 팀의 구성 방식, 계층 간 연계 방식을 포함하여 액세스 전략이 완전히 구현된 모습을 보여줍니다. 이 템플릿은 특정 기업이 아닌 일반적인 조직 유형을 나타냅니다. 이 템플릿을 자체 구현의 출발점으로 활용합니다.

## 템플릿 선택 {#choose-your-template}

다음 질문을 통해 조직에 가장 적합한 패턴을 파악할 수 있습니다.

| 질문 | '예'라고 답한 경우 참고할 템플릿 |
| :---- | :---- |
| **특정 사용자 그룹에게 보이지 않아야 하는 규제 대상 데이터가 있습니까?** | [템플릿 1 (금융)](#template-1-large-financial-institution)<br>[템플릿 2 (규제 대상 다중 사업부)](#template-2-regulated-enterprise-with-multiple-business-units) |
| **사업부 간 데이터를 완전히 격리해야 하는 엄격한 규정 준수 요건이 있습니까?** | [템플릿 2 (규제 대상 다중 사업부)](#template-2-regulated-enterprise-with-multiple-business-units) |
| **API 키 사용량이 많고 자동화 파이프라인이 많습니까?** | [템플릿 3 (대규모 기술 기업)](#template-3-large-technology-company) |
| **공유 플랫폼에서 여러 내부 테넌트 또는 클라이언트에게 서비스를 제공합니까?** | [템플릿 4 (플랫폼 제공업체)](#template-4-government-agency--platform-provider) |
| **Terraform 또는 유사한 IaC 도구를 통해 구성을 관리합니까?** | [템플릿 4 (플랫폼 제공업체)](#template-4-government-agency--platform-provider) |
| **여러 조직을 운영하며 조직 전반에 일관된 액세스 제어가 필요합니까?** | [템플릿 4 (플랫폼 제공업체)](#template-4-government-agency--platform-provider) |

## 템플릿 1: 대규모 금융 기관 {#template-1-large-financial-institution}

### 프로필 {#profile}

소매 금융, 투자 은행, 자산 관리 및 보험 부문에 걸쳐 15,000명의 Datadog 사용자를 보유한 글로벌 금융 서비스 회사입니다. 사업 부문별로 구성된 150개 팀을 포함하는 단일 Datadog 조직을 운영합니다. SOC 2, PCI DSS 및 여러 국가 금융 규제 기관의 규제를 받습니다. SCIM 프로비저닝을 지원하는 Okta를 ID 관리에 사용합니다.

### 액세스 전략 {#access-strategy}

| 계층 | 구현 |
| :---- | :---- |
| **조직 구조** | Data Access Control을 사용하여 사업부 간 데이터를 분리하면서도 사업부 간 인시던트 조사 기능을 유지하는 단일 조직 |
| **사용자 지정 역할** | 5가지 역할: 읽기 전용(감사자 및 규정 준수 담당자), 표준 사용자(대부분의 엔지니어), 플랫폼 관리자, 제한된 사용자(계약자) 및 트레이딩 플로어(규제 대상 데이터에 대한 확장된 로그 액세스 권한) 자동 업데이트는 표준 역할 템플릿을 따르도록 구성되었습니다. |
| **ID** | Okta를 통한 SCIM 프로비저닝 각 사업부에는 Datadog 팀에 매핑된 별도의 Okta 그룹이 있습니다. 역할은 Okta 그룹 멤버십에 따라 할당되며, 규정 준수 요건에 따라 분기별 액세스 검토가 수행됩니다. |
| **데이터 제한** | 트레이딩 데이터(`data_sensitivity:trading`)에 대한 Data Access Control 데이터셋의 액세스 권한을 트레이딩 팀과 규정 준수 팀으로 제한 PII 태그가 지정된 데이터(`data_sensitivity:pii`)를 위한 별도의 데이터셋으로, 개인정보 보호 팀만 액세스 가능 제한된 데이터셋에 포함되지 않은 데이터는 기본 설정인 **Unrestricted** 상태로 유지됩니다. |
| **자산 보호** | 모든 프로덕션 모니터와 운영 대시보드의 편집 권한을 해당 자산을 소유한 팀으로 제한 '플랫폼 거버넌스' 팀에는 모든 자산의 편집 제한을 무시할 수 있는 권한이 있습니다. |
| **키 및 토큰** | 각 CI/CD 파이프라인별 서비스 계정 특정 API 엔드포인트로 사용 범위가 제한된 애플리케이션 키 팀별 API 키 Terraform을 통해 적용되는 90일 주기의 애플리케이션 키 교체 |
| **감사** | Audit Trail을 활성화하여 역할 변경, 키 생성 및 Data Access Control 정책 수정 시 경보 발생 규제 기관에 제출할 분기별 액세스 검토 보고서 생성 |

### 핵심 요약 {#key-takeaway}

Data Access Control을 통해 이 조직은 사업부 간 엄격한 데이터 경계를 유지하면서도 통합된 관측 가능성을 위해 단일 조직을 운영할 수 있습니다. 핵심 성공 요인은 데이터 수집 시 일관된 태그 지정입니다. 신뢰할 수 있는 `data_sensitivity` 태그가 없으면 Data Access Control로 데이터 경계를 강제할 수 없습니다.

## 템플릿 2: 다수의 사업부를 보유한 규제 대상 기업 {#template-2-regulated-enterprise-with-multiple-business-units}

### 프로필 {#profile-1}

항공우주 및 방위, 상업용 전자제품, 의료, 운송, 에너지 등 5개 주요 사업부에 걸쳐 8,000명의 Datadog 사용자를 보유한 다국적 대기업입니다. 각 사업부에는 고유한 규정 준수 체계가 적용됩니다(방산 부문은 ITAR, 의료 부문은 HIPAA, 에너지 부문은 SOX). 상위 조직 아래에 구성된 12개의 Datadog 조직을 운영합니다. SAML 매핑과 보조 SCIM 기능을 지원하는 Entra ID(Azure AD)를 사용합니다.

### 액세스 전략 {#access-strategy-1}

| 계층 | 구현 |
| :---- | :---- |
| **조직 구조** | 12개 하위 조직 방산 사업부는 메타데이터까지 완전히 격리해야 하므로 별도의 조직을 운영할 필요가 있습니다. 다른 사업부는 지역 및 비즈니스 기능에 따라 조직을 공유합니다. 상위 조직은 Cross-Org Visibility를 통해 청구를 중앙에서 관리하고 경영진 대시보드를 제공하는 데 사용됩니다. |
| **사용자 지정 역할** | 각 하위 조직에는 규정 준수 요건에 맞게 설정된 4~5개의 사용자 지정 역할이 있습니다. 방산 조직은 엔지니어링 담당자가 아닌 직원의 모든 쓰기 권한을 제거한 최소 권한의 사용자 지정 역할을 사용합니다. 의료 조직에는 PHI 태그가 지정된 데이터에 액세스할 수 있는 전용 HIPAA 분석가 역할이 있습니다. |
| **ID** | Entra ID를 통한 SAML 인증 및 사업부별 조건부 액세스 정책 방산 사업부에서는 MFA와 관리형 장치 증명이 필요합니다. 팀 멤버십 관리를 위한 SCIM |
| **데이터 제한** | 방산 조직은 제한된 데이터셋에 포함되지 않은 데이터에 **Restricted** 설정을 적용합니다. 모든 데이터는 기본적으로 숨겨져 있으며, 사용자에게는 특정 데이터셋에 대한 액세스 권한이 명시적으로 부여됩니다. 의료 조직은 Data Access Control의 기본 **Unrestricted** 설정과 PHI 태그가 지정된 텔레메트리용 제한된 데이터셋을 사용합니다. 상업 부문은 서비스 기반 데이터 분리를 위해 Data Access Control의 기본 **Unrestricted** 설정을 사용합니다. |
| **자산 보호** | 각 조직은 자체 자산 액세스 정책을 관리합니다. 방산 및 의료 조직의 프로덕션 모니터는 해당 모니터를 소유한 팀과 사업부 보안 팀만 편집할 수 있습니다. |
| **조직 간** | 상위 조직에서 Cross-Org Visibility를 활성화하여 모든 사업부의 시스템 상태를 보여주는 경영진 대시보드를 제공합니다. 하위 조직 전반의 정책을 중앙에서 관리하기 위한 Organization Groups(미리 보기) |
| **키 및 토큰** | 모든 키를 Terraform으로 관리 방산 조직은 키 또는 역할을 변경할 때마다 승인 단계를 거쳐야 하는 보안 강화 Terraform 파이프라인을 사용합니다. 서비스 계정만 사용 개인 소유 애플리케이션 키 없음 |

### 핵심 요약 {#key-takeaway-1}

이 사례에서는 엄격한 규정 준수 요건으로 인해 다중 조직 구성이 필요합니다. 규정에 따라 엄격한 데이터 격리 및 레지던시 요건이 적용됩니다. 방산 사업부에서 **Restricted** 설정을 사용하는 것은 해당 규제 환경의 기본 거부 원칙을 반영합니다. Cross-Org Visibility를 사용하면 데이터 격리를 유지하면서 중앙 집중식 보고 기능을 활용할 수 있습니다.

## 템플릿 3: 대규모 기술 기업 {#template-3-large-technology-company}

### 프로필 {#profile-2}

12,000명의 Datadog 사용자를 보유하고 대규모 결제 처리 및 커머스 플랫폼을 운영하는 글로벌 기술 기업입니다. 20개 주요 제품군을 아우르는 단일 조직을 운영합니다. Teams API 및 Terraform과 통합된 독점 ID 시스템을 사용합니다. 500개 이상의 활성 애플리케이션 키와 200개의 서비스 계정을 사용하는 등 API 사용량이 많습니다.

### 액세스 전략 {#access-strategy-2}

| 계층 | 구현 |
| :---- | :---- |
| **조직 구조** | 20개 주요 제품군을 아우르는 단일 조직 Data Access Control과 Teams를 통해 각 조직 내부에 경계를 설정합니다. 샌드박스 및 비프로덕션 환경을 위한 별도의 조직 2개 |
| **사용자 지정 역할** | Terraform 모듈을 통해 전사적으로 표준화된 5개의 사용자 지정 역할: 읽기 전용, 표준, 플랫폼, 조직 관리자, 계약자 계약자 역할을 제외한 모든 역할에 자동 업데이트가 활성화되어 있습니다. |
| **ID** | Teams API 및 Terraform과 통합된 독점 IdP 내부 서비스 소유권 레지스트리를 기준으로 매일 밤 팀 멤버십을 동기화합니다. 중앙 직원 디렉터리에서 정보를 가져오는 Terraform 모듈을 통해 역할 할당을 관리합니다. |
| **데이터 제한** | 주요 민감 텔레메트리 유형(로그, RUM, 클라우드 비용)에 대해 제품군별 데이터를 분리하는 표준 Data Access Control 서비스를 기반으로 제한된 데이터셋을 생성하고, 명시적인 데이터셋 할당을 통해 팀 간 액세스 권한을 부여합니다. 계약자 사용자는 계약 범위에 명시된 일부 서비스에만 액세스할 수 있습니다. |
| **자산 보호** | 모든 프로덕션 모니터를 해당 모니터의 소유 팀으로 제한 대시보드는 대부분의 사용자가 볼 수 있지만 편집 권한은 제한됩니다. '플랫폼 SRE' 팀에는 인시던트 대응을 위해 액세스 제한을 무시할 수 있는 권한이 있습니다. |
| **키 및 토큰** | 팀당 API 키 1개 모든 자동화에 서비스 계정 사용 특정 API 작업으로 사용 범위가 제한된 애플리케이션 키 미사용 키를 식별하고 폐기하기 위한 분기별 감사 |

### 핵심 요약 {#key-takeaway-2}

팀별 API 키와 분기별 감사는 이러한 규모의 거버넌스를 관리하는 데 필수적입니다. Data Access Control, Teams 및 세분화된 액세스 제어를 통해 조직 내부에 경계를 설정할 수 있습니다.

## 템플릿 4: 정부 기관/플랫폼 제공업체 {#template-4-government-agency-platform-provider}

### 프로필 {#profile-3}

5,000명의 Datadog 사용자를 보유하고 약 200개의 내부 기관, 부서 또는 고객 테넌트를 위한 공유 관측성 플랫폼을 운영하는 대규모 정부 기관 또는 관리형 서비스 제공업체입니다. 환경(운영, 스테이징, 개발)별로 구분된 3개의 Datadog 조직을 운영하지만, 각 조직에는 서로 격리해야 하는 여러 테넌트의 데이터가 포함되어 있습니다. ServiceNow CMDB를 통해 통합된 Entra ID를 사용하며, 모든 구성은 Terraform으로 관리됩니다.

### 액세스 전략 {#access-strategy-3}

| 계층 | 구현 |
| :---- | :---- |
| **조직 구조** | 테넌트가 아닌 환경별로 구분된 3개 조직 Teams 및 Data Access Control을 통해 조직 내부를 세분화하여 테넌트 간 데이터를 격리합니다. 이를 통해 엄격한 경계를 유지하면서도 200개 이상의 개별 조직을 관리하는 데 따른 부담을 줄일 수 있습니다. |
| **사용자 지정 역할** | 5개 역할: 읽기 전용(감사자), 표준 사용자, 플랫폼 관리자, 조직 관리자, 제한된 관찰자(단일 테넌트 데이터에 대한 제한된 가시성이 필요한 이해관계자용). 플랫폼 관리자 역할에는 팀 기반 자산 제한을 우회하는 권한이 포함됩니다. |
| **ID** | 복잡한 ID 체계: Entra ID가 사용자 그룹을 ServiceNow CMDB에 동기화합니다. CMDB 레코드에 따라 사용자의 Datadog 조직, 팀 및 역할이 결정됩니다. 변경 사항은 Terraform을 사용하여 Datadog에 적용되기 전에 ServiceNow 승인 워크플로우를 거칩니다. SAML 속성 매핑이 초기 로그인 프로비저닝을 제공합니다. |
| **데이터 제한** | `agency` 태그로 정의된 테넌트 기관별 데이터셋을 사용하는 표준 Data Access Control 각 기관의 팀은 해당 기관의 데이터에만 액세스할 수 있습니다. 플랫폼 팀은 용량 계획 및 인시던트 대응을 위해 모든 테넌트의 인프라 수준 데이터에 액세스할 수 있습니다. |
| **자산 보호** | 각 기관의 모니터와 대시보드 편집 권한을 해당 기관의 팀으로 제한 중요한 공유 인프라 모니터(네트워크, DNS, 공유 컴퓨팅)를 플랫폼 팀으로 제한 관리자 액세스가 차단되는 것을 방지하기 위해 모든 자산 액세스 목록에 관리자 제한 우회 팀('플랫폼 거버넌스')을 포함합니다. |
| **키 및 토큰** | ServiceNow 승인 단계를 거쳐 Terraform으로 모든 API 키와 서비스 계정 관리 데이터 전송을 위한 기관별 API 키 1개 공유 자동화 파이프라인용 서비스 계정 개인 소유 애플리케이션 키 사용 금지 모든 API 액세스는 SAT를 사용하는 서비스 계정을 통해 이루어집니다. |
| **코드 기반 관리** | 모든 역할, Teams, Data Access Control 데이터셋, 세분화된 액세스 제어 정책 및 키를 Terraform에서 정의 변경 사항은 코드 검토와 ServiceNow 승인을 거친 후 적용됩니다. 이러한 규모에서는 코드 기반 관리가 필수적입니다. 200개 테넌트의 경계를 수동으로 구성하는 방식은 지속할 수 없기 때문입니다. |

### 핵심 요약 {#key-takeaway-3}

테넌트 경계가 규제상 경계가 아닌 조직상 경계인 경우, 조직 내 세분화(Teams + Data Access Control)가 다중 조직 격리를 대체할 수 있습니다. 이러한 규모에서는 CMDB 기반 ID 체계와 Terraform을 통한 구성 관리가 필요합니다. 관리자 제한 우회 팀은 자산에 액세스 제한을 적용하기 전에 구성해야 하는 중요한 안전장치입니다.
