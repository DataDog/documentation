## 개요 {#overview}

Datadog은 실험 분석과 함께 진단 검사를 실행하여 롤아웃 결정을 내리기 전에 데이터 품질, 무작위화 및 구성 문제를 파악하도록 돕습니다. 검사에서 문제가 발견되면 Datadog은 이를 실험 결과 페이지에 경고, 메트릭 메시지 또는 실패한 진단 검사로 표시합니다.

리프트, 신뢰 구간 또는 글로벌 리프트를 해석하기 전에 실패한 진단 검사 또는 경고 배너부터 확인하세요.

## 트래픽 불균형 {#traffic-imbalance}

샘플 비율 불일치(SRM)라고도 하는 트래픽 불균형은 변형 간에 관찰된 할당이 구성된 할당 가중치와 크게 다른 경우를 의미합니다.

Datadog은 피어슨의 카이제곱 적합도 테스트를 사용하여 SRM을 감지합니다. 이 테스트는 관찰된 변형 카운트와 구성된 가중치에서 예상되는 카운트를 비교합니다. p-값이 `0.001` 미만일 때 진단이 실패하며, 이는 유의 수준(알파) `0.001`에 해당합니다. Datadog은 이 전체 검사에 최소 총 샘플 크기나 예상 카운트 요구 사항을 적용하지 않습니다.

이 테스트는 순차적으로 유효하지 않기 때문에 더 보수적인 α = 0.001 수준에서 테스트를 실행합니다. 더 보수적인 유의 수준은 오탐을 방지하는 데 도움이 됩니다.

SRM을 결과 해석을 방해하는 요소로 간주해야 합니다. 이는 실험의 효과적인 무작위화, 노출 로깅 또는 분석 모집단에 편향이 있음을 나타냅니다. 근본 원인을 찾아 해결하기 전까지는 리프트, 신뢰 구간 및 글로벌 리프트가 유효한 인과 추론을 뒷받침할 수 없습니다.

### 일반적인 원인 {#common-causes}

Datadog Feature Flags를 기반으로 하는 실험의 경우, 일반적인 원인은 다음과 같습니다.

- 트래픽 분할(변형에 할당된 상대적 비율)이 시작 후 변경되었으나(예: `90/10`에서 `50/50`으로 변경), 이전 분할 하에서 이루어진 할당이 분석 기간 내에 남아 있는 경우입니다.
- 노출 이벤트가 할당 후 변형에 따라 서로 다른 비율로 손실되는 경우입니다. 예를 들어, 변형별 리디렉션이나 충돌로 인해 버퍼링된 노출 이벤트가 Datadog에 도달하지 못할 수 있습니다.

실험 기간 동안 변형 간의 트래픽 분할을 일정하게 유지하세요. 균등하게 분할된 실험을 진행하려면, 두 변형 모두에 대해 [트래픽 노출][1]을 비례적으로 늘리도록 합니다. 예를 들어, 트래픽 노출을 `10/10` 분할에서 `50/50` 분할로 늘립니다. 이렇게 하면 상대적인 분할을 유지하면서 두 변형의 비율이 모두 비례적으로 증가합니다.

타겟팅 규칙, 타겟팅 키 또는 트래픽 노출을 변경하는 것만으로는 SRM이 발생하지 않습니다. 포함된 할당 모집단을 변형별로 다르게 변경하는 경우에만 이러한 변경이 SRM을 유발합니다. 그렇지 않은 경우 트래픽 볼륨이 변경되거나 다른 진단 결과가 발생할 수 있습니다. 예를 들어, 일관되지 않은 SDK `targetingKey`는 할당 및 메트릭 이벤트가 더 이상 동일한 대상에 조인되지 않을 때 **누락된 메트릭 데이터**를 유발할 수 있습니다. 동일한 기록 대상이 두 개 이상의 변형을 수신하는 경우에만 **혼합 할당**이 발생합니다.

웨어하우스 네이티브 실험의 일반적인 원인은 다음과 같습니다.

- Datadog에 구성된 각 변형의 예상 노출 비율이 업스트림 무작위화 시스템에서 사용하는 할당 확률과 일치하지 않는 경우입니다.
- [노출 SQL 모델][2]이 한 변형의 할당 대상을 다른 변형보다 더 자주 삭제하는 방식으로 필터링, 조인, 집계하거나 타임스탬프 제약 조건을 적용하는 경우입니다.
- 업스트림 할당 로깅에서 처리에 따라 텔레메트리가 손실되거나 한 변형이 잘못된 변형 키에 매핑되는 등, 변형별로 서로 다른 비율로 할당이 누락되거나 잘못 기록되는 경우입니다.
- 할당 후 발생하며 변형의 영향을 받을 수 있는 행동을 기반으로 한 대상이 분석에 포함되는 경우입니다. 예를 들어, 처리 의존적 적격성 이벤트나 봇 필터가 특정 변형을 더 높은 비율로 제외할 수 있습니다.

### 해결 방법 {#how-to-resolve}

1. SRM의 소스를 파악할 때까지 실험에 대한 의사 결정을 일시 중지합니다.
2. Datadog Feature Flags 기반 실험의 경우, 플래그의 [{{< ui >}}Version history{{< /ui >}}][3]에서 트래픽 분할 또는 변형 변경 사항이 있는지 검토하고, 혼합 할당을 확인하며, 노출 이벤트가 모든 변형에 대해 동일한 비율로 Datadog에 도달하는지 확인합니다.
3. 웨어하우스 네이티브 실험의 경우, Datadog의 각 변형에 대한 예상 노출 비율을 업스트림 할당 확률과 비교합니다. 노출 SQL 모델이 조인, 필터, 집계 및 타임스탬프 제약 조건을 적용하기 전후의 변형별 원시 할당 카운트를 비교합니다.
4. 불균형이 특정 세그먼트나 시간대에 국한되어 있는지 확인합니다. 세그먼트별 SRM 또는 시작 시간 SRM은 근본 원인을 좁히는 데 도움이 될 수 있습니다.
5. 불균형의 소스를 수정하고 실험 분석을 다시 실행하세요.

## 누락된 할당 {#missing-assignments}

Datadog에 실험에 대한 할당 데이터가 없으면 결과를 계산할 수 없습니다. 이는 Feature Flag가 평가되지 않거나, 트래픽이 실험 타겟팅 규칙에 도달하지 않거나, 웨어하우스 노출 SQL 모델이 지정된 **실험 ID** 및 **변형 ID** 값에 대해 분석 창에서 행을 반환하지 않을 때 발생할 수 있습니다.

웨어하우스 메트릭을 사용하는 Datadog Feature Flags 기반 실험의 경우, Datadog은 해당 노출을 웨어하우스의 `g_exposures` 표에 동기화하기 전에 할당을 기록할 수 있습니다. 웨어하우스 메트릭 결과는 동기화가 완료될 때까지 사용할 수 없습니다.

### 해결 방법 {#how-to-resolve-1}

- Datadog Feature Flags 기반 실험의 경우, 플래그가 올바른 환경에서 활성화되어 있는지, 그리고 애플리케이션이 예상되는 대상에 대해 플래그를 평가하고 있는지 확인합니다. 노출 이벤트에 대한 플래그의 {{< ui >}}Real-time metric overview{{< /ui >}}를 확인하세요.
- 웨어하우스 네이티브 실험의 경우, 노출 SQL 모델이 예상되는 **대상 키**, **타임스탬프**, **실험 ID** 및 **변형 ID** 값을 포함한 행을 반환하는지 확인합니다.
- 실험이 방금 시작된 경우, 다음 분석 실행을 기다리거나 {{< ui >}}Run an update now{{< /ui >}}를 클릭합니다.

## 혼합 할당 {#mixed-assignments}

동일한 실험에서 동일한 대상이 두 개 이상의 변형에 할당된 경우, Datadog은 해당 대상을 분석에서 제외합니다. Datadog은 각 할당 소스에 대해 고유한 대상을 분모로 사용하여 백분율을 별도로 계산합니다. 진단은 5% 이하일 때 통과, 5% 초과 20% 미만일 때 경고, 20% 이상일 때 실패로 처리됩니다. 제외되는 비율이 커질수록 결과의 대표성과 신뢰성이 떨어집니다.

### 해결 방법 {#how-to-resolve-2}

- Datadog Feature Flags 기반 실험의 경우, 플래그의 [{{< ui >}}Version history{{< /ui >}}][3]에서 시작 후 예상치 못한 변경 사항, 특히 실험 타겟팅 규칙, 트래픽 분할 또는 변형에 대한 변경 사항이 있는지 검토합니다.
- 웨어하우스 네이티브 실험의 경우, [노출 SQL 모델][2]에서 **실험 ID**에 매핑된 열이 더 넓은 플래그 키가 아닌 특정 실험이나 플래그 할당 키와 같은 실험 노출만을 식별하고 있는지 확인합니다.
- 웨어하우스 네이티브 [노출 SQL 모델][2]이 의도적으로 플래그 평가 로그를 읽는 경우, 실험 노출에 해당하지 않는 평가를 필터링합니다. 예를 들어, 모델이 플래그에 대한 모든 평가를 캡처하는 경우, 노출 램프는 대상이 실험 자격을 갖추기 전의 실험 전 대조군 경험을 기록한 다음, 자격을 갖춘 뒤의 무작위 처리 노출을 기록할 수 있습니다. 실험 전 플래그 평가는 실험의 일부가 아니므로 노출로 캡처되어서는 안 됩니다.
- 웨어하우스 네이티브 실험의 경우, 할당 데이터에서 충돌하는 변형 기록이 있는지 확인합니다.
- 충돌하는 할당의 소스를 수정하고 다음 분석을 다시 실행하세요.

## 차원 할당 불균형 {#dimensional-assignment-imbalance}

Datadog은 변형에 할당될 확률이 차원 값에 따라 크게 다를 때 실험에 플래그를 지정할 수 있습니다. 예를 들어, 특정 장치 유형, 국가, 플랜 또는 고객 등급의 경우 실험의 나머지 부분과 다른 분할 비율로 변형을 할당받을 수 있습니다.

각 할당 차원에 대해 Datadog은 변형과 차원 값 간의 독립성에 대한 피어슨 카이제곱 검정을 실행합니다. 여러 차원에 대한 테스트를 고려하여 Datadog은 본페로니 교정을 적용합니다. p-값이 `0.001 / n` 미만일 때 해당 차원은 실패하며, 여기서 `n`은 테스트된 적격 차원의 수입니다. Datadog은 해당 값에 대한 예상 변형 수가 5 미만인 경우 차원 값을 제외하고, 값이 100개를 초과하는 차원은 건너뛰며, 최소 두 개의 남은 차원 값과 양의 한계 카운트를 가진 두 개의 변형이 필요합니다. 건너뛴 차원은 `n`에 기여하지 않습니다. 적격 차원이 없으면 진단은 차원 테스트를 실행하지 않고 통과합니다.

전체 SRM 검사와 마찬가지로, 차원 테스트는 반복적인 분석 실행 전반에 걸쳐 순차적으로 유효하지 않습니다. 본페로니 교정은 한 번의 실행에서 테스트된 차원을 제어하며, 실험 데이터가 누적됨에 따라 반복되는 검사를 제어하지는 않습니다.

이 진단은 전체 트래픽 불균형 또는 샘플 비율 불일치(SRM)와는 별개이며, 전역 불균형만으로는 이 진단이 트리거되지 않습니다. 두 진단이 모두 실패하면, 영향을 받는 차원 값이 전체 SRM의 원인을 파악하는 데 도움이 될 수 있습니다. 예를 들어, 장치 유형에 대한 차원 불균형은 변형 전달, SDK 평가, 리디렉션, 페이지 성능, 충돌 또는 노출 텔레메트리에서의 기기별 버그를 가리킬 수 있습니다.

Datadog은 대상의 첫 번째 할당 기록에 있는 차원 값을 사용합니다. 나중에 대상의 차원 값이 변경되어도 이 진단이 발생하지 않아야 합니다.

### 해결 방법 {#how-to-resolve-3}

- 영향을 받는 차원 값을 검토하고 전체 트래픽 불균형 진단과 비교합니다.
- 플래그 평가, 변형 전달, 애플리케이션 동작 및 노출 텔레메트리에서 세그먼트별 차이를 조사합니다.
- 웨어하우스 네이티브 실험의 경우, 노출 SQL 모델이 의도한 할당 시간 속성 열을 매핑하고 세그먼트별로 노출을 다르게 필터링하지 않는지 확인합니다.
- 국소적 불균형의 소스를 수정하고 분석을 다시 실행하세요.

## 누락된 메트릭 데이터 {#missing-metric-data}

Datadog은 할당은 존재하지만 실험 분석에서 사용할 수 있는 메트릭 값을 찾을 수 없을 때 **누락된 메트릭 데이터**를 보고합니다. 단순 메트릭 및 비율 메트릭의 경우, 이상치 처리 전의 기여 값 중 최소 하나는 0이 아니어야 합니다. 모든 기여 값이 0이거나 null인 경우, 기본 메트릭에 대해서는 진단이 실패하고 보조 메트릭이나 가드레일 메트릭에 대해서는 경고가 표시됩니다. 백분위수 메트릭의 경우 0은 유효한 결과이며, null 결과만 누락된 것으로 간주됩니다. Datadog에서 메트릭이 기본 메트릭인지 확인할 수 없는 경우, 누락된 데이터를 실패로 처리합니다.

이 진단이 반드시 소스 이벤트가 발생하지 않았음을 의미하는 것은 아닙니다. 이벤트가 존재하더라도 메트릭 필터를 통과하지 못하거나, 실험 할당에 조인되지 않거나, 0 또는 null 메트릭 값만 생성할 수 있습니다.

### 일반적인 원인 {#common-causes-1}

- 메트릭 정의의 이벤트 이름, 집계, 필터 또는 데이터 소스가 전송되는 데이터와 일치하지 않습니다.
- 소스 이벤트가 발생하지 않거나, 대상의 첫 번째 할당 이전에만 발생하여 할당 후 어트리뷰션에서 제외됩니다.
- 메트릭 이벤트와 실험 할당이 동일한 대상을 다르게 식별합니다. 이러한 대상 식별자 불일치는 누락된 메트릭 데이터의 일반적인 원인입니다.
  - Datadog Feature Flags를 기반으로 하는 실험의 Product Analytics 또는 RUM 메트릭의 경우, 구성된 [대상 유형 속성][4]이 SDK `targetingKey`와 일치해야 합니다.
  - 웨어하우스 메트릭의 경우, [메트릭 SQL 모델][5]에 매핑된 대상 열은 할당 대상 열과 동일한 값을 포함해야 합니다. Datadog Feature Flags를 기반으로 하는 실험의 경우, 해당 값은 SDK `targetingKey`와 일치해야 합니다. 웨어하우스 네이티브 실험의 경우, [노출 SQL 모델][2]에 구성된 할당 대상 열과 일치해야 합니다.
- 웨어하우스 메트릭 SQL 모델이 분석 기간 내에 일치하는 행을 반환하지 않거나 예상되는 이벤트를 필터링합니다.

### 해결 방법 {#how-to-resolve-4}

1. 메트릭을 열고 이벤트 이름, 집계, 필터 및 데이터 소스가 올바른지 확인합니다. 최근의 일치하는 데이터에 대해 메트릭 이벤트 볼륨 차트를 검사합니다.
2. 할당된 대상의 식별자를 해당 메트릭 이벤트의 식별자와 비교합니다. 구성된 대상 유형 속성 또는 매핑된 웨어하우스 열이 SDK `targetingKey` 또는 노출 SQL 모델에 구성된 할당 대상 열과 동일한 값을 포함하는지 확인합니다.
3. 메트릭 이벤트가 대상의 첫 번째 할당 이후 및 실험 분석 기간 내에 발생하는지 확인합니다.
4. Datadog Feature Flags를 기반으로 하는 실험의 경우, [소스 코드 통합][6]이 구성되어 있다면 기본 메트릭의 **누락된 메트릭 데이터** 실패에 대해 [{{< ui >}}Ask Bits{{< /ui >}}][7]를 클릭합니다. Bits는 Feature Flag가 평가되는 소스 위치를 검사하고, 근처의 메트릭 계측을 검사하는 데 도움을 줄 수 있습니다. 빈 코드 검색은 결정적이지 않으며 SDK나 플래그가 애플리케이션에서 누락되었음을 증명하지 않습니다.
5. 웨어하우스 메트릭의 경우, 메트릭 SQL 모델을 실행하거나 해당 소스 표를 직접 쿼리합니다.
6. 메트릭 정의, ID 매핑, 이벤트 타이밍 또는 계측 문제를 수정한 다음 실험 분석을 다시 실행하세요.

## 메트릭이 0으로 윈저라이즈됨 {#metric-winsorized-to-zero}

이상치 처리는 분산을 줄이기 위해 극단적인 메트릭 값을 제한합니다. Datadog은 이상치 처리 전에는 최소 하나의 원시 값이 0이 아니었음에도 불구하고 이상치 처리 후 모든 변형의 전체 결과가 0이거나 null로 남을 때 경고합니다. 비율 메트릭의 경우, Datadog은 분자와 분모를 별도로 검사합니다. 이 진단에는 백분율이나 최소 샘플 임계값이 없으며 실험에 실패하지 않습니다.

이는 소수의 대상만이 메트릭 이벤트를 수행하고 이상치 처리가 모든 관측값을 0으로 제한할 때 발생할 수 있습니다. 예를 들어, 메트릭에 99백분위수 상한 윈저라이징 경계가 있고 0이 아닌 값을 가진 대상이 1% 미만인 경우, 상한값은 0이 됩니다. 그러면 0이 아닌 모든 값은 이상치로 취급되어 0으로 제한됩니다.

백분위수 윈저라이징의 경우, Datadog은 할당된 모든 대상 또는 0이 아닌 값만을 사용하여 경계값을 계산할 수 있습니다. 계산에서 0을 제외하면 구조적 0이 희소 메트릭에 대해 0의 경계값을 설정하는 것을 방지할 수 있습니다. 이 전략은 분석에서 0 값을 가진 대상을 제거하지 않습니다. 백분위수 경계값을 계산할 때만 0을 제외하며, Datadog은 이를 모든 대상에 적용합니다.

### 해결 방법 {#how-to-resolve-5}

1. 메트릭을 엽니다.
2. {{< ui >}}Experiment settings{{< /ui >}} 아래에서 {{< ui >}}Outlier handling{{< /ui >}}을 검토합니다. 백분위수 윈저라이징을 사용하는 희소 메트릭의 경우, 0이 아닌 값에서만 경계값을 계산합니다.
3. 윈저라이징 백분위수를 변경하거나 이상치 처리를 비활성화하여 경고를 해결하고 싶을 수 있습니다. 그러나 이 진단을 트리거하는 메트릭은 통계적 검정력이 낮은 경향이 있습니다. 메트릭을 의사결정에 활용하기 전에 [샘플 크기 계산기][8]를 사용하여 실험 기간과 최소 감지 효과를 추정하세요.
4. 메트릭을 업데이트한 후 실험 분석을 다시 실행하세요.

## 실험 전 메트릭 불균형 {#pre-experiment-metric-imbalance}

CUPED가 활성화되면 Datadog은 실험 전 메트릭 값을 사용하여 분산을 줄입니다. 노출 전에는 실험이 A/A 테스트처럼 작동해야 합니다. 즉, 처리는 할당 전에 발생한 행동에 영향을 줄 수 없습니다. 감지된 불균형은 우연히 발생할 수 있으며, 근본 원인이 처리와 상관관계가 있는 선택, 데이터 유출 또는 무작위화 문제를 나타낼 수도 있습니다. 이러한 근본적인 문제는 CUPED의 가정을 위반하거나 CUPED 조정 이상의 결과를 무효화할 수 있습니다.

Datadog은 실험 전 구성 요소 평균의 처리군-대조군 차이에 대해 양측 순차 정규 혼합 신뢰 구간을 계산합니다. 단순 메트릭은 메트릭 평균을 테스트하고, 비율 메트릭은 분자와 분모 평균을 독립적으로 테스트하며, 백분위수 메트릭은 내부 S 및 N 구성 요소를 테스트합니다. Datadog은 검정군 전체 유의수준(family significance level, 알파)을 `0.05`로 설정하고, 적격 메트릭·처리 변형·구성 요소 검사 전반에 다중 비교 보정을 적용합니다. 조정된 신뢰 구간이 0을 엄격하게 제외하면 진단이 실패하며, 0에 닿는 구간은 통과합니다. 데이터가 누적됨에 따라 분석이 반복되어도 신뢰 구간은 유효하게 유지됩니다. 이 테스트는 양의 분산을 가진 관측치를 필요로 하지만 명시적인 최소 샘플 크기는 없습니다.

### 일반적인 원인 {#common-causes-2}

- 처리 의존적 ID 연결. 예를 들어, 실험에서 익명 ID를 무작위화하지만 계정 수준의 구매를 분석하는 경우, 익명-계정 매핑은 로그인 후에만 생성되는 경우를 생각해 보겠습니다. 노출 후 로그인이 소급하여 이전 구매 내역을 포함하거나 다시 키를 지정하는 경우, 로그인을 증가시키는 처리는 더 많은 실험 전 내역이 처리에 나타나게 할 수 있습니다.
- 타임스탬프 잘림 또는 일치하지 않는 시간 세분성. 예를 들어, 노출에는 이벤트 타임스탬프가 있지만 메트릭 데이터는 일 단위로 집계되어 자정에 표시되므로 해당 날짜의 노출 후 이벤트가 노출보다 앞선 것처럼 보일 수 있습니다.
- 나중 이벤트를 더 이른 타임스탬프와 저장하거나 비교하는 일관되지 않은 시간대 또는 일광 절약 시간 처리.
- 사전 처리 결과 또는 이전 처리와 상관관계가 있는 할당 규칙. 예를 들어, 식별자 범위에서 직접 변형을 할당하거나 실험 전반에 걸쳐 동일한 버킷 매핑을 재사용하면 할당과 이전 실험 노출 간의 관계가 유지될 수 있습니다.
- 변형 간에 실험 전 데이터의 가용성을 다르게 만드는 무작위화, 타겟팅, 대상 ID 또는 데이터 처리 문제.

### 해결 방법 {#how-to-resolve-6}

1. 각 변형에 대해 실험 전 데이터를 사용할 수 있고 대표성이 있는지 확인하고, 실험 전 기간 동안 메트릭 정의가 변경되었는지 확인합니다.
2. 원시 할당 및 메트릭 타임스탬프를 원래 세분성과 일관된 시간대에서 비교합니다. 일일 롤업, 타임스탬프 변환 또는 일광 절약 시간 전환으로 인해 노출 후 이벤트가 실험 전 기간으로 이동할 수 있는지 확인합니다.
3. 대상 ID 매핑을 점검합니다. 로그인과 같은 노출 후 행동이 분석 가능한 실험 전 이력이 있는 대상을 결정하지 못하도록 하세요.
4. 할당이 사전 처리 결과, 대상 속성 및 이전 처리와 독립적인지 확인합니다. Datadog Feature Flags를 기반으로 하는 실험의 경우 SDK `targetingKey`를 안정적으로 유지하세요. Datadog은 플래그 키와 `targetingKey`를 사용하여 대상을 동일한 롤아웃 버킷에 유지합니다. 웨어하우스 네이티브 실험의 경우 대상 식별자를 실험별 솔트 또는 키와 결합하는 결정론적 할당 방법을 사용합니다. 이렇게 하면 실험 전반에 걸쳐 동일한 할당 패턴을 재사용하지 않고 실험 내에서 대상을 동일한 변형에 유지할 수 있습니다.
5. ID, 타임스탬프, 무작위화 또는 데이터 처리 문제를 수정한 다음 분석을 다시 실행하세요. 선택 편향, 노출 후 데이터 유출 또는 잘못된 무작위화로 인해 불균형이 발생하는 경우 CUPED를 비활성화해도 실험이 유효하게 되지 않습니다.

## 타당하지 않은 사전 분포 {#implausible-prior}

베이지안 분석의 경우 Datadog은 상대적 리프트에 대해 양측 사전 예측 검사를 실행합니다. 이 검사는 사전 분포의 분산과 추정치의 샘플링 불확실성을 모두 고려합니다. Datadog은 사전 예측 분포 하에서 실험에서 추정된 리프트만큼 극단적인 리프트가 어느 한 방향으로든 관찰될 확률이 1% 미만일 때 경고를 표시합니다. Datadog은 다중 검정 보정 없이 각 적격 메트릭-처리 비교를 테스트합니다. 이 검사를 위해서는 양수이고 유한한 표준 오차가 필요하지만 명시적인 최소 샘플 크기는 없습니다. 경고가 발생했다는 것은 선택한 사전 분포 하에서 관찰된 효과가 이례적이었음을 나타냅니다.

예를 들어, 많은 전환율 실험의 실제 리프트는 5% 미만이므로 평균 0, 표준 편차 0.05인 기본 정규 사전 분포가 합리적인 선택이 될 수 있습니다. 실험을 통해 대부분의 사용자가 전환하지 못하게 만들던 결함이 있는 결제 페이지를 수정하는 경우, 훨씬 더 큰 리프트가 타당할 수 있습니다. 이 경우 기본 사전 분포가 너무 보수적이어서 추정된 효과를 너무 많이 축소할 수 있습니다.

### 해결 방법 {#how-to-resolve-7}

- 추정된 리프트를 해당 메트릭의 과거 효과 및 개입이 타당하게 생성할 수 있는 효과와 비교합니다.
- 실험의 통계 분석 계획 및 사전 설정을 검토합니다.
- 추정된 리프트가 그럴듯하지만 사전 분포가 해당 크기의 효과에 매우 낮은 확률을 할당하는 경우, 관련 도메인 지식을 반영하도록 사전 분포를 업데이트하고 분석을 다시 실행하세요.

## 세그먼트 수준 성능 저하 {#segment-level-degradation}

Datadog은 세그먼트의 점 추정치가 메트릭의 원하는 변경 방향과 반대이고 해당 세그먼트가 비교 가능한 세그먼트보다 현저히 나쁜 성과를 보일 때 경고합니다. 증가가 바람직한 메트릭의 경우, 세그먼트 리프트는 0 미만이어야 합니다. 감소가 바람직한 메트릭의 경우, 세그먼트 리프트는 0 초과여야 합니다.

각 메트릭, 처리 변형 및 차원에 대해 Datadog은 각 세그먼트 리프트를 동일한 조합 내 유효한 세그먼트 리프트의 역분산 가중 평균과 비교합니다. 세그먼트는 가중 평균과의 차이에 대한 순차적 신뢰 구간이 완전히 더 나쁜 방향에 있고 점 추정치가 원하는 변경 방향과 반대일 때만 경고합니다.

Datadog은 검정군 전체 유의수준(family significance level, 알파)인 `0.05`를 초기 요약 통계 검증을 통과한 세그먼트 비교 횟수로 나누어 본페로니 보정을 적용합니다. 이후 검사에서 건너뛴 비교는 분모에 남아 있어 임계값을 더 보수적으로 설정합니다. 이 검사를 위해서는 동일한 메트릭, 처리 변형 및 차원에 대해 양의 분산을 가진 최소 두 개의 세그먼트가 필요합니다. 세그먼트 수준 성능 저하는 진단 실패가 아니라 경고를 발생시킵니다.

### 해결 방법 {#how-to-resolve-8}

- 국가, 플랜, 장치 또는 고객 등급과 같이 영향을 받는 차원에 대한 세그먼트 수준 차트를 검토합니다.
- 영향을 받는 세그먼트가 실제 제품 또는 계측 문제에 해당하는지 확인합니다.
- 영향력이 큰 세그먼트를 조사하는 동안 영향을 받는 세그먼트 트래픽을 실험에서 다른 곳으로 돌리는 것을 고려하세요.

## 분석 파이프라인 실패{#analysis-pipeline-failure}

실험 분석은 Datadog의 Product Analytics 및 RUM 데이터 또는 웨어하우스 네이티브 모드를 사용할 수 있습니다. **분석 파이프라인 실패**는 웨어하우스 메트릭을 사용하는 실험에만 적용됩니다. Datadog은 고객 웨어하우스 쿼리가 실패하여 현재 웨어하우스 결과를 계산할 수 없을 때 이 진단을 보고합니다. Datadog은 내부 Product Analytics 또는 RUM 분석 실패를 이 진단으로 보고하지 않습니다.

정의하는 SQL은 실험이 무작위화되는 방식에 따라 달라집니다. Datadog Feature Flags를 기반으로 하는 실험의 경우, Datadog은 할당을 `g_exposures` 표로 동기화하며, 사용자는 메트릭 SQL 모델을 정의합니다. 웨어하우스 네이티브 실험의 경우, 노출 SQL 모델과 메트릭 SQL 모델을 모두 정의합니다. Datadog은 나머지 파이프라인 SQL을 생성합니다.

### 해결 방법 {#how-to-resolve-9}

1. 실패한 진단에서 [{{< ui >}}Ask Bits{{< /ui >}}][7]를 클릭합니다. Bits는 파이프라인 오류, 실패한 웨어하우스 쿼리, 실험에 대해 구성된 모든 SQL 모델을 검토합니다. 이를 통해 가장 가능성이 높은 원인을 식별하고 구체적인 해결 방법을 제안합니다.
2. Datadog Feature Flags를 기반으로 하는 실험의 경우, 노출이 `g_exposures`로 동기화되었는지 확인한 다음, 실패한 쿼리, 메트릭 SQL 모델, 웨어하우스 연결 및 권한, 소스 표 가용성을 검토합니다.
3. 웨어하우스 네이티브 실험의 경우, 실패한 쿼리, 노출 SQL 모델, 메트릭 SQL 모델, 웨어하우스 연결 및 권한, 소스 표 가용성을 검토합니다.
4. 수정 사항을 적용한 다음 실험 분석을 다시 실행하세요.
5. 동일한 오류가 지속되면 실험 URL 및 오류 세부 정보와 함께 [Datadog 지원팀][9]에 문의하세요.
