<div id="cdoc-content" class=""><article><h2 id="overview">Overview</h2><p>The RUM iOS SDK generates events that have associated telemetry and attributes. Telemetry is quantifiable values that can be used for measurements related to the event. Attributes are non-quantifiable values used to slice telemetry values (group by) in analytics.</p><p>Every RUM event has all of the <a href="#default-attributes">default attributes</a>, for example, the device type (<code>device.type</code>) and user information such as their name (<code>usr.name</code>) and their country (<code>geo.country</code>).</p><p>There are additional <a href="#event-specific-attributes">attributes specific to a given event type</a>. For example, the <code>view.loading_time</code> telemetry is associated with view events, and the <code>resource.method</code> attribute is associated with resource events.</p><table><thead><tr><th>Event Type</th><th>Retention</th><th>Description</th></tr></thead><tbody><tr><td>Session</td><td>30 days</td><td>A session represents a real user journey on your mobile application. It begins when the user launches the application, and the session remains live as long as the user stays active. During the user journey, all RUM events generated as part of the session share the same <code>session.id</code> attribute. <strong>Note:</strong> The session resets after 15 minutes of inactivity. If the application is killed by the OS, you can reset the session while the application is in the background.</td></tr><tr><td>View</td><td>30 days</td><td>A view represents a unique screen (or screen segment) on your mobile application. A view starts and stops when the <code>viewDidAppear(animated:)</code> and <code>viewDidDisappear(animated:)</code> callbacks on the <code>UIViewController</code> class are notified. Individual <code>UIViewControllers</code> are classified as distinct views. While a user stays on a view, RUM event attributes (Errors, Resources, Actions) get attached to the view with a unique <code>view.id</code>.</td></tr><tr><td>Resource</td><td>15 days</td><td>A resource represents network requests to first-party hosts, APIs, and third-party providers in your mobile application. All requests generated during a user session are attached to the view with a unique <code>resource.id</code>.</td></tr><tr><td>Error</td><td>30 days</td><td>An error represents an exception or crash emitted by the mobile application attached to the view it is generated in.</td></tr><tr><td>Action</td><td>30 days</td><td>An action represents user activity in your mobile application (for example, application launch, tap, swipe, or back). Each action is attached with a unique <code>action.id</code> attached to the view it gets generated in. When an action is being tracked, other actions within the next <code>100 ms</code> do not get sent, unless they are <a href="/real_user_monitoring/application_monitoring/ios/advanced_configuration/#custom-actions">custom actions</a>.</td></tr><tr><td>Long task</td><td>15 days</td><td>A long task event is generated for any task in the application that blocks the main thread for more than the specified duration threshold.</td></tr></tbody></table><p>The following diagram illustrates the RUM event hierarchy:</p><a href="http://localhost:1313/images/real_user_monitoring/data_collected/event-hierarchy.86b26bc249a457cd958cad386d03aabd.png?fit=max&amp;auto=format" class="pop" data-bs-toggle="modal" data-bs-target="#popupImageModal"><div class="shortcode-wrapper shortcode-img expand"><figure class="text-center"><picture style="width:50%"><img srcSet="http://localhost:1313/images/real_user_monitoring/data_collected/event-hierarchy.86b26bc249a457cd958cad386d03aabd.png?auto=format" class="img-fluid" style="width:50%" alt="RUM Event hierarchy"/></picture></figure></div></a><h2 id="views-instrumentation-versus-app-lifecycle">Views instrumentation versus app lifecycle</h2><p>RUM integrates with <code>UIKit</code> and <code>SwiftUI</code> views and also provides APIs for manual view tracking. The timing of when a view starts and ends depends on the type of instrumentation used:</p><p><strong>UIKit Views</strong>: When <a href="/real_user_monitoring/application_monitoring/ios/advanced_configuration/?tab=swift#automatically-track-views">automatically tracking UIKit views</a> using <code>UIKitRUMViewsPredicate</code>, RUM starts the view at the <code>viewDidAppear(animated:)</code> event of the <code>UIViewController</code> lifecycle. The view is stopped at <code>viewDidDisappear(animated:)</code>. <strong>SwiftUI Views</strong>: When <a href="/real_user_monitoring/application_monitoring/ios/setup/?tab=swiftpackagemanagerspm#instrument-views">tracking SwiftUI views</a> with the <code>.trackRUMView(name:)</code> view modifier, RUM starts the view at the <code>onAppear(perform:)</code> callback and stops it at <code>onDisappear(perform:)</code>. <strong>Manual View Tracking</strong>: When tracking views manually using <code>RUMMonitor</code> APIs, the view starts precisely when you call the <code>startView(...)</code> method and stops when you call the <code>stopView()</code> method.</p><p>When the application leaves the foreground, RUM automatically stops the current view, leaving no active view. Since RUM's data model requires an active view to track other events, by default, all events tracked in the background are skipped due to the absence of a view. To capture these events instead, see the <a href="/real_user_monitoring/application_monitoring/ios/advanced_configuration/#track-background-events">Track Background Events</a>.</p><p><strong>Note</strong>: If you're tracking views manually, you need to decide on your own whether the view should be stopped when the app leaves the foreground.</p><h2 id="default-attributes">Default attributes</h2><p>By default, RUM collects common attributes for all events and event-specific attributes listed below.
