<div id="cdoc-content" class=""><article><h2 id="overview">Overview</h2><p>The RUM Android SDK generates events that have associated attributes. These can have quantifiable values and can be used for measurements related to the event, while others are non-quantifiable values used to slice telemetry values (group by) in analytics.</p><p>Every RUM event has all of the <a href="#default-attributes">default attributes</a>, for example, the device type (<code>device.type</code>) and user information such as their name (<code>usr.name</code>) and their country (<code>geo.country</code>).</p><p>There are additional <a href="#event-specific-attributes">attributes that are specific to a given event type</a>. For example, the <code>view.time_spent</code> attribute is associated with &quot;view&quot; events and the <code>resource.method</code> one is associated with &quot;resource&quot; events.</p><table><thead><tr><th>Event Type</th><th>Retention</th><th>Description</th></tr></thead><tbody><tr><td>Session</td><td>30 days</td><td>A session represents a real user journey on your mobile application. It begins when the user launches the application, and the session remains live as long as the user stays active. During the user journey, all RUM events generated as part of the session share the same <code>session.id</code> attribute. <strong>Note:</strong> The session resets after 15 minutes of inactivity. If the application is killed by the OS, you can reset the session while the application is in the background.</td></tr><tr><td>View</td><td>30 days</td><td>A view represents a unique screen (or screen segment) on your mobile application. A view starts and stops when the <code>onActivityResumed</code> and <code>onActivityPaused</code> callbacks are called through the <code>ActivityLifecycleCallbacks</code> interface. Each occurrence is classified as a distinct view. While a user stays on a view, RUM event attributes (Errors, Resources, and Actions) get attached to the view with a unique <code>view.id</code>.</td></tr><tr><td>Resource</td><td>15 days</td><td>A resource represents network requests to first-party hosts, APIs, and third-party providers in your mobile application. All requests generated during a user session are attached to the view with a unique <code>resource.id</code>.</td></tr><tr><td>Error</td><td>30 days</td><td>An error represents an exception or crash emitted by the mobile application attached to the view it is generated in.</td></tr><tr><td>Action</td><td>30 days</td><td>An action represents user activity in your mobile application (such as an application launch, tap, swipe, or back). Each action is attached with a unique <code>action.id</code> that is also attached to the view it gets generated in. When an action is being tracked, other actions within the next <code>100 ms</code> do not get sent, unless they are <a href="/real_user_monitoring/application_monitoring/android/advanced_configuration/#custom-actions">custom actions</a>.</td></tr><tr><td>Long Task</td><td>15 days</td><td>A long task event is generated for any task in the application that blocks the main thread for more than the specified duration threshold.</td></tr></tbody></table><p>The following diagram illustrates the RUM event hierarchy:</p><a href="http://localhost:1313/images/real_user_monitoring/data_collected/event-hierarchy.86b26bc249a457cd958cad386d03aabd.png?fit=max&amp;auto=format" class="pop" data-bs-toggle="modal" data-bs-target="#popupImageModal"><div class="shortcode-wrapper shortcode-img expand"><figure class="text-center"><picture style="width:50%"><img srcSet="http://localhost:1313/images/real_user_monitoring/data_collected/event-hierarchy.86b26bc249a457cd958cad386d03aabd.png?auto=format" class="img-fluid" style="width:50%" alt="RUM Event hierarchy"/></picture></figure></div></a><h2 id="views-instrumentation-versus-app-lifecycle">Views instrumentation versus app lifecycle</h2><p>The Android RUM SDK offers various strategies to <a href="/real_user_monitoring/application_monitoring/android/advanced_configuration/?tab=kotlin#automatically-track-views">automatically track views</a> like Activities, Fragments, or Navigation destinations. You can also track views manually by directly calling the RUM APIs. The precise moment a view starts or stops depends on the chosen tracking strategy or manual instrumentation:</p><ul><li>Activities (<code>ActivityViewTrackingStrategy</code>): When you rely on this strategy, the SDK automatically starts a RUM view when the Activity enters the foreground (<code>onResume</code>) and stops it when the Activity leaves the foreground (<code>onPause</code>).</li><li>Fragments (<code>FragmentViewTrackingStrategy</code>): Each <code>Fragment</code> in your application is tracked as a separate RUM view. The SDK starts the view in the Fragment's <code>onResume</code> lifecycle method and stops it in <code>onPause</code>.</li><li>Mixed (<code>MixedViewTrackingStrategy</code>): Activities and Fragments each become distinct RUM views based on their respective lifecycle events (<code>onResume</code> and <code>onPause</code>).</li><li>Navigation (<code>NavigationViewTrackingStrategy</code>): Each navigation destination is treated as a distinct RUM view, so view boundaries align with navigation events in your graph.</li><li>Manual View Tracking: When <a href="/real_user_monitoring/application_monitoring/android/advanced_configuration/?tab=kotlin#custom-views">tracking views manually</a> using <code>GlobalRumMonitor</code> APIs, the view starts precisely when you call the <code>startView(...)</code> method and stops when you call the <code>stopView()</code> method.</li></ul><p>When the application goes into the background (for example, the user presses the home button or switches apps), RUM automatically stops the current view. Consequently, there is no active view while the app remains in the background. Since RUM's data model requires an active view to correlate and capture events, any events generated in the background are skipped by default. To capture these events instead, see the <a href="/real_user_monitoring/application_monitoring/android/setup?tab=rum#track-background-events">Track Background Events</a> section.</p><p><strong>Note</strong>: If you're tracking views manually, you need to configure whether the view should be stopped when the app leaves the foreground.</p><h2 id="default-attributes">Default attributes</h2><p>RUM collects common attributes for all events and attributes specific to each event listed below <a href="/real_user_monitoring/application_monitoring/android/advanced_configuration/#automatically-track-views">automatically</a>. <code>/proc/self/status</code>. This value measures resident memory for the entire application process. It includes native memory, the Java Virtual Machine (JVM) or Android Runtime (ART) heap, and resident shared pages.</p><p>Each view tracks the exact running mean and maximum of successful samples. Calculations reset when the view starts, so they reflect only the samples collected during that view, not a rolling average carried over from previous views.</p><p>By default, the SDK samples memory every 500 ms (<code>VitalsUpdateFrequency.AVERAGE</code>) while the view is in the foreground. Use <a href="/real_user_monitoring/application_monitoring/android/advanced_configuration/#initialization-parameters"><code>RumConfiguration.setVitalsUpdateFrequency</code></a> to change the frequency or disable collection with <code>VitalsUpdateFrequency.NEVER</code>. However, if the mobile device is rooted, or someone tampers with the Linux kernel, the stored data might become readable.</p><h2 id="data-upload">Data upload</h2><p>The RUM Android SDK allows you to get the data you need to Datadog while considering user bandwidth impact. The Datadog SDK batches and uploads events as follows:</p><ul><li>On <em>event collected</em>, the Datadog SDK appends uncompressed events to a batch file (using a tag-length-value, or TLV encoding format)</li><li>On <em>upload</em> (when the batch is considered &quot;closed&quot;), the Datadog SDK:<ul><li>Reads the batch and extracts events</li><li>Drops redundant View events in RUM (no optimizations in other tracks)</li><li>Builds payloads specific to each track</li><li>Compresses the payload and sends it</li></ul></li></ul><h2 id="direct-boot-mode-support">Direct Boot mode
