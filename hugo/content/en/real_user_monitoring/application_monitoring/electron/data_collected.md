<div id="cdoc-content" class=""><article><h2 id="overview">Overview</h2><p>The Electron SDK collects data from two sources:</p><ul><li><strong>Renderer processes</strong> are monitored by the Browser SDK. Views, actions, resources, errors, and other renderer events follow the <a href="/real_user_monitoring/application_monitoring/browser/data_collected/">Browser data collected</a> reference.</li><li><strong>The main process</strong> is monitored by the Electron SDK, which generates RUM events, and by <code>dd-trace-js</code>, which generates traces.</li></ul><p>Every event has attributes. See the <a href="#shared-attributes">Shared attributes</a> section. Quantifiable attributes can be used for measurements related to the event, while non-quantifiable attributes can be used to filter and group telemetry in analytics (group by). You can further enrich your data by <a href="/real_user_monitoring/application_monitoring/electron/advanced_configuration/#global-context">adding global context</a>.</p><h2 id="main-process-rum-events">Main process RUM events</h2><table><thead><tr><th>Event type</th><th>Retention</th><th>Description</th></tr></thead><tbody><tr><td>Session</td><td>30 days</td><td>A session represents a continuous usage period in your application. All RUM events generated during the session, from the main process and the renderer processes, share the same <code>session.id</code>.</td></tr><tr><td>Error</td><td>30 days</td><td>An error represents an exception or problem in the main process, such as an uncaught Node.js error or a native crash.</td></tr><tr><td>Resource</td><td>15 days</td><td>A resource represents a network request made by the main process.</td></tr><tr><td>Vital</td><td>15 days</td><td>A vital represents a <a href="/real_user_monitoring/application_monitoring/electron/advanced_configuration/#custom-duration-vitals">custom duration vital</a> or an <a href="/real_user_monitoring/application_monitoring/electron/advanced_configuration/#operation-monitoring">operation</a> step recorded in the main process.</td></tr></tbody></table><p>Main process events are not attached to a view.</p><h2 id="execution-context">Execution context</h2><p>An execution context is a unit of code execution, such as an operating system process of your application. Events carry the following attributes to identify the process that generated them:</p><table><thead><tr><th>Attribute name</th><th>Type</th><th>Description</th></tr></thead><tbody><tr><td><code>execution_context.id</code></td><td>string</td><td>Unique identifier (UUID) of the execution context.</td></tr><tr><td><code>execution_context.type</code></td><td>string</td><td>Type of the execution context: <code>main-process</code> or <code>renderer-process</code>.</td></tr><tr><td><code>execution_context.name</code></td><td>string</td><td>Name of the execution context. See the following table.</td></tr></tbody></table><p>The name of the main process is <code>Main Process</code>. The name of a renderer process is derived from the URL of its window, after the page is loaded:</p><table><thead><tr><th>Window URL</th><th>Name</th></tr></thead><tbody><tr><td>External host (for example, <code>https://example.com</code>)</td><td>Origin and path. Query, fragment, and credentials are dropped.</td></tr><tr><td><code>localhost</code> or a custom protocol such as <code>app://</code></td><td>Path, query, and hash.</td></tr><tr><td><code>file://</code></td><td>Filename, followed by any query and hash.</td></tr></tbody></table><p>Names are truncated to 200 characters. You can modify <code>execution_context.name</code> in <a href="/real_user_monitoring/application_monitoring/electron/advanced_configuration/#modify-or-drop-rum-events"><code>beforeSendRum</code></a>.</p><p>To filter events by process in the RUM Explorer, use the <code>execution_context.type</code> facet. For example, <code>@execution_context.type:main-process</code> shows only events generated by the main process.</p><h2 id="main-process-traces">Main process traces</h2><p>The Electron SDK uses and configures <code>dd-trace-js</code>, so tracing requires no additional setup. The SDK generates traces for the following main process activity:</p><ul><li>Network requests</li><li>Command execution</li></ul><p>To control how many traces are kept, see <a href="/real_user_monitoring/application_monitoring/electron/advanced_configuration/#trace-sampling-rules">Trace sampling rules</a>.</p><h2 id="shared-attributes">Shared attributes</h2><p>The following attributes are attached to events from the main process and the renderer processes.</p><h3 id="common-core-attributes">Common core attributes</h3><table><thead><tr><th>Attribute name</th><th>Type</th><th>Description</th></tr></thead><tbody><tr><td><code>application.id</code></td><td>string</td><td>The RUM application ID.</td></tr><tr><td><code>date</code></td><td>integer</td><td>Start of the event in milliseconds from epoch.</td></tr><tr><td><code>service</code></td><td>string</td><td>The <a href="/getting_started/tagging/unified_service_tagging/">unified service name</a> for this application. Main process events report the <code>service</code> set in the Electron SDK <code>init</code>. Renderer events report the <code>service</code> set in the Browser SDK <code>init</code>.</td></tr><tr><td><code>env</code></td><td>string</td><td>The environment tag (for example, <code>production</code> or <code>staging</code>), set with the <code>env</code> initialization parameter.</td></tr><tr><td><code>version</code></td><td>string</td><td>The application version. Main process events report the <code>version</code> set in the Electron SDK <code>init</code>. Renderer events report the <code>version</code> set in the Browser SDK <code>init</code>.</td></tr><tr><td><code>type</code></td><td>string</td><td>The type of the event (for example, <code>session</code>, <code>error</code>, or <code>resource</code>).</td></tr></tbody></table><p>For the initialization parameters, see <a href="/real_user_monitoring/application_monitoring/electron/advanced_configuration/#initialization-parameters">Initialization parameters</a>. To choose <code>service</code> and <code>version</code> values that match your uploaded source maps, see <a href="/real_user_monitoring/application_monitoring/electron/error_tracking/#prepare-your-source-maps">Prepare your source maps</a>.</p><h3 id="operating-system">Operating system</h3><p>Datadog derives the following attributes from the user agent that the SDK sends with its uploads. The SDK builds this user agent from the operating system, its version, and the CPU architecture.</p><table><thead><tr><th>Attribute name</th><th>Type</th><th>Description</th></tr></thead><tbody><tr><td><code>os.name</code></td><td>string</td><td>The OS name, as reported in the user agent.</td></tr><tr><td><code>os.version</code></td><td>string</td><td>The OS version, as reported in the user agent. Linux user agents do not include the OS version.</td></tr><tr><td><code>os.version_major</code></td><td>string</td><td>The OS major version, as reported in the user agent.</td></tr></tbody></table><h3 id="device">Device</h3><p>Datadog derives the following attribute from the same user agent.</p><table><thead><tr><th>Attribute name</th><th>Type</th><th>Description</th></tr></thead><tbody><tr><td><code>device.type</code></td><td>string</td><td>The device type, as reported in the user agent.</td></tr></tbody></table><h3 id="geolocation">Geolocation</h3><p>Datadog resolves geolocation attributes (<code>geo.country</code>, <code>geo.city</code>, and others) from the client IP address. To stop collecting them, change the setting in your <a href="/data_security/real_user_monitoring/#geolocation">application details</a>.</p><h3 id="user-and-account-attributes">User and account attributes</h3><p>Events from the main process and the renderer processes include the user (<code>usr.id</code>, <code>usr.name</code>, <code>usr.email</code>) and account (<code>acc.id</code>, <code>acc.name</code>) information you set. See <a href="/real_user_monitoring/application_monitoring/electron/advanced_configuration/#user-and-account-information">User and account information</a>.</p><h3 id="global-context">Global context</h3><p>Attributes set with the global context are sent in the <code>context</code> field of events. Renderer processes keep their own global context, set with the Browser SDK. Both are merged on renderer events, and the renderer value wins when a key is in both. See <a href="/real_user_monitoring/application_monitoring/electron/advanced_configuration/#global-context">Global context</a>.</p><h2 id="data-storage">Data storage</h2><p>The SDK stores events on disk before uploading them to Datadog. Events are preserved across application restarts, so data collected before an unexpected shutdown is sent on the next launch.</p><p>The <a href="/real_user_monitoring/application_monitoring/electron/advanced_configuration/#tracking-consent">tracking consent</a> decides what the SDK keeps and sends. While consent is <code>'pending'</code>, the SDK keeps data on disk until the end user decides. It deletes data kept while consent is pending if no decision is made before the next launch. When consent is <code>'not-granted'</code>, the SDK does not store new data.</p><h2 id="further-reading">Further reading</h2><div class="whatsnext"><p>Additional helpful documentation, links, and
