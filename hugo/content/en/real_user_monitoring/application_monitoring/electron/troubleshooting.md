<div id="cdoc-content" class=""><article><h2 id="overview">Overview</h2><p>If you experience unexpected behavior with the Datadog Electron SDK, use this guide to resolve issues. If you continue to have trouble, contact <a href="/help">Datadog Support</a> for further assistance.</p><h2 id="runtime-issues">Runtime issues</h2><h3 id="browser-windows-opened-before-">Browser windows opened before <code>init</code> completes are not tracked</h3><p>Windows opened before <code>init</code> completes are not tracked until you reload them. They send nothing, not even the interactions that keep the session alive. If end users interact only with such windows, the session expires after 15 minutes of inactivity and no new session starts.</p><p>To fix this, wait for <code>init</code> to complete before you create any browser window, as described in <a href="/real_user_monitoring/application_monitoring/electron/setup/#initialize-the-sdk-in-the-main-process">Initialize the SDK in the main process</a>. If a window must open earlier, reload it after <code>init</code> completes. To wait for the end user's consent, call <code>init</code> at startup with <code>trackingConsent: 'pending'</code> instead of deferring it. See <a href="/real_user_monitoring/application_monitoring/electron/advanced_configuration/#tracking-consent">Tracking consent</a>.</p><h3><code>init</code> returns <code>false</code></h3><p><code>init</code> returns <code>false</code> if the configuration is invalid.</p><p>To fix this, check the configuration passed to <code>init</code>. Call <code>init</code> once per launch. To change the tracking consent later, call <code>setTrackingConsent</code> instead of calling <code>init</code> again. See <a href="/real_user_monitoring/application_monitoring/electron/advanced_configuration/#tracking-consent">Tracking consent</a>.</p><h3 id="renderer-events-are-missing">Renderer events are missing</h3><p>The main process accepts events only from renderers whose host is listed in <code>allowedRendererHosts</code>. Renderers whose host is not listed do not report through the main process. Their Browser SDK runs on its own, so their events are not part of the application's sessions.</p><p>To fix this, add the host of your renderer pages to <code>allowedRendererHosts</code>. For custom protocols, use the hostname component of the URL. For example, use <code>myapp</code> for <code>app://myapp/index.html</code>. See <a href="/real_user_monitoring/application_monitoring/electron/advanced_configuration/#allowed-renderer-hosts">Allowed renderer hosts</a> for the supported patterns.</p><p>Also verify that the <a href="/real_user_monitoring/application_monitoring/browser/setup/">Browser SDK is set up</a> in the pages loaded by the renderer.</p><h3 id="no-profiles-are-collected">No profiles are collected</h3><p>Renderer profiling relies on the JS Self-Profiling API, which requires the page to be served with the <code>Document-Policy: js-profiling</code> HTTP response header. Pages loaded from <code>file://</code> are not served with this header by default, so profiling is not available for them.</p><p>To fix this, serve the renderer over a protocol where you control the response headers: a custom protocol that you handle with <code>protocol.handle</code>, or a local HTTP server. If you use a custom protocol, register it as privileged with the <code>standard</code> and <code>secure</code> privileges before the app is ready. See <a href="/real_user_monitoring/correlate_with_other_telemetry/profiling/?platform=electron">Correlate RUM and Profiling</a> for the full setup.</p><h3 id="a-custom-duration-vital-never-stops">A custom duration vital never stops</h3><p>The SDK records a duration vital only when <code>startDurationVital</code> and <code>stopDurationVital</code> run in the same process. A vital started in the main process cannot be stopped in a renderer process, and vice versa.</p><p>To fix this, start and stop the vital in the same process. In renderer processes, use the equivalent <code>@datadog/browser-rum</code> APIs directly. See <a href="/real_user_monitoring/application_monitoring/electron/advanced_configuration/#custom-duration-vitals">Custom duration vitals</a>.</p><h3 id="some-events-are-not-dropped-by-">Some events are not dropped by <code>beforeSendRum</code></h3><p>Only returning <code>false</code> from <code>beforeSendRum</code> drops an event. Any other return value keeps the event. View, execution context, and native crash events cannot be dropped.</p><p>To fix this, return <code>false</code> for events that can be dropped, and modify the editable fields of the other events instead. See <a href="/real_user_monitoring/application_monitoring/electron/advanced_configuration/#modify-or-drop-rum-events">Modify or drop RUM events</a>.</p><h2 id="further-reading">Further
