## Overview

Error Tracking processes errors collected from the .NET MAUI SDK.

Enable .NET MAUI Crash Reporting and Error Tracking to get comprehensive crash reports, symbolicated C# and native iOS stack traces, deobfuscated Android stack traces, and error trends across iOS and Android. Your crash reports appear in [{{< ui >}}Error Tracking{{< /ui >}}][1].

### C# error tracking

C# error tracking is enabled automatically as soon as RUM is enabled — no extra configuration is required. The SDK captures:

- Unhandled C# exceptions (`AppDomain.UnhandledException`)
- Unobserved task exceptions (`TaskScheduler.UnobservedTaskException`)

You can also manually report an error with `DdRum.AddError`.

### Native crash reporting (optional)

`NativeCrashReportEnabled` is **only** needed if you also want to capture crashes that originate from native iOS or Android code — for example, an Objective-C/Swift crash on iOS, or a JNI/Kotlin crash on Android. C# error tracking works without it.

To enable native crash reporting, set `NativeCrashReportEnabled = true` on the SDK configuration:

```csharp
.UseDatadog(new DdSdkConfiguration
{
    ClientToken = "<CLIENT_TOKEN>",
    Environment = "<ENV_NAME>",
    TrackingConsent = TrackingConsent.Granted,
    NativeCrashReportEnabled = true,
})
```

<div class="alert alert-info">
When <code>NativeCrashReportEnabled = true</code>, an unhandled C# exception that crashes the application is reported <strong>twice</strong>. One report is a C# error captured by <code>AppDomain.UnhandledException</code>. The other is a native iOS or Android crash captured by the platform's crash reporter. Both events share the same RUM session and view, so you can correlate them in the Explorer.<br><br>To keep only one of the two, use <a href="/real_user_monitoring/application_monitoring/maui/advanced_configuration/#modify-or-drop-rum-events"><code>ErrorEventMapper</code></a> to drop the copy that doesn't fit your workflow. For example, filter by <code>Source</code> or <code>Stacktrace</code> content.
</div>

## Get symbolicated stack traces

To resolve C# file names and line numbers, native iOS crash addresses, and obfuscated Android class and method names, upload your app's symbol files to Datadog. Symbolication then happens server-side on each error event.

| Platform | Symbol file | What it covers | Generated by |
|---|---|---|---|
| iOS | `.dSYM` bundle | Native crashes and AOT-compiled C# method names | `dotnet publish -r ios-arm64` |
| Android | `mapping.txt` | R8/ProGuard obfuscated Java/Kotlin class and method names | `dotnet publish` with R8 enabled (see [Enable R8 on Android](#enable-r8-on-android)) |
| iOS and Android | Portable PDB (`.pdb`) | File names and line numbers for managed C# stack traces | `dotnet publish` with portable debug symbols enabled |

### How C# symbolication works

.NET MAUI Release builds compile C# ahead of time, so the runtime on the device cannot map a stack frame back to a source file and line. Instead, the SDK resolves C# frames server-side using your app's Portable PDB files:

1. At build time, the `Datadog.Maui` package generates a debug ID manifest (`dd_debug_ids.json`) that records the debug ID of each assembly your app ships, and packages it into the app.
2. At runtime, when the SDK reports a C# error, it attaches the assembly debug ID and IL offset of each managed stack frame.
3. At publish time, the SDK uploads the Portable PDB that matches each shipped assembly. On iOS device builds, the linker rewrites the app's assembly, so the SDK uploads the PDB produced by the linker instead of the pre-link copy in the build output directory.
4. Datadog matches each frame to its Portable PDB by debug ID and resolves the file name and line number.

On iOS, line numbers depend on the IL offsets that the Mono AOT runtime reports. See [C# line numbers on iOS](#c-line-numbers-on-ios).

Portable PDB files do not need to be bundled inside the app. On iOS, when symbol upload is enabled, the SDK removes any Portable PDB from the published app bundle by default (see `DatadogKeepPortablePdbs` in [Configuration](#configuration)).

### Upload symbols with `datadog-ci`

The `Datadog.Maui` NuGet package ships MSBuild targets that upload symbols to Datadog automatically as part of `dotnet publish`. To enable it:

#### 1. Install `datadog-ci`

```bash
npm install -g @datadog/datadog-ci
```

Verify the installation with `datadog-ci version`. Portable PDB upload requires `datadog-ci` v5.25.0 or later. Earlier versions do not include the `ppdb-symbols upload` command.

#### 2. Set your Datadog API key

Export the key in the shell that runs `dotnet publish`:

```bash
export DATADOG_API_KEY=<YOUR_DATADOG_API_KEY>
```

For CI environments, set `DATADOG_API_KEY` as a protected/secret environment variable on your runner. Do not commit the key to source control.

For local testing, you can pass the key as an MSBuild property (`-p:DatadogApiKey=...`), but **do not set `DatadogApiKey` in your `.csproj`**. That file is checked in to source control.

#### 3. Enable the upload

Set `DatadogUploadSymbols=true` either as a `<PropertyGroup>` entry in your `.csproj` or on the `dotnet publish` command line. The MSBuild targets run automatically after publish. If `datadog-ci` is missing or the API key is unset, the upload is skipped with a message and the build continues.

{{< tabs >}}
{{% tab "iOS" %}}

```bash
dotnet publish -c Release -f net10.0-ios -r ios-arm64 \
  -p:DatadogUploadSymbols=true
```

The `.dSYM` bundle generated next to the `.app` and the Portable PDBs of your app's assemblies are uploaded. dSYMs are only produced for device builds (`-r ios-arm64`). Simulator builds (`iossimulator-arm64`) skip the dSYM upload.

{{% /tab %}}
{{% tab "Android" %}}

```bash
dotnet publish -c Release -f net10.0-android \
  -p:DatadogUploadSymbols=true
```

The R8 `mapping.txt` file and the Portable PDBs of your app's assemblies are uploaded. The mapping file is only generated when R8 is enabled (see [Enable R8 on Android](#enable-r8-on-android)).

{{% /tab %}}
{{< /tabs >}}

Portable PDBs are uploaded for your app's own assemblies and project references, meaning every assembly whose `.pdb` file is written to the build output directory. To include PDBs shipped inside NuGet packages, copy them to the build output directory (for example, with `<CopyDebugSymbolFilesFromPackages>true</CopyDebugSymbolFilesFromPackages>`).

Portable PDB upload requires portable debug symbols, which is the .NET default. If your project overrides it, set `<DebugType>portable</DebugType>` for the configuration you publish.

### Enable R8 on Android

By default, .NET MAUI Android Release builds do not run R8, so no `mapping.txt` file is generated. To enable it, add the following to your `.csproj`:

```xml
<PropertyGroup Condition="'$(Configuration)' == 'Release'">
  <AndroidLinkTool>r8</AndroidLinkTool>
  <AndroidCreateProguardMappingFile>true</AndroidCreateProguardMappingFile>
</PropertyGroup>
```

The mapping file is generated at `bin/Release/net10.0-android/mapping.txt`.

The mapping file is uploaded with the `DatadogServiceName` property and your app's `ApplicationDisplayVersion`. For Datadog to match it with your crash reports, both values must match the service and version that the SDK reports at runtime.

### Configuration

All configuration is done through MSBuild properties, either in your `.csproj` `<PropertyGroup>` or on the `dotnet publish` command line with `-p:`.

| Property | Required | Default | Description |
|---|---|---|---|
| `DatadogUploadSymbols` | Yes | `false` | Set to `true` to enable symbol upload after publish. |
| `DatadogServiceName` | No | `$(AssemblyName)` | Service name used to identify your app in Datadog. Must match the `Service` you pass to `DdSdkConfiguration` at runtime. |
| `DatadogSite` | No | — | The Datadog site that receives the upload (for example, `datadoghq.eu`, `us5.datadoghq.com`). Must match the `Site` value set on `DdSdkConfiguration`. If unset, `datadog-ci` reads the `DATADOG_SITE` or `DD_SITE` environment variable, and defaults to `datadoghq.com`. Setting this property overrides both environment variables. |
| `DatadogApiKey` | No | — | API key passed directly. If unset, the `DATADOG_API_KEY` environment variable is used instead. |
| `DatadogFailOnSymbolUploadError` | No | `false` | Set to `true` to fail the build when a symbol upload fails. By default, failures are reported as MSBuild warnings. |
| `DatadogKeepPortablePdbs` | No | `false` | iOS only. Applies only when `DatadogUploadSymbols=true`. Some debug configurations (for example, `soft-debug`) bundle the Portable PDB inside the `.app`. Because C# symbolication uses the uploaded PDB, the SDK removes it from the bundle by default. Set to `true` to keep it in the bundle. |

```xml
<PropertyGroup>
  <DatadogServiceName>my-maui-app</DatadogServiceName>
  <DatadogSite>datadoghq.eu</DatadogSite>
</PropertyGroup>
```

The terminal logger that `dotnet publish` uses by default hides informational output. To see the Datadog upload messages, add `-v n -tl:off`:

```bash
dotnet publish -c Release -f net10.0-ios -r ios-arm64 \
  -p:DatadogUploadSymbols=true -v n -tl:off
```

After publish, a summary shows the outcome of each upload (`uploaded`, `FAILED`, `skipped`, or `not run`).

### Upload failures

By default, a failed upload produces an MSBuild warning and the build still succeeds, so a symbol upload problem does not block shipping your app. To turn upload failures into build errors, which is recommended in CI, pass `-p:DatadogFailOnSymbolUploadError=true`.

After upload, symbols take up to 5 minutes to process. You can confirm they were received under [{{< ui >}}Error Tracking{{< /ui >}} > {{< ui >}}Settings{{< /ui >}} > {{< ui >}}Symbol Files{{< /ui >}}][4].

## Limitations

### C# assemblies without Portable PDBs

C# frames resolve to file names and line numbers only for assemblies whose Portable PDB was uploaded. Frames from .NET framework assemblies, and from third-party assemblies whose PDB is not in the build output directory, resolve to method names only.

### C# line numbers on iOS

To resolve a C# frame to a line number, Datadog needs the frame's IL offset. On iOS, the Mono AOT runtime reports accurate IL offsets when the app is AOT-compiled with debug information (soft-debug), which is the default for the `Debug` configuration. In builds compiled without debug information, frames can be reported without an accurate IL offset. Those frames resolve to method names only.

Soft-debug builds also bundle the Portable PDB inside the `.app`. When symbol upload is enabled, the SDK removes it from the bundle by default, because symbolication uses the uploaded PDB. To keep it, set `DatadogKeepPortablePdbs=true`.

### File sizing

dSYM bundles (iOS) can go up to **2 GB** each.

### Collection

The SDK handles crash reporting with the following behaviors:

- Crashes can only be detected after the SDK is initialized. Initialize the SDK as early as possible in `MauiProgram.CreateMauiApp`.
- RUM crashes must be attached to a RUM view. If a crash occurs before a view is visible (or after the app has been moved to the background by the user), the crash is muted and isn't reported. To mitigate this, set `TrackBackgroundEvents = true` on `DdRumConfiguration`.
- Only crashes that occur in sampled sessions are kept.

### Android NDK crash symbols

When `NativeCrashReportEnabled = true`, native (C/C++) crashes captured by `dd-sdk-android-ndk` require unstripped `.so` files for symbolication.

In a MAUI app, the native `.so` files typically come from the .NET runtime (`libmonosgen-2.0.so`, `libmonodroid.so`) and from Datadog's own NDK library — Datadog resolves these server-side; no manual upload is needed for either. If you ship custom native C/C++ libraries, upload their symbols manually with `datadog-ci dsyms upload <path-to-so-directory>`.

## Test your implementation

To verify your Crash Reporting and Error Tracking configuration, trigger a crash and confirm that the error appears in Datadog:

1. Publish your application with `DatadogUploadSymbols=true` and run it on a real device or emulator (dSYMs are generated only for device builds on iOS).
2. Execute code that throws an unhandled exception. For example:

   ```csharp
   void OnButtonClicked(object sender, EventArgs e)
   {
       throw new InvalidOperationException("Crash the app");
   }
   ```

3. After the crash, restart your application and wait for the SDK to upload the crash report.
4. Confirm the event in [{{< ui >}}Error Tracking{{< /ui >}}][1]. C# frames from your app's assemblies show file names and line numbers, native iOS frames from a device build are symbolicated, and obfuscated Android frames are deobfuscated.

## Troubleshooting

**`Skipping symbol upload — datadog-ci is not installed`**
Run `npm install -g @datadog/datadog-ci` and verify with `datadog-ci version`.

**`Skipping symbol upload — DATADOG_API_KEY is not set`**
Export the key in your shell: `export DATADOG_API_KEY=<YOUR_DATADOG_API_KEY>`. Verify with `echo $DATADOG_API_KEY`.

**`Skipping dSYM upload — file not found`**
dSYMs are only generated for device builds (`-r ios-arm64`). Simulator builds do not produce dSYMs.

**`Skipping mapping upload — mapping.txt not found`**
R8 is not enabled for the build. Add `<AndroidLinkTool>r8</AndroidLinkTool>` and `<AndroidCreateProguardMappingFile>true</AndroidCreateProguardMappingFile>` to your `.csproj`. See [Enable R8 on Android](#enable-r8-on-android).

**`Skipping Portable PDB upload — no debug-id manifest found`**
The debug ID manifest (`dd_debug_ids.json`) is generated during the build that `dotnet publish` runs. Confirm that the build succeeded and that debug symbols are enabled with `<DebugType>portable</DebugType>`.

**`Skipping Portable PDB upload — no Portable PDB found`**
No `.pdb` file was written to the build output directory. Confirm that debug symbols are enabled for the configuration you publish, with `<DebugType>portable</DebugType>`.

**Warning: no Portable PDB matching the shipped assembly was found**
For one or more assemblies, none of the PDB files found matches the assembly the app ships, so C# frames from those assemblies are not resolved to file names and line numbers. The publish output lists each affected assembly in a `not uploading a Portable PDB for <assembly>` line. This can happen when the PDB files are left over from an earlier build. Delete the `bin/` and `obj/` directories and publish again.

**C# frames show method names but no file names or line numbers**
Confirm that the publish summary reports the Portable PDB upload as `uploaded`, and that the frames belong to one of your app's assemblies. See [C# assemblies without Portable PDBs](#c-assemblies-without-portable-pdbs).

**No Datadog output visible during publish**
The terminal logger hides informational messages. Add `-v n -tl:off` to your `dotnet publish` command.

**Upload completes but symbols don't appear in Datadog**
Symbols take up to 5 minutes to process. Check [{{< ui >}}Error Tracking{{< /ui >}} > {{< ui >}}Settings{{< /ui >}} > {{< ui >}}Symbol Files{{< /ui >}}][4].
