## 概要 {#overview}

Feature Flags の使用量は、フラグのデプロイ方法に応じてスケールします。

- クライアントサイド**で使用する場合、使用量は Datadog に接続するクライアントアプリケーションとエンドユーザーの数に依存します。**
- サーバーサイド**で使用する場合、使用量は構成をポーリングするバックエンドサービスの数に依存します。**

フラグの数が同じ 2 つの組織であっても、このデプロイのフットプリントにより使用量が異なる場合があります。このガイドは、広範囲に展開する前に使用量とコストを推定する際に役立ちます。また、デプロイ後にコストを管理および削減するために利用可能な手段についても説明します。

## Feature Flags の使用量とコストを推定する {#estimate-your-feature-flags-usage-and-costs}

Datadog は、Feature Flags の使用量を Monthly Flag Configuration Requests (MFCR) で請求します。MFCR とは、個々のフラグ評価のリクエストではなく、フラグとそのターゲティングルールを含むファイルに対するリクエストのことです。SDK はそのファイルをローカルにキャッシュし、ネットワークで呼び出しを行うことなく、キャッシュされたファイルでフラグを評価します。したがって、1 つの構成リクエストで多数のフラグを評価できます。完全な定義とカウントルールについては、[月間フラグ構成リクエスト][1] を参照してください。

MFCR は構成リクエストをカウントするため、維持しているフラグの数や評価の頻度は使用量に直接影響を与えません。影響を与える要因は次のとおりです。

- **クライアントサイドでの使用**: クライアントサイド SDK は初期化時に構成をリクエストします。したがって通常は、ユーザーがブラウザのタブやモバイルアプリを開くたびに、構成がリクエストされます。クライアントサイドの MFCR は、フラグを使用するアプリケーション全体でのセッションまたはアプリ起動の (サンプリングなしの) 合計数を厳密に追跡します。
- **サーバーサイドでの使用**: サーバーサイド SDK は、構成能な間隔 (デフォルトは 30 秒) で Datadog (または選択した [構成ソース][2] に応じた Datadog Agent) をポーリングします。サーバーサイドの MFCR は、SDK がデプロイされている実行中のホスト、サービス、またはコンテナの総数に、それぞれのポーリング頻度を掛けた値を追跡します。
- **クライアントサイドとサーバーサイドの組み合わせ**: クライアントとサーバーの両方でフラグを使用する場合は、2 つの推定値を合計します。

<div class="alert alert-info">Datadog は、サーバーサイドの構成リクエストをそのカウントの 10 倍で請求します。これは、単一のサーバーサイドリクエストでは、単一のクライアントサイドリクエストよりもはるかに多くのエンドユーザーにバリアントを割り当てる場合があるためです。</div>

### 展開前に使用量を推定する {#estimate-your-usage-before-you-roll-out}

1. クライアントサイド SDK またはサーバーサイド SDK のどちらをデプロイするか、あるいは両方ともデプロイするかを決定します。
1. クライアントサイドの使用量については、以下のいずれかを使用して推定します。
   - RUM セッションの月間ボリューム。または、フラグを使用する予定のアプリケーション全体の 1 日あたりのアクティブユーザー数に 30 を掛けて、月間推定値を算出します。
   - フラグが現在の RUM 実装よりも広範なアプリケーションをカバーしている場合は、代わりにそれらのアプリケーション全体の 1 日あたりのアクティブユーザー数または 1 日あたりのセッション数を使用します。
1. サーバーサイドの使用量については、SDK がデプロイされている実行中のホスト、サービス、またはコンテナの総数をカウントします。そのカウントにポーリング間隔ごとの 1 日あたりの構成リクエスト数を掛け、さらに 30 を掛けて月間推定値を算出し、サーバーサイドの 10 倍の乗数を適用します。
1. クライアントサイドとサーバーサイドの推定値を合計して、月間 MFCR 推定値を算出します。

たとえば、フラグ付きクライアントアプリケーションで 1 日あたり 120 万人のアクティブユーザーがいる組織では、1 か月あたり約 3,600 万件の MFCR が発生します (120 万人 x 30 日)。

サーバーサイドの例としては、33 台のホストで SDK を実行している組織では、デフォルトの 30 秒のポーリング間隔で 1 ホストあたり 1 日 2,880 件の構成リクエストが発生します (1 日 86,400 秒 / 30 秒)。つまり、33 x 2,880 x 30 日 = 2,851,200 (約 285 万) MFCR となり、サーバーサイドの乗数を適用する前で約 285 万の MFCR、適用後で約 2,850 万の MFCR となります。

1 か月あたり 100 万までの MFCR の利用は無料です。その割り当てを超える現在の料金プランについては、[Feature Flags の料金ページ][4] を参照してください。

### 実際の使用量とコストを監視する {#monitor-your-actual-usage-and-cost}

デプロイ後、推定使用量と実際の使用量を比較します。Datadog は、Feature Flags の使用量とコストを他の製品とともに [[Usage Details] (使用量の詳細)][5] ページと [[Bill Overview] (請求の詳細)][6] ページに報告します。これらのページでは、経時的な使用量の傾向を確認したり、詳細な使用量データをダウンロードしたりできます。

## Feature Flags のコストを管理して削減する {#manage-and-reduce-feature-flags-costs}

MFCR はフラグの数ではなく構成リクエストを追跡するため、維持するフラグの数を減らしても、それだけでコストが削減されるわけではありません。次の手段は、MFCR の真の要因である SDK を初期化するクライアントセッション数、構成をポーリングするサーバーインスタンス数、およびその頻度を対象としています。

### 環境の無秩序な増加とサーバー SDK のフットプリントを確認する {#review-environment-sprawl-and-server-sdk-footprint}

サーバーサイドの MFCR は、SDK のインスタンスを実行している環境ごとに乗算されます。ライブのサーバーサイドフラグ配信が真に必要となる [環境][3] を見直してください。ブランチごと、または CI 環境などの一時的または短時間有効なインフラストラクチャーは、ターゲティングが不要であれば、展開の価値を付加することなくリクエスト量のみを増加させます。複数の `env` 値が同じ論理環境にマッピングされている場合は環境クエリを統合し、構成の配信が不必要に重複しないようにしてください。

### 使用していない Feature Flags を無効にする {#turn-off-feature-flags-where-they-arent-in-use}

サーバー SDK をインストールしただけでは課金は発生しません。構成リクエストは、プロバイダーが初期化された後にのみ発生します。サービスにトレーサーがインストールされていてもフラグを使用しない場合は、`DD_FEATURE_FLAGS_ENABLED=false` を設定してプロバイダーを無効にし、構成のポーリングを停止してください。詳細については、[サーバー SDK 構成ソース][2] を参照してください。

### 構成のポーリング間隔を調整する {#adjust-the-configuration-polling-interval}

エージェントレスのサーバーサイド配信の場合、`DD_FEATURE_FLAGS_CONFIGURATION_SOURCE_AGENTLESS_POLL_INTERVAL_SECONDS` によって SDK が構成をリクエストする頻度が制御されます。デフォルトは 30 秒で、最大のリクエスト間隔は 3,600 秒 (1 時間) です。間隔を長くするとリクエスト数は減りますが、フラグの伝播が遅くなるという代償が伴います。開発環境やステージング環境など、優先度の低い環境で間隔を長くすることは、本番環境ほど高速な伝播を必要としない場合にリクエスト数を減らす一つの方法です。

### デプロイに合致する構成ソースを選択する {#choose-a-configuration-source-that-matches-your-deployment}

Agent Remote Configuration を使用すると、アプリケーションは Datadog を直接ポーリングする代わりに、ローカルの Datadog Agent と通信します。同じホスト上で複数のアプリケーションプロセスを実行している場合、それらを共有 Agent 経由でルーティングすることで、各プロセスがエージェントレス配信で個別に Datadog をポーリングする場合と比較して、構成リクエストを集約できます。これを、Remote Configuration が有効な Agent の実行および維持にかかる運用コストと比較してください。2 つのうちのどちらを選択するかについては、[サーバー SDK 構成ソース][2] を参照してください。

### クライアントサイドの SDK の初期化のスコープを、フラグを使用する場所に設定する {#scope-client-side-sdk-initialization-to-where-you-use-flags}

クライアントサイドの MFCR は、フラグプロバイダーを初期化するアプリケーション内のセッションまたはアプリの起動を追跡します。すべてのクライアントプロパティで一律に初期化するのではなく、フラグで機能を制御するアプリケーションやプロパティでのみプロバイダーを初期化してください。

### 古くなったフラグや未使用のフラグをクリーンアップする {#clean-up-stale-and-unused-flags}

構成リクエストはフラグの数に関係なくすべてのフラグを対象とするため、[古くなったフラグ][7] は MFCR に直接追加されるわけではありません。それらをアーカイブすることで、フラグの負債を減らし、不要になったサービスや環境に関連付けられたロジックを維持するリスクを軽減できます。古くなったフラグを確認することは、使用されなくなった環境や SDK デプロイメント全体を廃止するための有用なシグナルでもあり、これによりサーバー側のリクエスト数を削減できます。
