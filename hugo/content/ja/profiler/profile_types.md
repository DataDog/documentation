{{< ui >}}Profiles{{< /ui >}} タブでは、特定の言語で使用可能なすべてのプロファイルタイプを確認できます。言語やバージョンによって、収集されるプロファイル情報は異なります。

{{< programming-lang lang="java" >}}

プロファイリングを有効にすると、[サポートされている Java バージョン][1]について、以下のプロファイルタイプが収集されます。


CPU
: 各メソッドが CPU 上で実行に費やした時間。これには JVM 内で実行されるコード (Java、Kotlin など) が含まれますが、JVM 操作や JVM 内から呼び出されるネイティブコードは含まれません。

Allocations
: 各メソッドによって行われたヒープ割り当ての数 (その後に解放された割り当てを含む)。<br />
_要件: Java 11_

Allocated Memory
: 各メソッドによって割り当てられたヒープメモリの量 (その後に解放された割り当てを含む)。<br />
_要件: Java 11_

Live Heap (v1.61.0 以降)
: 各メソッドによって割り当てられ、まだガベージコレクションされていないオブジェクトとメモリ。これは、サービス全体のメモリ使用量を調査し、潜在的なメモリリークを特定するのに役立ちます。プロファイラーは、お使いの JVM バージョンで利用可能な最も正確なエンジンを自動的に使用します。<br />
_Java 11+ が必要です: _

Wall Time
: 各メソッドの経過時間。経過時間には、コードが CPU で実行されている時間、I/O を待機している時間、およびメソッドの実行中に発生するその他すべての時間が含まれます。

Class Load
: 各メソッドによってロードされたクラスの数。

Thrown Exceptions
: 各メソッドによってスローされたエラーおよび例外の数と、その型。

File I/O
: 各メソッドがファイルの読み取りと書き込みに費やした時間。

Lock
: 各メソッドがロックを待機した時間。

Socket I/O
: 各メソッドがソケット I/O の読み取りと書き込みに費やした時間。

_Python 2.7+ が必要です: _

_Python 2.7+ が必要です: _

: 各関数がロックを取得した回数。<br />
_Python 2.7+ が必要です: _

_要件: Python 2.7+_

_要件: Python 2.7+、POSIX プラットフォーム_

_要件: Python 3.5+_

Allocated Memory
: 各関数によって割り当てられたヒープメモリの量 (その後に解放された割り当てを含む)。<br />
_要件: Python 3.5+_

Allocations
: 各関数によって行われたヒープ割り当ての数 (その後に解放された割り当てを含む)。<br />
_要件: Python 3.5+_

{{< programming-lang lang="go" >}}

プロファイリングを有効にすると、サポートされている [Go バージョン][3]について、以下のプロファイルタイプが収集されます。


CPU Time
: 各関数が CPU で実行されていた時間。ネットワーク、チャネル、ミューテックス、スリープなどの待機によるオフ CPU 時間は、このプロファイルには記録されません。Mutex および Block プロファイルを参照してください。

Allocations
: プロファイリング期間 (デフォルト: 60 秒) 中に各関数によってヒープメモリに割り当てられたオブジェクトの数 (その後に解放された割り当てを含む)。Go ではこれを `alloc_objects` と呼びます。スタック割り当ては追跡されません。これはガベージコレクションの負荷を調査するのに役立ちます。この測定値がバージョン `1.33.0` でどのように変化するかについての注記も、[Delta プロファイル](#delta-profiles)で参照してください。

Allocated Memory
: プロファイリング期間 (デフォルト: 60 秒) 中に各関数によって割り当てられたヒープメモリの量 (その後に解放された割り当てを含む)。Go ではこれを `alloc_space` と呼びます。スタック割り当ては追跡されません。これはガベージコレクションの負荷を調査するのに役立ちます。この測定値がバージョン `1.33.0` でどのように変化するかについての注記も、[Delta プロファイル](#delta-profiles)で参照してください。

Heap Live Objects
: ガベージコレクション後も使用されている、各関数によってヒープメモリに割り当てられたオブジェクトの数。Go ではこれを `inuse_objects` と呼びます。これは、サービス全体のメモリ使用量を調査し、潜在的なメモリリークを特定するのに役立ちます。

Heap Live Size
: これは、ガベージコレクション後も使用されている、各関数によって割り当てられたヒープメモリの量です。デフォルト設定 (GOGC=100) では、これは通常、プロセスの RSS 使用量の約 50% に相当します。Go ではこれを `inuse_space` と呼びます。このメトリクスを使用してメモリ消費量を確認し、[リークを診断][4]してください。Go がどのようにメモリを管理するかについての詳細は、[Go メモリメトリクスの仕組みを解き明かす][5]および [Go ガベージコレクターガイド][6]を参照してください。

Mutex
: プロファイリング期間中に、関数が Mutex で待機していた時間 (デフォルト: 60 秒)。このプロファイルのスタックトレースは、Mutex でブロックされていた別のゴルーチンの処理を進めた `Unlock()` 操作を指します。スピンロックを使用した短時間の Mutex 競合はこのプロファイルでは取得されませんが、CPU プロファイルで確認できます。この測定値がバージョン `1.33.0` でどのように変化するかについての注記も、[Delta プロファイル](#delta-profiles)で参照してください。

Block
: プロファイリング期間中、各関数が Mutex やチャネル操作で待機していた時間 (デフォルト: 60 秒)。スリープ、GC、ネットワーク、およびシステムコール操作はこのプロファイルでは取得されません。ブロック操作はブロック解除後にのみ取得されるため、このプロファイルを使用して、停止しているように見えるアプリケーションのデバッグを行うことはできません。Mutex 競合の場合、このプロファイルのスタックトレースは、ブロックされた `Lock()` 操作を指します。これはプログラムのどこでブロックが発生しているかを示し、Mutex プロファイルはプログラムのどの部分が競合を引き起こしているかを示します。詳細については、Datadog の [Go における Block プロファイリング][1]の調査を参照してください。この測定値がバージョン `1.33.0` でどのように変化するかについての注記も、[Delta プロファイル](#delta-profiles)で参照してください。**注**: Block プロファイラーは、本番環境のワークロードで顕著なオーバーヘッドを引き起こす可能性があります。本番環境で有効にする場合は、高いレート (100 ミリ秒である `100000000` など) を優先し、レイテンシや CPU 使用率の増加の兆候がないか確認してください。

Goroutines
: 現在同じ関数を実行している (CPU 上および CPU 外で待機中の両方の) goroutines の数のスナップショット。スナップショット間で goroutines の数が増加している場合、プログラムが goroutines をリークしている可能性があります。ほとんどの健全なアプリケーションでは、このプロファイルはワーカープールとそれらが使用する goroutines の数によって占められています。極めてレイテンシに敏感で、多数の goroutines (> 10,000) を使用するアプリケーションでは、このプロファイルを有効にすると stop-the-world ポーズが発生することに注意してください。ポーズはプロファイリング期間 (デフォルト 60 秒) ごとに 1 回のみ発生し、通常は goroutines あたり約 `1µsec` 続きます。p99 レイテンシ SLO が約 `100ms` の一般的なアプリケーションでは、通常、この警告を無視できます。詳細については、Datadog の [Go での goroutines プロファイリング][2]に関する調査を参照してください。

#### Delta プロファイル {#delta-profiles}
<div class="alert alert-info">Go プロファイラーのバージョン <code>1.33.0</code>以前では、Allocations、Allocated Memory、Mutex、および Block の各メトリクスは、<em>プロファイリング期間中</em>ではなく、<em>プロセスが開始されてからの累積値</em>として表示されます。バージョン <code>1.33.0</code> での Delta プロファイルへの変更により、これらの測定値が累積されるのではなく、どのように変化しているかを確認できるようになります。Delta プロファイリングはデフォルトで有効になっています。プロファイラーのバージョン <code>1.35.0</code> では、 <code>WithDeltaProfiles</code> オプションを使用して Delta プロファイルを無効にすることができます。<br/><br/>プロファイラーのバージョン <code>1.37.0</code>以降では、Delta プロファイルが有効な場合、アップロード帯域幅の使用量を削減するために累積プロファイルはアップロードされなくなります。完全な累積プロファイルに依存している場合は、<a href="/help/">サポートにお問い合わせ</a>の上、ユースケースについてご相談ください。</div>

: 各メソッドによってヒープメモリに割り当てられ、まだガベージコレクションされていないオブジェクトの数。これは、サービス全体のメモリ使用量を調査し、潜在的なメモリリークを特定するのに役立ちます。<br />

_要件: Ruby 3.1 以降 _ および[手動有効化][2] (現在 Ruby 4 とは互換性がありません)

: バックグラウンドスレッドを含む、他の「ノイジーネイバー」スレッドによってスレッドの動作が妨げられた時間を記録します。これは、タイムラインの可視化を使用する際にアプリケーションのレイテンシスパイクを調査するのに役立ちます。<br />
_要件: Ruby 3.2 以降 _

{{< programming-lang lang="dotnet" >}}

プロファイリングを有効にすると、[サポートされている .NET バージョン][1]に対して以下のプロファイルタイプが収集されます。

Wall Time
: マネージドメソッドで費やされた経過時間。経過時間には、コードが CPU で実行されている時間、I/O を待機している時間、およびメソッドの実行中に発生するその他すべての時間が含まれます。

CPU (v2.15 以降)
: 各メソッドが CPU 上で実行に費やした時間。

Thrown Exceptions (v2.31 以降)
: 各メソッドによって発生したキャッチ済みまたは未キャッチの例外の数、およびその型とメッセージ。

Allocations (v3.28 以降)
: 各メソッドによって割り当てられたオブジェクトの数とサイズ、およびその型。
.NET Framework の場合、サイズは利用できません。<br />
_要件: .NET Framework (Datadog Agent 7.51 以降および v3.2 以降が必要) / .NET 6 以降。ただし、より正確なサンプリングのために Datadog は .NET 10 以降を推奨しています。

Lock (v2.49 以降)
: スレッドがロックを待機している回数と、その待機時間。<br />
_要件: .NET Framework (Datadog Agent 7.51 以降が必要) / .NET 5 以降_

Live Heap (v3.28 以降)
: メモリ内に保持されている割り当て済みオブジェクトのサブセット (クラス名を含む)。<br />
_要件: .NET 7 以降。ただし、より正確なサンプリングのために Datadog は .NET 10 以降を推奨しています。

Outgoing HTTP requests (Timeline 内) (プレビュー、v3.19 以降)
: 送信 HTTP リクエストの開始と終了。各フェーズ (DNS、セキュリティハンドシェイク、ソケット、リクエスト/レスポンス) の所要時間と、予期しないリダイレクトの可能性を表示します。<br />
_要件: .NET 7 以降_

Thread lifetime (Timeline 内) (v3.19 以降)
: スレッドのライフタイムの開始と終了。ThreadPool の枯渇や短命なスレッドを容易に検出できます。<br />
_要件: .NET Framework (Datadog Agent 7.51 以降および v3.2 以降が必要) / .NET 5 以降_

Garbage Collector CPU consumption (v3.19 以降)
: ガベージコレクターのスレッドが CPU 上で実行されていた時間。<br />
_要件: .NET Framework (Datadog Agent 7.51 以降および v3.2 以降が必要) / .NET 5 以降_

**注**: .NET 10 より前では、.NET ランタイムで使用されるサンプリングアルゴリズムにより、{{< ui >}}Allocations{{< /ui >}} および {{< ui >}}Live Heap{{< /ui >}} のプロファイリングで小さなオブジェクトよりも大きなオブジェクトが多く表示される場合があります。Datadog では、より統計的に正確な結果を得るために .NET 10 以降の使用を推奨しています。

{{< programming-lang lang="ddprof" >}}

プロファイリングが有効になると、[サポートされている言語とバージョン][1]に対して以下のプロファイルタイプが収集されます。

CPU
: 各関数が CPU で実行されていた時間。

Allocations
: プロファイリング期間中 (デフォルト :  59 秒) の各関数による割り当て数。これには、その後に解放された割り当てが含まれます。スタック割り当ては追跡されません。

プロファイリングが有効になると、[サポートされている言語とバージョン][1]に対して以下のプロファイルタイプが収集されます。

CPU Time (eBPF)
: 各メソッドまたは関数が CPU 上で実行されていた時間。マルチスレッドプログラムでは、CPU 時間が経過時間よりも長くなることがあります。たとえば、2 つのスレッドがそれぞれ 45 秒間実行されている場合、「eBPF CPU 時間、1分あたり 1 分 30 秒」と表示されます。
