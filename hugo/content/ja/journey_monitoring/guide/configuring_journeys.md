## 概要 {#overview}

このガイドでは、重要なユーザーフローを表し、その健全性を明らかにするジャーニーを構成する方法を説明します。

ジャーニーの構成には 3 つのステップがあります。

1. ジャーニーを作成し、そのユーザーフローを定義します。
2. 重要な技術的ステップを表す RUM オペレーションを追加します。
3. ジャーニーをカバーする Synthetic テストを追加します。

これらの手順を完了したら、ジャーニーの主要なパフォーマンス指標 (KPI)、オペレーション、サービスレベル目標 (SLO)、テスト、およびバリアントを検証します。

## Journey Monitoring を使用するタイミング {#when-to-use-journey-monitoring}

Journey Monitoring は、ユーザーの行動と技術的な健全性を組み合わせて、エンドツーエンドのフローを監視します。これは、複数の製品における個別の構成が必要となるフローを監視およびトラブルシューティングするための主要な場所として機能します。

一般的な選択肢は以下のとおりです。

- **Real User Monitoring (RUM)**:
  - RUM Session Explorer のファネル、または RUM イベントに基づくファネルウィジェット
  - ボタンクリックやページビューなど、ユーザーのアクティビティを追跡するウィジェット
  - フローのボリューム、完了までの時間、または完了したジャーニーを測定するカスタムメトリクスまたはアクション
  - 主要な技術的ステップを表すカスタムバイタル (ジャーニー内の RUM オペレーションで表現可能)
- **Synthetic Monitoring**: 同じフローをカバーしているものの、ジャーニーのテストスイートに組織されていない複数のテスト。
- **Product Analytics**: エンドツーエンドのフロー全体で行動を追跡するファネル、ジャーニーパス、またはその他の可視化機能。

Journey Monitoring は、Product Analytics を使用してユーザーの行動とエクスペリエンスを把握し、RUM を使用してパフォーマンスと可用性を評価し、Synthetic テストを使用して回帰の検出とジャーニーの稼働時間の測定を行います。

## はじめに {#before-you-begin}

このガイドに従う前に、[Journey Monitoring の概要と前提条件][1] を確認してください。Journey Monitoring を使用するには、RUM without Limits、Product Analytics、Synthetic Browser Tests、または Synthetic Mobile Tests のいずれかの製品について、組織が有料サブスクリプションまたはトライアルサブスクリプションを保有している必要があります。

### 権限とロール {#permissions-and-roles}

Journey Monitoring は複数の製品のアセットを使用するため、ジャーニーおよびリンクされたアセットへのアクセス権は各製品の権限に依存します。

ジャーニーを作成または編集するには、以下の手順に従います。

- 自分のロールに Journey Monitoring の書き込みアクセス権が必要です。
- ジャーニーのテストスイートを作成するには、Synthetic Monitoring の書き込みアクセス権も必要です。それがない場合、Datadog はテストスイートなしでジャーニーを作成しますが、後から追加することも可能です。

ジャーニーおよびリンクされたアセットの表示と編集の詳細については、[ロールと権限][10] を参照してください。

## ステップ 1: ジャーニーを作成する {#step-1-create-a-journey}

### ユーザーフローを選択する {#choose-a-user-flow}

ビジネス成果を達成するためにユーザーが完了する必要のあるユーザー向けの重要なフローに対してジャーニーを作成します。ジャーニーは複数のステップにまたがり、重要なアクションを表している必要があります。

各ジャーニーの焦点を明確にするために、以下のガイドラインに従ってください。

**行うべきこと:**

- 個別のユーザーフローごとにジャーニーを作成し、関連するジャーニー同士を接続します。
- 1 つの高レベルなジャーニーを使用し、属性フィルターを使用して、米国や英国のユーザーなど、コホートを比較します。

**避けるべきこと:**

- 単一の短いインタラクションのためのジャーニーを作成しないでください。代わりに [RUM オペレーション][4] を使用してください。
- いくつかの異なるユーザーフローを 1 つのジャーニーに組み合わせないでください。
- 国などの属性値のみが異なる重複したジャーニーを作成しないでください。

### 作成方法を選択する {#choose-a-creation-method}

ジャーニーを手動で作成するか、推奨ジャーニーから開始します。手順については、[Journey Monitoring のセットアップ][2] を参照してください。

特定のユーザーフローを想定しているかどうかに基づいて、作成方法を選択します。

- どのジャーニーを作成すべきか迷う場合は、[推奨ジャーニー][6] から開始してください。推奨ジャーニーは、開始数、コンバージョン数、コンバージョン率などの高レベルな KPI を提供します。
- 機能をリリースし、アプリケーションのエクスペリエンスを更新する際は、新しい推奨ジャーニーを確認してください。Datadog は、アプリケーション内のユーザーアクティビティに基づいて提案を生成します。
- 監視したい特定のユーザーフローがある場合は、手動でジャーニーを作成してください。

### 開始条件と終了条件を定義する {#define-start-and-end-conditions}

ジャーニーは、その開始イベントと終了イベントによって定義されます。アクションイベント、ビューイベント、またはその両方を選択します。

#### 複数の開始イベントと終了イベント {#multiple-start-and-end-events}

複数の開始イベントは、同じユーザーフローへの複数のエントリーポイントを表すことができます。複数の終了イベントは、複数の有効な結論を表すことができます。

イベントを追加するたびに、ジャーニーの定義が広がります。開始イベントや終了イベントが多すぎると、ジャーニーの範囲が不明確になり、KPI の精度が低下する可能性があります。

#### 属性フィルター {#attribute-filters}

ジャーニーレベルの属性は、社内ユーザーなどの広範なコホートを含めたり除外したりします。個々の開始条件および終了条件の属性により、フローがさらに絞り込まれます。

重要な属性フィルターをジャーニーの名前や説明に含めることで、ユーザーは KPI のスコープを理解しやすくなります。

#### 参照元のパス {#referrer-paths}

参照元のパスは、開始イベントまたは終了イベントを特定のページビューに続くインスタンスに限定します。これらは、複数のジャーニーコンテキストに表示されるイベントと、特定のジャーニーに属するインスタンスを区別する上で役立ちます。

#### ジャーニーのバリアント {#journey-variants}

＠ベースとなるジャーニー定義には、開始イベントと終了イベントのみが含まれます。バリアントは、それらのポイントの間に特定の中間アクションや表示イベントのシーケンスを追加します。バリアントは、ジャーニー全体のスコープを変更することなく、同じジャーニー内の一般的なパスを区別します。

バリアントを選択すると、ジャーニーのメトリクスとテレメトリがそのイベントシーケンスに絞り込まれます。これにより、異なるパス間でのボリューム、コンバージョン率、完了までの時間を比較できます。属性フィルターを使用すると、バリアントを特定のコホートにさらに絞り込むことができます。

各バリアントには、一意の名前と少なくとも 1 つの中間イベントが必要です。バリアントの作成、分析、削除の詳細については、[ジャーニーのバリアント][3] を参照してください。

#### 開始イベントと終了イベントの選択 {#start-and-end-event-selection}

開始イベントは、ジャーニーを明確に開始し、ユーザーの意図的なアクションを表すものでなければなりません。

<div class="alert alert-danger">ジャーニーが完了したことを確認できる終了イベントを選択してください。「支払う」または「送信」をクリックしても、アクションが成功したとは限りません。後のイベントで成功が確認できる場合は、そのイベントを使用してください。そうすることで、失敗した試行が完了したジャーニーとしてカウントされなくなります。</div>

例:

- **サインインジャーニー**
  - 開始: ユーザーがサインインページを開きます。
  - 終了: アプリケーションがユーザーをホーム画面にリダイレクトします。
  - 次で終了しない: ユーザーが**サインイン**をクリックします。
- **チェックアウトジャーニー**
  - 開始: ユーザーがチェックアウトページを開きます。
  - 終了: アプリケーションが支払い確認モーダルを表示します。
  - 次で終了しない: ユーザーが**支払う**をクリックします。
- **フォーム送信ジャーニー**
  - 開始: ユーザーがフォームを開きます。
  - 終了: アプリケーションが送信確認メッセージを表示します。
  - 次で終了しない: ユーザーが**送信**をクリックします。

### 名前、タグ、所有権を追加する {#add-names-tags-and-ownership}

タグとチームの所有権は、チームが関連ジャーニーを見つけ、ジャーニーカタログをフィルタリングする上で役立ちます。一貫した命名規則とタグ付け規則により、カタログが拡大してもジャーニーを整理された状態に保つことができます。

## ステップ 2: RUM オペレーションを追加する {#step-2-add-rum-operations}

RUM オペレーションは、ジャーニーの重要な瞬間に対する技術的なカバレッジを提供します。それらの可用性とレイテンシーは、技術的なパフォーマンスがユーザーの離脱に寄与しているかどうかを説明する上で役立ちます。

### 推奨オペレーションをリンクする {#link-suggested-operations}

ジャーニー詳細レポートは時間相関を使用して、ジャーニーの一部である可能性がある既存の RUM オペレーションを提案します。ユーザーがジャーニーを完了する過程で遭遇するオペレーションのみをリンクしてください。

{{< img src="journey_monitoring/journey-monitoring-correlated-operations.png" alt="実行、成功率、レイテンシー、および SLO 作成オプションを含む、時間ベースで相関付けられた RUM オペレーションが表示されている、ジャーニーモニタリング詳細レポート。" style="width:100%;" >}}

オペレーションのリンク:

- オペレーションをジャーニーにリンクし、それをジャーニーのクリティカルパスの一部として識別します。
- オペレーションにまだ SLO がない場合、そのオペレーションの可用性 SLO を自動的に作成します。

### オペレーションを作成する {#create-operations}

以下のいずれかの方法でオペレーションを作成します。

- [Datadog で][11]
- [RUM Operations API を使用して][12]
- [RUM SDK API を使用して][13]

### オペレーションの SLO を作成する {#create-slos-for-operations}

Datadog がジャーニーへの貢献度を評価するには、リンクされた各オペレーションに少なくとも 1 つの SLO が必要です。オペレーションには、可用性 SLO、レイテンシー SLO、またはその両方を持たせることができます。ガイダンスについては、[RUM オペレーションで SLO を作成するためのベストプラクティス][14] を参照してください。

ジャーニー詳細レポートからオペレーションを作成すると、Datadog はそれをジャーニーにリンクし、可用性 SLO を作成します。RUM SDK API または RUM Operations API を使用してオペレーションを作成する場合は、[RUM Operations API][12] を使用してそれをジャーニーにリンクしてください。


<div class="alert alert-tip">
ジャーニーのコンバージョンに最も大きな影響を与えるオペレーションから始めます。必要に応じてオペレーションを追加します。
<ul>
<li>ユーザーのサインインジャーニーについては、最終的なサインインアクションを監視し、有効な認証情報で認証が成功することを確認します。</li>
<li>e コマースのチェックアウトジャーニーでは、支払いアクションを監視することが重要です。支払いに失敗すると、ユーザーはジャーニーを完了できなくなります。</li>
</ul>
</div>

## ステップ 3: Synthetic テストカバレッジを追加する {#step-3-add-synthetic-test-coverage}

Synthetic テストは、重要なジャーニーパスに対する技術的なカバレッジを提供します。テストの失敗はユーザーに影響を与える回帰を示している可能性があり、カバーテストによってジャーニーのアップタイムが決定されます。

Datadog は各ジャーニーに対して、Synthetic テストスイートと、デフォルトの目標が 99.9% である編集可能なアップタイム SLO を自動的に作成します。また、ジャーニーをカバーする Synthetic テストも追加します。テストカバレッジ、テストの管理、およびアップタイム SLO の詳細については、[ジャーニーのアップタイム][5] を参照してください。

### ジャーニーカバレッジを確認する {#review-journey-coverage}

Datadog は RUM データを使用して、ジャーニーをカバーする Synthetic テストを特定します。これらのテストは、ジャーニー詳細ページおよび Synthetic テストスイートページに表示されます。

- Datadog がジャーニーをカバーしていると特定したテストを確認します。
- Datadog がスイートに含まれていないカバーテストを特定した場合、インジケーターが追加のテストを強調表示します。

### ジャーニーにテストを追加する {#add-tests-to-a-journey}

スイートが空の場合、または Datadog が追加のテストを特定した場合は、カバーテストを追加します。

- 既存のテストを追加するには、**ジャーニーカバレッジを管理する**を選択し、追加するテストを選択します。
- カバレッジを作成するには、[ブラウザテスト][7] または [モバイルアプリテスト][8] を作成し、それをジャーニーのスイートに追加します。詳しくは、[テストスイート][9] を参照してください。

{{< img src="journey_monitoring/journey-monitoring-covering-tests.png" alt="ジャーニーをカバーする Synthetic ブラウザテストが表示されている、スイート内のテストを管理するパネル。" style="width:100%;" >}}

**プレビュー**: ジャーニーをカバーする Synthetic テストがない場合、[Bits Testing][15] を使用して、カバーするブラウザテストを生成できます。[Bits Testing プレビューにサインアップ][16] します。

### カバレッジを維持する {#maintain-coverage}

- ジャーニーの開始条件や終了条件を変更すると、それをカバーするテストに影響を与える可能性があります。これらの条件を変更した後は、カバレッジを確認してください。
- ジャーニーは、そのスイートに少なくとも 1 つのカバーするテストが含まれている場合にのみ、アップタイムを報告します。ジャーニーのカバレッジが失われると、アップタイムの報告が停止します。

カバレッジの管理は Synthetic テストを変更するため、Synthetic Monitoring の書き込みアクセス権と、スイートに対する制限ポリシーが必要です。[ロールと権限][10] を参照してください。

## Journey Monitoring の構成を検証する {#validate-the-journey-monitoring-configuration}

適切に構成されたジャーニーには、以下の特徴があります。

- 開始数、コンバージョンボリューム、コンバージョン率、コンバージョンまでの時間といったトップレベルの KPI が期待されるユーザー行動と一致している。
- リンクされた RUM オペレーションと Synthetic テストがジャーニーにおける重要なステップの技術的パフォーマンスを表している。
- リンクされた各オペレーションに少なくとも 1 つの SLO と高い成功率が設定されており、重要なステップがユーザーにとって利用可能であることを示している。
- Synthetic テストが断続的な失敗なしに一貫した結果を生成する。
- ユーザーが期待される異なるパスを通じてジャーニーを完了できる場合、バリアントはそのパスを表す。
