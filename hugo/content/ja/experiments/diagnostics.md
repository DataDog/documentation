## 概要{#overview}

Datadog は実験分析で診断チェックを実行して、ロールアウトの決定を下す前に、データの品質、ランダム化、および構成の問題を特定できるようにします。チェックが問題を検出した場合には、Datadog はそれを警告、メトリクスメッセージ、または失敗した診断チェックとして実験結果ページに表示します。

リフト、信頼区間、またはグローバルリフトを解釈する前に、失敗した診断チェックまたは警告バナーを確認してください。

## トラフィックの不均衡 {#traffic-imbalance}

トラフィックの不均衡 (サンプル比率の不一致、SRM とも呼ばれます) とは、バリアント全体で観測された割り当てが、構成された割り当ての重みと大きく異なることを意味します。

Datadog は、ピアソンのカイ二乗適合度検定を使用して SRM を検出します。この検定は、観測されたバリアントのカウントと、構成された重みから期待されるカウントを比較します。p 値が、有意水準 (アルファ) `0.001` に相当する `0.001` を下回ると、診断は失敗となります。Datadog は、この全体的なチェックに対して最小合計サンプルサイズや期待カウントの要件を適用しません。

この検定は逐次検定としての妥当性を持たないため、より厳格な α = 0.001 の水準で検定を実施します。より厳格な有意水準を設定することで、偽陽性を回避できます。

SRM は結果を解釈する上での阻害要因として扱ってください。これは、実験の有効なランダム化、エクスポージャーのログ記録、または分析対象の母集団に偏りがあることを示しています。根本的な原因を見つけて修正するまで、リフト、信頼区間、およびグローバルリフトは、有効な因果推論をサポートできません。

### 一般的な原因 {#common-causes}

Datadog Feature Flags を利用した実験における一般的な原因は以下のとおりです。

- トラフィックの分割 (バリアントに割り当てられた相対的なパーセンテージ) が開始後に変更された (例: `90/10` から `50/50` へ)。その一方で、以前の分割に基づいて行われた割り当てが分析期間内に残っている。
- 割り当て後、バリアントによって異なる割合でエクスポージャーイベントが失われている。たとえば、バリアント固有のリダイレクトやクラッシュにより、バッファリングされたエクスポージャーイベントが Datadog に到達できない場合があります。

実験期間中、バリアント間のトラフィック分割を一定に保ってください。均等に分割された実験を拡大するには、両方のバリアントの [トラフィックエクスポージャー][1] を比例して増やしてください。たとえば、トラフィックエクスポージャーを `10/10` 分割から `50/50` 分割に増やします。これにより、相対的な分割比を維持しながら、両方のバリアントの割合が比例して増加します。

ターゲティングルール、ターゲティングキー、またはトラフィックエクスポージャーを変更しても、それ自体が SRM を引き起こすことはありません。そのような変更は、含まれる割り当て対象の母集団をバリアントによって異なる方法で変化させた場合にのみ、SRM を引き起こします。そうでなければ、トラフィック量が変わるか、異なる診断結果が生じる可能性があります。たとえば、一貫性のない SDK `targetingKey` は、割り当てとメトリクスイベントが同じ対象に紐付かなくなった場合に、**メトリクスデータの欠落** の原因となることがあります。同じ記録対象が複数のバリアントを受け取った場合にのみ、**混合割り当て** が発生します。

ウェアハウスネイティブの実験における一般的な原因は以下のとおりです。

- Datadog で構成された各バリアントの予想エクスポージャー比率が、アップストリームのランダム化システムで使用される割り当て確率と一致していません。
- [Exposure SQL モデル][2] が、あるバリアントの割り当て対象を他のバリアントよりも頻繁に除外するような方法で、タイムスタンプ制約をフィルタリング、結合、集計、または適用している。
- アップストリームの割り当てログで、バリアントによって異なる割合で割り当てが失われたり、誤って記録されたりしている。処理依存のテレメトリ損失や、あるバリアントを誤ったバリアントキーにマッピングするなどが挙げられる。
- この分析には、割り当て後に生じる行動に基づく対象が含まれており、その行動はバリアントの影響を受ける可能性がある。たとえば、処理依存の適格性イベントやボットフィルターが、あるバリアントをより高い割合で除外する可能性があります。

### 解決方法 {#how-to-resolve}

1. SRM の原因を特定するまで、実験の意思決定を一時停止してください。
2. Datadog Feature Flags を利用した実験では、フラグの [{{< ui >}}Version history{{< /ui >}}][3] でトラフィック分割やバリアントの変更を確認し、混合割り当てがないかチェックし、すべてのバリアントでエクスポージャーイベントが同じ割合で Datadog に到達していることを確認してください。
3. ウェアハウスネイティブの実験では、Datadog における各バリアントの予想エクスポージャー比率と、アップストリームの割り当て確率を比較してください。Exposure SQL モデルが結合、フィルタリング、集計、タイムスタンプ制約を適用する前後の、バリアントごとの生の割り当て数を比較してください。
4. 不均衡が特定のセグメントや時間枠に限定されているかどうかをチェックしてください。セグメント固有または起動時の SRM は、根本原因を絞り込むのに役立ちます。
5. 不均衡の原因を修正してから、実験分析を再実行してください。

## 割り当ての欠落 {#missing-assignments}

Datadog に実験の割り当てデータがない場合、結果を計算できません。これは、機能フラグが評価されていないか、トラフィックが実験のターゲティングルールに到達していないか、またはウェアハウスの Exposure SQL モデルが指定された**Experiment ID** および **Variant ID** の値に対して分析期間中に何も行を返さない場合に発生する可能性があります。

Datadog Feature Flags を利用し、ウェアハウスメトリクスを使用する実験の場合、Datadog はそれらのエクスポージャーをウェアハウス内の `g_exposures` テーブルに同期する前に割り当てを記録することがあります。同期が完了するまで、ウェアハウスメトリクスの結果は利用できません。

### 解決方法 {#how-to-resolve-1}

- Datadog Feature Flags を利用している実験については、フラグが正しい環境で有効になっており、期待される対象に対してアプリケーションがフラグを評価していることを確認してください。フラグの [{{< ui >}}Real-time metric overview{{< /ui >}}] におけるエクスポージャーイベントをチェックしてください。
- ウェアハウスネイティブの実験については、Exposure SQL モデルが期待される **Subject Key**、**Timestamp**、**Experiment ID**、および **Variant ID** の値を含む行を返すことを確認してください。
- 実験を開始したばかりの場合は、次の分析実行を待つか、[{{< ui >}}Run an update now{{< /ui >}}] をクリックしてください。

## 混合割り当て {#mixed-assignments}

同じ実験内で同じ対象が複数のバリアントに割り当てられている場合、Datadog はその対象を分析から除外します。Datadog は、各割り当てソースについて個別に割合を計算し、そのソースのユニークな対象を分母として使用します。診断は 5% 以下で合格、5% を超え 20% 未満で警告、20% 以上で不合格となります。除外される割合が増えるほど、結果の代表性と信頼性は低下します。

### 解決方法 {#how-to-resolve-2}

- Datadog Feature Flags を利用する実験については、開始後に予期しない変更がないか、特に実験のターゲティングルール、トラフィック分割、またはバリアントへの変更について、フラグの [{{< ui >}}Version history{{< /ui >}}][3] を確認してください。
- ウェアハウスネイティブの実験では、[Exposure SQL モデル][2] で **Experiment ID** にマッピングされた列が、より広範なフラグキーではなく、特定の実験やフラグ割り当てキーなど、実験のエクスポージャーのみを識別するようにしてください。
- ウェアハウスネイティブの [Exposure SQL モデル][2 ]が意図的にフラグ評価ログを読み取る場合は、実験のエクスポージャーではない評価を除外してください。たとえば、モデルがフラグのすべての評価をキャプチャする場合、エクスポージャーランプは、対象者が実験の対象となる前の実験前の対照群での経験を記録し、その後、対象となった後にランダム化された処理エクスポージャーを記録することができます。実験前のフラグ評価は実験の一部ではないため、エクスポージャーとしてキャプチャされるべきではありません。
- ウェアハウスネイティブの実験では、矛盾するバリアントレコードが割り当てデータにないかチェックしてください。
- 矛盾する割り当てのソースを修正してから、分析を再実行してください。

## ディメンション割り当ての不均衡 {#dimensional-assignment-imbalance}

Datadog は、バリアントに割り当てられる確率がディメンション値間で大きく異なる場合に、実験にフラグを立てることができます。たとえば、特定のデバイスタイプ、国、プラン、または顧客層では、実験の他の部分とは異なる分割でバリアントを受け取る可能性があります。

割り当てディメンションごとに、Datadog はバリアントとディメンション値の間の独立性に関するピアソンのカイ二乗検定を実行します。複数のディメンションのテストを考慮するため、Datadog はボンフェローニ補正を適用します。ディメンションの p 値が `0.001 / n` を下回ると、そのディメンションは不合格となります。ここで `n` はテストされた対象ディメンションの数です。Datadog は、その値の期待バリアント数が 5 を下回るディメンション値を除外し、100 を超える値を持つディメンションをスキップします。また、残りのディメンション値が少なくとも 2 つあり、かつ正の限界カウントを持つバリアントが 2 つ以上あることが条件となります。スキップされたディメンションは `n` に寄与しません。対象となるディメンションがない場合、診断はディメンションテストを実行せずに合格となります。

全体的な SRM チェックと同様に、ディメンションテストで分析を繰り返し実施する場合、その結果の有効性は各分析間で引き継がれません。ボンフェローニ補正は、1 回の実行でテストされたディメンションを制御するものであり、実験データが蓄積される際の繰り返しチェックを制御するものではありません。

この診断は、全体的なトラフィックの不均衡、つまりサンプル比率の不一致 (SRM) とは別のものであり、グローバルな不均衡のみではトリガーされません。両方の診断が失敗した場合、影響を受けるディメンション値は、全体的な SRM の原因を特定するのに役立ちます。たとえば、デバイスタイプのディメンションの不均衡は、バリアントの配信、SDK 評価、リダイレクト、ページパフォーマンス、クラッシュ、またはエクスポージャーテレメトリにおけるデバイス固有のバグを示している可能性があります。

Datadog は、対象の最初の割り当てレコードのディメンション値を使用します。対象のディメンション値に対するその後の変更によって、この診断が引き起こされることはありません。

### 解決方法 {#how-to-resolve-3}

- 影響を受けるディメンション値を確認し、それらを全体的なトラフィック不均衡診断と比較してください。
- フラグ評価、バリアント配信、アプリケーションの動作、およびエクスポージャーテレメトリにおけるセグメント固有の差異を調査してください。
- ウェアハウスネイティブの実験については、Exposure SQL モデルが意図した割り当て時のプロパティ列をマッピングしており、セグメントによって異なるエクスポージャーのフィルタリングを行っていないことを確認してください。
- 局所的な不均衡の原因を修正してから、分析を再実行してください。

## メトリクスデータの欠落 {#missing-metric-data}

Datadog は、割り当てが存在するにもかかわらず実験分析で使用可能なメトリクス値が見つからない場合に、**メトリクスデータの欠落**を報告します。単純メトリクスおよび比率メトリクスの場合、外れ値処理の前に少なくとも 1 つの寄与値がゼロ以外である必要があります。すべての寄与値がゼロまたは null の場合、診断はプライマリメトリクスに対しては失敗し、セカンダリメトリクスまたはガードレールメトリクスに対しては警告を出します。パーセンタイルメトリクスの場合、ゼロは有効な結果であり、null の結果のみが欠落としてカウントされます。Datadog がメトリクスがプライマリであるかどうかを判断できない場合、欠落データを失敗として扱います。

この診断は、ソースイベントが一度も発生しなかったことを必ずしも意味するわけではありません。イベントは存在していても、メトリクスのフィルターに適合しなかったり、実験の割り当てと結合できなかったり、あるいはゼロまたは null のメトリクス値しか生成されなかったりする可能性があります。

### 一般的な原因 {#common-causes-1}

- メトリクス定義のイベント名、集計、フィルター、またはデータソースが、出力されているデータと一致していない。
- ソースイベントが発生していないか、対象の最初の割り当ての前にのみ発生しているため、割り当て後の属性から除外されている。
- メトリクスイベントと実験の割り当てで、同じ対象が異なる方法で識別されている。この対象識別子の不一致は、メトリクスデータが欠落する一般的な原因です。
  - Datadog Feature Flags を利用する実験における Product Analytics または RUM メトリクスの場合、構成された [対象タイプ属性][4] は SDK `targetingKey` と一致している必要がある。
  - ウェアハウスメトリクスの場合は、[Metric SQL モデル][5] でマッピングされた対象列に、割り当て対象列と同じ値が含まれている必要がある。Datadog Feature Flags を利用した実験の場合、それらの値は SDK `targetingKey` と一致している必要があります。ウェアハウスネイティブの実験の場合は、[Exposure SQL モデル][2] で構成された割り当て対象列と一致している必要があります。
- ウェアハウスの Metric SQL モデルが分析期間内に一致する行を返さないか、期待されるイベントを除外している。

### 解決方法 {#how-to-resolve-4}

1. メトリクスを開き、イベント名、集計、フィルター、およびデータソースが正しいことを確認してください。メトリクスイベントのボリュームチャートで、最近の一致データをチェックしてください。
2. 割り当てられた対象の識別子と、そのメトリクスイベントの識別子を比較してください。構成された対象タイプ属性またはマッピングされたウェアハウス列に、SDK `targetingKey` または Exposure SQL モデルで構成された割り当て対象列と同じ値が含まれていることを確認してください。
3. メトリクスイベントが、対象の最初の割り当て後、かつ実験分析期間内に発生していることを確認してください。
4. Datadog Feature Flags を利用した実験で、[ソースコードインテグレーション][6] が構成されている場合は、プライマリメトリクスの **メトリクスデータの欠落** エラーについて、[{{< ui >}}Ask Bits{{< /ui >}}][7] をクリックしてください。Bits は、フィーチャーフラグが評価されるソースの場所を調査し、近くのメトリクスインスツルメンテーションをチェックするのに役立ちます。コード検索で何も見つからなくても、それだけでは結論は出ず、SDK やフラグがアプリケーションから欠落していることを証明するものではありません。
5. ウェアハウスメトリクスの場合は、Metric SQL モデルを実行するか、そのソーステーブルを直接クエリしてください。
6. メトリクス定義、ID マッピング、イベントのタイミング、またはインスツルメンテーションの問題を修正してから、実験分析を再実行してください。

## メトリクスがゼロにウィンザー化されました {#metric-winsorized-to-zero}

外れ値の処理は、極端なメトリクス値を上限で制限し、分散を抑えます。外れ値の処理の前に少なくとも 1 つの生の値がゼロ以外であったにもかかわらず、外れ値の処理によってすべてのバリアントの全体的な結果がゼロまたは null になった場合、Datadog は警告を表示します。比率メトリクスの場合、Datadog は分子と分母を個別にチェックします。この診断にはパーセンテージや最小サンプル数のしきい値はなく、実験が失敗することはありません。

これは、メトリクスイベントを実行する対象が少数であり、外れ値の処理によって観測されたすべての値がゼロに制限される場合に発生する可能性があります。たとえば、メトリクスに 99 パーセンタイルの上限ウィンザー化境界があり、ゼロ以外の値を持つ対象が 1% 未満の場合、上限はゼロになります。その場合、ゼロ以外のすべての値は外れ値として扱われ、ゼロに制限されます。

パーセンタイルウィンザー化の場合、Datadog は、割り当てられたすべての対象またはゼロ以外の値のみを使用して境界を計算できます。計算からゼロを除外することで、疎なメトリクスにおいて構造的なゼロが境界をゼロに設定するのを防ぐことができます。この戦略は、ゼロ値の対象を分析から削除するわけではありません。パーセンタイル境界を計算する際にのみゼロを除外し、Datadog はその境界をすべての対象に適用します。

### 解決方法 {#how-to-resolve-5}

1. メトリクスを開きます。
2. [{{< ui >}}Experiment settings{{< /ui >}}] の下にある [{{< ui >}}Outlier handling{{< /ui >}}] を確認します。パーセンタイルウィンザー化を行う疎なメトリクスの場合は、ゼロ以外の値のみから境界を計算してください。
3. ウィンザー化のパーセンタイルを変更したり、外れ値の処理を無効にしたりして警告を解決したくなるかもしれません。しかし、この診断をトリガーするメトリクスは、統計的検出力が低い傾向があります。メトリクスを意思決定の根拠にする前に、[サンプルサイズ計算ツール][8] を使用して、実験期間と最小検出可能効果を見積もってください。
4. メトリクスを更新した後、実験分析を再実行してください。

## 実験前のメトリクスの不均衡 {#pre-experiment-metric-imbalance}

CUPED が有効な場合、Datadog は実験前のメトリクス値を使用して分散を低減します。エクスポージャー前は、実験は A/A テストのように動作するはずです。つまり、割り当て前に発生した行動に処理が影響を与えることはありません。検出された不均衡は偶然発生する場合もあれば、その根本原因が処理と相関のある選択、データ漏洩、またはランダム化の問題を示している場合もあります。それらの根本的な問題は、CUPED の前提条件に違反したり、CUPED 調整以上の無効化を招いたりする可能性があります。

Datadog は、実験前のコンポーネント平均における「処理群 - 対照群」の差について、両側逐次正規混合信頼シーケンスを計算します。単純メトリクスはメトリクスの平均をテストし、比率メトリクスは分子と分母の平均を個別にテストし、パーセンタイルメトリクスは内部の S および N コンポーネントをテストします。Datadog は `0.05` のファミリー有意水準 (アルファ) から開始し、対象となるメトリクス、処理バリアント、およびコンポーネントのチェック全体に多重比較補正を適用します。調整された信頼区間がゼロを厳密に除外する場合、診断は失敗となります。ゼロに触れる区間は合格です。データが蓄積されるにつれて分析が繰り返されても、信頼区間は有効なままです。このテストには正の分散を持つ観測値が必要ですが、明示的な最小サンプルサイズはありません。

### 一般的な原因 {#common-causes-2}

- 処理依存のアイデンティティのつながり。たとえば、ある実験では匿名 ID を無作為に割り当てる一方で、アカウント単位の購入履歴を分析しており、匿名 ID とアカウントの対応付けはログイン後にのみ作成されます。エクスポージャー後のログインによって、それ以前の購入履歴が遡及的に含まれたり再キー化されたりする場合、ログインを増加させる処理によって、実験前の履歴がより多く処理群に出現する可能性があります。
- タイムスタンプの切り捨て、または時間粒度の不一致。たとえば、エクスポージャーにはイベントのタイムスタンプがあるものの、メトリクスデータが日単位で集計され、深夜 0 時として表現されている場合、その日のエクスポージャー後のイベントがエクスポージャーより前に発生したように見えてしまいます。
- 後のイベントを前のタイムスタンプで保存または比較してしまう、一貫性のないタイムゾーンや夏時間の扱い。
- 処理前の結果や以前の処理と相関関係にある割り当てルール。たとえば、識別子の範囲から直接バリアントを割り当てたり、実験間で同じバケットマッピングを再利用したりすると、割り当てと以前の実験のエクスポージャーとの間に相関関係が残ってしまう可能性があります。
- 実験前のデータの可用性がバリアント間で異なる原因となる、ランダム化、ターゲティング、対象の識別、またはデータ処理の問題。

### 解決方法 {#how-to-resolve-6}

1. 実験前のデータが各バリアントで利用可能かつ代表的であることをチェックし、実験前の期間中にメトリクスの定義が変更されていないかをチェックしてください。
2. 生の割り当てタイムスタンプとメトリクスのタイムスタンプを、元の粒度および一貫したタイムゾーンで比較してください。日次集計、タイムスタンプ変換、または夏時間の切り替えによって、エクスポージャー後のイベントが実験前の期間に移動していないかをチェックしてください。
3. 対象の識別マッピングを監査してください。ログインなどの事後エクスポージャー時の行動によって、どの対象が分析可能な実験前の履歴を持っているかを特定できないようにしてください。
4. 割り当てが、前処理の結果、対象の属性、および以前の処理から独立していることを確認してください。Datadog Feature Flags を利用する実験では、SDK `targetingKey` を安定させてください。Datadog はフラグキーと `targetingKey` を使用して、対象を同じロールアウトバケットに維持します。ウェアハウスネイティブの実験では、対象の識別子と実験固有の salt またはキーを組み合わせた決定論的な割り当て方法を使用してください。これにより、実験間で同じ割り当てパターンを再利用することなく、対象を実験内の同じバリアントに維持できます。
5. ID、タイムスタンプ、ランダム化、またはデータ処理の問題を修正してから、分析を再実行してください。不均衡が選択の偏り、事後エクスポージャーデータの漏洩、またはランダム化の不備に起因する場合、CUPED を無効にしても実験は有効になりません。

## 不合理な事前分布 {#implausible-prior}

ベイズ分析において、Datadog は相対リフト値に対して、事前分布と予測値に基づく両側チェックを実施します。このチェックでは、事前分布の分散と推定値のサンプリング不確実性の両方を考慮します。Datadog は、事前予測分布において、実験で推定されたリフトと同等以上に極端なリフトがどちらかの方向に観測される確率が 1% 未満である場合に警告を発します。Datadog は、多重比較補正を行わずに、対象となる各メトリクスと処理の比較をテストします。このチェックでは正の有限の標準誤差が必要ですが、明示的な最小サンプルサイズはありません。警告は、観測された効果が選択された事前分布の下で予想外であることを示しています。

たとえば、多くのコンバージョン率の実験では真のリフトが 5% 未満であるため、平均 0、標準偏差 0.05 のデフォルトの正規事前分布は妥当な選択となり得ます。もし、実験によって、大多数のユーザーのコンバージョンを妨げている不具合のあるチェックアウトページが修正されれば、はるかに大きな成果が期待できるかもしれません。その場合、デフォルトの事前分布が過度に保守的となり、推定される効果が過小評価されてしまう可能性があります。

### 解決方法 {#how-to-resolve-7}

- 推定されたリフトを、そのメトリクスの過去の効果や、介入によって妥当に生じ得る効果と比較してください。
- 実験の統計分析計画と事前設定を見直してください。
- 推定されたリフトが妥当であるにもかかわらず、事前分布がその規模の効果に対して非常に低い確率を割り当てている場合は、関連するドメイン知識を反映するように事前分布を更新し、分析を再実行してください。

## セグメントレベルの劣化 {#segment-level-degradation}

Datadog は、セグメントの点推定値がメトリクスの望ましい変化と逆であり、そのセグメントが比較可能なセグメントよりも著しくパフォーマンスが低い場合に、警告を発します。増加が望ましいメトリクスの場合、セグメントリフトはゼロを下回る必要があります。減少が望ましいメトリクスの場合、セグメントリフトはゼロを上回る必要があります。

各メトリクス、処理バリアント、およびディメンションについて、Datadog は各セグメントリフトを、同じ組み合わせにおける有効なセグメントリフトの逆分散加重平均と比較します。セグメントが警告を発するのは、加重平均との差に対する逐次信頼区間が完全に悪い方向にある場合で、かつ点推定値が望ましい変化と逆である場合のみです。

Datadog は、`0.05` のファミリー有意水準 (アルファ) を、初期の要約統計量検証を通過したセグメント比較の数で割ることにより、ボンフェローニ補正を適用します。後のチェックでスキップされた比較は分母に残るため、しきい値はより保守的になります。このチェックには、同じメトリクス、処理バリアント、およびディメンションに対して、正の分散を持つセグメントが少なくとも 2 つ必要です。セグメントレベルの劣化は警告を生成しますが、診断の失敗ではありません。

### 解決方法 {#how-to-resolve-8}

- 国、プラン、デバイス、顧客層など、影響を受けるディメンションのセグメントレベルのチャートを確認してください。
- 影響を受けるセグメントが、実際の製品やインスツルメンテーションの問題に関連しているかどうかをチェックしてください。
- 影響の大きいセグメントを調査する間、影響を受けるセグメントのトラフィックを実験からそらすことを検討してください。

## 分析パイプラインの失敗 {#analysis-pipeline-failure}

実験分析では、Datadog の Product Analytics および RUM データ、またはウェアハウスネイティブモードを使用できます。**分析パイプラインの失敗** は、ウェアハウスメトリクスを使用する実験にのみ適用されます。Datadog は、顧客のウェアハウスクエリが失敗し、現在のウェアハウス結果を計算できない場合に、この診断を報告します。Datadog は、内部の Product Analytics や RUM 分析の失敗については、この診断で報告しません。

ユーザーが定義する SQL は、実験がどのようにランダム化されるかによって異なります。Datadog Feature Flags を利用する実験の場合、Datadog は割り当てを `g_exposures` テーブルに同期し、ユーザーは Metric SQL モデルを定義します。ウェアハウスネイティブの実験の場合、ユーザーは Exposure SQL モデルと Metric SQL モデルの両方を定義します。Datadog は、残りのパイプライン SQL を生成します。

### 解決方法 {#how-to-resolve-9}

1. 失敗した診断の [{{< ui >}}Ask Bits{{< /ui >}}][7] をクリックします。Bits は、パイプラインエラー、失敗したウェアハウスのクエリ、および実験用に構成された SQL モデルをレビューします。最も可能性の高い原因を特定し、具体的な修正案を提示します。
2. Datadog Feature Flags を利用する実験の場合、エクスポージャーが `g_exposures` に同期されていることを確認してから、失敗したクエリ、Metric SQL モデル、ウェアハウスのコネクションと権限、およびソーステーブルの可用性を確認してください。
3. ウェアハウスネイティブの実験については、失敗したクエリ、Exposure SQL モデル、Metric SQL モデル、ウェアハウスのコネクションと権限、およびソーステーブルの可用性を確認してください。
4. 修正を適用してから、実験分析を再実行してください。
5. 同じエラーが続く場合は、実験の URL とエラーの詳細を添えて [Datadog サポート][9] までお問い合わせください。
