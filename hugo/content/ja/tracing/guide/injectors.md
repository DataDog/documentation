## 概要{#overview}

インジェクターは、実行時にアプリケーションを自動的にインスツルメントする共有ライブラリです。[シングルステップインスツルメンテーション][1]を使用すると、インジェクターが環境構成とトレーサーの初期化を自動化するため、手動構成が不要になります。

## インジェクターのロード方法 {#how-the-injector-is-loaded}

### Linux {#linux}

Linux システムでは、インジェクターは `LD_PRELOAD` メカニズム (UNIX 系環境における動的リンク機能) を使用して、すべての動的リンクプロセスに自身をロードします。これには 2 つの方法があります。
- 明示的に `LD_PRELOAD` 環境変数を設定する方法。
- 暗黙的にシステム全体の `/etc/ld.so.preload` ファイルを変更する方法。

### Docker {#docker}

Docker 環境では、インジェクターは Linux ホストと同じ `LD_PRELOAD` メカニズムを使用して、実行時にアプリケーションプロセスにロードされます。これにより、アプリケーションの起動前にトレーシングロジックを初期化し、環境変数を変更できるようになります。

これを有効にするために、Datadog は Docker のデフォルトのコンテナランタイムを置き換えるカスタム `runc` シムを提供しています。このシムの目的は以下のとおりです。
1. 共有ライブラリ (インジェクター) をコンテナに注入します。
1. `LD_PRELOAD` 環境変数を設定し、インジェクターがコンテナ内のすべての動的リンクプロセスに確実にロードされるようにします。

### Kubernetes {#kubernetes}

Kubernetes 環境では、インジェクションは Datadog Admission Controller によって処理され、ミューテーティングアドミッション Webhook が使用されます。Pod がスケジュールされると、コントローラーは以下のとおり処理します。

1. 構成されたセレクター (名前空間、ラベル、特定の Pod プロパティなど) に基づいて、Pod をインスツルメントする必要があるかどうかを評価します。
1. Pod スペックを変更して、次の処理を行います。
   - init コンテナまたは Datadog CSI ドライバーを使用して、インジェクターと SDK を配信します。
   - 環境変数 (`LD_PRELOAD` など) を設定します。
   - 注入されたライブラリを永続化するためのボリュームをマウントします

デフォルトでは、SSI はクラスターに最適な配信方法を選択します。[インジェクションモード][2]を明示的に選択することもできます。

### Windows {#windows}

Windows では、インジェクターは DLL として配信されます。Datadog カーネルドライバーがインジェクター DLL をすべての新しいプロセスにロードし、DLL の `DllMain` 関数がアプリケーションのエントリーポイントの前に実行されます。ロード後、インジェクターは[インジェクターの動作](#injector-behavior)で説明されているのと同じフローに従います。Windows は Java と .NET のみをサポートしています。Windows でのランタイム検出は実装の点で Linux と異なりますが、結果として得られるインスツルメンテーションの動作は同じです。

## インジェクターの動作 {#injector-behavior}

インジェクターがプロセスのメモリ空間にロードされた後 (プラットフォームに関係なく)、以下の処理を行います。
- アプリケーションのランタイム (Python、Node.js、PHP、Java、.NET、Ruby、NGINX など) を検出します。
- プロセスをインスツルメントすべきかどうかを評価します。一部のプロセスはデフォルトで除外されます。また、[Linux][3]、[Kubernetes][4]、および [Windows][5] 上のワークロードごとに、インジェクションを許可または拒否するインスツルメンテーションルールを定義することもできます。
- 適切なトレーサー SDK をロードするために、環境変数またはコマンドライン引数を変更します。
- テレメトリを出力してステータスを報告し、デバッグを支援します。

インジェクションが失敗した場合や、サポートされているランタイムが検出されなかった場合、アプリケーションはインスツルメンテーションなしで実行を継続します。プロセスが構成によって除外されている場合も同様です。

**注**: インジェクターは SDK が環境変数を評価する前に実行されるため、`DD_TRACE_ENABLED=false` を設定しても SSI による SDK のロードを防ぐことはできません。SSI を無効化または削除するには、お使いのプラットフォームの[シングルステップ APM インスツルメンテーション][1]のセットアップページをご覧ください。

## インジェクターのライフサイクル {#injector-life-cycle}

インジェクターは、アプリケーションの `main` 関数が実行される前にその作業を完了します。これは、アプリケーションと並行して実行されるバックグラウンドプロセスやスレッドではありません。

インジェクターが必要な環境変数またはコマンドライン引数を設定した後、アプリケーションは通常どおり処理を継続します。その時点から、プロセス内に存在する Datadog コードは、アプリケーション自体がその構成を使用してロードするトレーサー SDK のみとなります。

## ランタイムごとのインスツルメンテーション {#per-runtime-instrumentation}

インジェクターは、アプリケーションプロセスの環境変数を設定するか、コマンドライン引数を変更することで、適切なトレーサー SDK をロードします。メカニズムはランタイムによって異なります。

| ランタイム  | メカニズム |
|----------|-----------|
| Java     | `JAVA_TOOL_OPTIONS` を `-javaagent:<path-to-dd-java-agent.jar>` に設定します。|
| Python   | `PYTHONPATH` をトレーサーのインストールディレクトリに設定します。|
| Node.js  | `NODE_OPTIONS` を `--require` (CommonJS) または `--import` (ECMAScript モジュール) に設定します。|
| Ruby     | `RUBYOPT` を `-r <path-to-Datadog-host-inject-script>` に設定します。|
| .NET     | .NET CLR プロファイラーの環境変数 (`CORECLR_ENABLE_PROFILING`、`CORECLR_PROFILER`、`CORECLR_PROFILER_PATH`、および関連する変数) を設定します。|
| PHP      | `PHP_INI_SCAN_DIR` を Datadog が提供するローダーディレクトリに設定します。|
| NGINX    | Datadog モジュールをロードするために、追加のコマンドライン引数を指定して NGINX バイナリを再実行します (例: `-g "load_module <path-to-Datadog-module>;"`)。|

## 権限とスコープ {#privileges-and-scope}

### インジェクションのスコープ {#injection-scope}

SSI は、ユーザー空間の動的リンク (Linux 上の `LD_PRELOAD` や Windows 上の DLL インジェクションなど) を使用して、トレーサーまたはプロファイラーをアプリケーションプロセスにロードすることで、アプリケーションをインスツルメントします。カーネルモジュールのインストール、カーネルへのパッチ適用、システムコールのフック、eBPF の使用は行いません。インジェクターとトレーサーまたはプロファイラーは、アプリケーションプロセスと同じ OS 権限で実行されます。[ランタイム権限](#runtime-privileges)を参照してください。

インジェクションされたコードはアプリケーションプロセス内で実行されますが、一部のデプロイメントモードでは、インジェクターが自動的にロードされるように OS またはランタイム構成を更新します。

- **Kubernetes アドミッションコントローラーインジェクション**: Pod スペックを変更してインジェクターをマウントし (init コンテナまたは [Datadog CSI ドライバー][2]を使用)、環境変数を設定します。これは Kubernetes API のアクションであり、ホスト OS の変更ではありません。
- **Linux ホストインジェクション**: 動的ローダー (通常は `/etc/ld.so.preload` を介して) を構成し、新しい動的リンクプロセスがすべてインジェクションランチャーをロードするようにします。これは OS レベルの構成変更ですが、カーネルコードではなく、ユーザー空間の動的リンクのままです。
- **Docker ランタイムインジェクション**: Docker がラッパーランタイムを使用するように構成し、トレーサーがマウントおよび構成された状態でコンテナが起動するようにします (通常は `LD_PRELOAD` 環境変数をコンテナに注入することによって行われます)。これは Docker デーモンの構成を変更します。
- **Windows インジェクション**: 新しいプロセスにインジェクター DLL をロードするカーネルドライバーをインストールします。このドライバーは OS レベルで動作します。各アプリケーションプロセス内で実行される注入されたコードは、ユーザー空間で動作します。

### ランタイム権限 {#runtime-privileges}

インジェクター、トレーサー、プロファイラーはすべてアプリケーションプロセス内で実行され、そのプロセスと同じ OS 権限を継承します。これらが追加の権限を取得することはありません。アプリケーションが制限されたユーザーとして実行される場合、インジェクター、トレーサー、プロファイラーもそのユーザーの権限に制限されます。

### インストール権限 {#installation-privileges}

インストール時の権限要件は、デプロイメントモードによって異なります。

#### Kubernetes アドミッションコントローラー {#kubernetes-admission-controller}

- **クラスター側のコンポーネント** (Datadog Cluster Agent およびアドミッションコントローラー) は、通常、Webhook を登録し Pod を変更するためにクラスターレベルの権限を必要とします。
- **アプリケーション Pod** は Datadog による特権昇格を必要としませんが、セキュリティを強化したクラスターでは以下の許可が必要になる場合があります。
  - Agent との通信に使用されるボリュームマウント (通常はソケットディレクトリへの `hostPath` マウント)。
  - 特定の `SecurityContext` または SCC の許可。

  ポリシーで必要なマウントが許可されている限り、注入された init コンテナとアプリケーションコンテナを制限された状態 (非 root、ケーパビリティの削除、特権昇格なし) に維持できます。

#### Linux ホスト {#linux-host}

- パッケージのインストールや、システム全体のローダー構成およびサービス構成の変更が行われるため、インストールには通常 root (または同等の権限) が必要です。
- インストール後、Datadog Agent サービスは専用のサービスユーザー (通常は `dd-agent`) として実行され、注入されたコードはアプリケーションユーザーの権限で実行されます。

#### ホスト上の Docker ランタイム {#docker-runtime-on-a-host}

- インストールと構成には通常 root が必要です。Docker デーモンの構成を変更するためです。
- 実行時、インジェクターとトレーサーは、そのコンテナのユーザーとしてコンテナのアプリケーションプロセス内で実行されます。

#### Windows {#windows-1}

- Windows への Datadog Agent のインストールには、管理者特権 (サービスインストールおよびシステム全体の構成) が必要です。
- アプリケーションのインスツルメンテーション (例: .NET) の場合、プロファイラーは対象プロセスのコンテキストで実行されます。システム全体の構成変更によりプロセスやサービスでプロファイラーが有効になりますが、プロファイラーに追加の特権が付与されることはありません。
