## 概要{#overview}

以下の 4 つの実装テンプレートは、使用されているメカニズム、ロールとチームの構造、レイヤーがどのように連携するかなどを含め、完全に実装されたアクセス戦略がどのようなものかを示しています。これらは一般的な組織の典型例を表しており、特定の企業を指すものではありません。独自の実装を開始するための出発点として使用してください。

## テンプレートを選択する{#choose-your-template}

どのパターンが最も関連性が高いかを特定するために、以下の質問を使用します。

| 質問 | はいの場合に参照する場所|
| :---- | :---- |
| **特定のユーザーグループから不可視にする必要がある規制対象データはありますか** | [テンプレート 1 (金融)](#template-1-large-financial-institution)<br>[テンプレート 2 (規制対象のマルチ BU)](#template-2-regulated-enterprise-with-multiple-business-units) |
| **部門間で完全なデータ分離を必要とする厳格なコンプライアンス境界はありますか** | [テンプレート 2 (規制対象のマルチ BU)](#template-2-regulated-enterprise-with-multiple-business-units) |
| **API キーのボリュームが多く、自動化パイプラインが多数ありますか** | [テンプレート 3 (大手テクノロジー企業)](#template-3-large-technology-company) |
| **共有プラットフォーム上で複数の内部テナントまたはクライアントにサービスを提供しますか** | [テンプレート 4 (プラットフォームプロバイダー)](#template-4-government-agency--platform-provider) |
| **Terraform や同様の IaC ツールを使用して構成を管理しますか** | [テンプレート 4 (プラットフォームプロバイダー)](#template-4-government-agency--platform-provider) |
| **多くの組織を運営しており、それら全体で一貫したアクセス制御が必要ですか** | [テンプレート 4 (プラットフォームプロバイダー)](#template-4-government-agency--platform-provider) |

## テンプレート 1: 大手金融機関{#template-1-large-financial-institution}

### プロフィール{#profile}

リテールバンキング、投資銀行、資産管理、保険部門全体で 15,000 人の Datadog ユーザーを抱えるグローバル金融サービス企業。ビジネスラインにマッピングされた 150 のチームがある単一の Datadog 組織で運用。SOC 2、PCI DSS、および複数の国の金融規制の対象。ID 管理には Okta を使用し、SCIM プロビジョニングを行います。

### アクセス戦略{#access-strategy}

| レイヤー | 実装 |
| :---- | :---- |
| **組織構造** | 部門間のデータ分離のためにData Access Controlを備えた単一組織。部門横断的なインシデント調査能力は維持されます。|
| **カスタムロール** | 5 つのロール: 読み取り専用 (監査人およびコンプライアンス担当者)、標準ユーザー (ほとんどのエンジニア)、プラットフォーム管理者、制限付きユーザー (契約社員)、およびトレーディングフロア (規制データに対する高度なログアクセス権)。自動更新は、標準ロールテンプレートに従うように構成されています。|
| **ID** | Okta からの SCIM。各部門には、Datadog チームにマッピングされた独自の Okta グループがあります。ロールの割り当ては Okta グループのメンバーシップに基づいており、コンプライアンス主導で四半期ごとにアクセスレビューが行われます。|
| **データ制限** | トレーディングデータ (`data_sensitivity:trading`) の Data Access Control データセットは、トレーディングチームとコンプライアンスチームに制限されます。PII タグが付与されたデータ (`data_sensitivity:pii`) 用の別個のデータセットは、プライバシーチームに制限されます。制限付きデータセットに含まれないデータは、**無制限** (デフォルト) です。|
| **資産保護** | 本番環境のすべてのモニターおよび運用ダッシュボードの編集アクセスは、所有しているチームに限定されます。「プラットフォームガバナンス」チームには、すべての資産に対して上書き編集アクセス権があります。|
| **キーとトークン** | 各 CI/CD パイプライン用のサービスアカウント。特定の API エンドポイントにスコープ設定されたアプリケーションキー。チームごとの API キー。アプリケーションキーの 90 日のローテーションサイクル。Terraform を通じて強制されます。|
| **監査** | ロールの変更、キーの作成、および Data Access Control ポリシーの変更に関するアラートを備えた Audit Trail が有効です。規制当局向けに四半期ごとのアクセスレビューレポートが生成されます。|

### 重要なポイント{#key-takeaway}

Data Access Control により、この組織は部門間の厳格なデータ境界を保ちながら、接続された監視可能性を持つ単一組織を維持できます。重要な成功要因は、取り込み時の整合性のあるタグ付けです。信頼性の高い `data_sensitivity` タグがなければ、Data Access Control は境界を強制できません。

## テンプレート 2: 複数のビジネスユニットを持つ規制対象企業 {#template-2-regulated-enterprise-with-multiple-business-units}

### プロフィール{#profile-1}

航空宇宙・防衛、民生用電子機器、ヘルスケア、輸送、エネルギーの 5 つの主要部門にまたがる 8,000 人の Datadog ユーザーを抱える多国籍コングロマリット。各部門には独自のコンプライアンス体制 (防衛向けの ITAR、ヘルスケア向けの HIPAA、エネルギー向けの SOX) があります。親組織の下に編成された 12 の Datadog 組織全体で運用されています。SAML マッピングと補足的な SCIM を備えた Entra ID (Azure AD) を使用しています。

### アクセス戦略{#access-strategy-1}

| レイヤー | 実装 |
| :---- | :---- |
| **組織構造** | 12 の子組織。防衛部門はメタデータも完全なデータ分離を必要とするため、別の組織を設けることが正当化されます。その他の部門は、地域およびビジネス機能ごとに組織を共有しています。親組織は、Cross-Org Visibility を通じた一元的な請求およびエグゼクティブダッシュボードに使用されます。|
| **カスタムロール** | 各子組織には、それぞれのコンプライアンス要件に合わせて調整された 4〜5 個のカスタムロールがあります。防衛組織は、エンジニアリング以外のスタッフからすべての書き込み権限を剥奪する最小限のカスタムロールを使用しています。ヘルスケア組織には、PHI タグが付けられたデータにアクセスできる専用の HIPAA アナリストロールがあります。|
| **ID** | Entra ID からの SAML を使用し、部門ごとの条件付きアクセス ポリシーが適用されます。防衛部門は、MFA および管理対象デバイス認証が必要です。SCIM によるチームのメンバーシップ管理。|
| **データ制限** | 防衛組織は、制限付きデータセットに含まれないデータに対しても**制限付き**の設定を使用します。すべてのデータはデフォルトで非表示になっており、ユーザーには特定のデータセットへのアクセス権が明示的に付与されます。ヘルスケア組織は、デフォルトの**無制限**設定と、PHI タグ付きテレメトリ用の制限付きデータセットで Data Access Control を使用します。商業部門は、サービスベースのデータ分離のために、デフォルトの**無制限**設定の Data Access Control を使用します。|
| **資産保護** | 各組織は独自の資産アクセスポリシーを管理します。防衛およびヘルスケア組織の本番環境モニターで編集アクセス権が付与されるのは、所有チームと部門のセキュリティチームに限定されています。|
| **Cross-org** | 親組織は、Cross-Org Visibilityを有効にして、すべての部門にわたるシステム健全性を示すエグゼクティブダッシュボードを運用しています。子組織全体でポリシーを一元化するための組織グループ (プレビュー)。|
| **キーとトークン** | すべてのキーは Terraform を通じて管理されます。防衛組織は、キーやロールの変更に対して承認ゲートを備えた堅牢な Terraform パイプラインを使用しています。サービスアカウントのみが使用されます。人間が所有するアプリケーションキーはありません。|

### 重要なポイント{#key-takeaway-1}

ここでのマルチ組織は、厳格なコンプライアンス境界のために正当化されます。規制により、厳格なデータ分離とデータレジデンシーの要件が課されます。防衛部門による**制限付き**設定の使用は、その規制環境におけるデフォルト拒否要件を反映しています。Cross-Org Visibility により、分離を損なうことなく一元化されたレポート機能が維持されます。

## テンプレート3: 大手テクノロジー企業{#template-3-large-technology-company}

### プロフィール{#profile-2}

12,000 人の Datadog ユーザーを抱え、大規模な決済処理およびコマースプラットフォームを運用するグローバルテクノロジー企業。20 の主要な製品ラインを表す単一の組織を運用しています。Teams API および Terraform と統合された独自の ID システムを使用しています。500 以上の有効なアプリケーションキーと 200 のサービスアカウントを使用しており、API が多用されています。

### アクセス戦略{#access-strategy-2}

| レイヤー | 実装 |
| :---- | :---- |
| **組織構造** | 20 の主要な製品ラインを表す単一の組織です。Data Access Control と Teams により、各組織内に内部境界が提供されています。サンドボックスおよび非本番環境用に 2 つの追加組織を使用しています。|
| **カスタムロール** | Terraform モジュールを通じて全社で標準化された 5 つのカスタムロール (読み取り専用、標準、プラットフォーム、組織管理者、契約社員) です。契約社員以外のロールに対して自動更新が有効になっています。|
| **ID** | Teams API および Terraform と統合された独自の IdP です。チームメンバーシップは、社内のサービスオーナーシップレジストリから毎晩同期されます。ロールの割り当ては、中央の従業員ディレクトリから読み取る Terraform モジュールを通じて管理されています。|
| **データ制限** | 機密性の高いキーテレメトリタイプ (ログ、RUM、クラウドコスト) において製品ラインを分離する標準 Data Access Control が提供されています。サービスに基づいて制限付きデータセットが作成され、明示的なデータセット割り当てを通じてチーム間のアクセスが許可されます。契約社員のユーザーは、契約スコープ内で定義された限定的なサービスセットのみにアクセスが制限されます。|
| **資産保護** | すべての本番環境モニターは、所有するチームに制限されています。ダッシュボードは広く閲覧可能ですが、編集は制限されています。「プラットフォーム SRE」チームは、インシデント対応のためのオーバーライドアクセス権を有しています。|
| **キーとトークン** | チームごとに 1 つの API キーが割り当てられています。すべての自動化のためのサービスアカウントがあります。アプリケーションキーが特定の API 操作にスコープ設定されます。未使用のキーを特定して取り消すための四半期ごとの監査が行われます。|

### 重要なポイント{#key-takeaway-2}

チームごとの API キーと四半期ごとの監査は、この規模でガバナンスを管理するために不可欠です。Data Access Control、Teams、およびきめ細かなアクセス権が、組織内の境界を提供しています。

## テンプレート4: 政府機関 / プラットフォームプロバイダー {#template-4-government-agency-platform-provider}

### プロフィール{#profile-3}

5,000 人の Datadog ユーザーを抱え、約 200 の内部機関、部門、またはクライアントテナント向けに共有オブザーバビリティプラットフォームを運用する大規模な政府機関またはマネージドサービスプロバイダーです。環境 (本番、ステージング、開発) ごとにセグメント化された 3 つの Datadog 組織を運用していますが、各組織には相互に分離する必要がある多数の異なるテナントのデータが含まれています。ServiceNow CMDB を通じて統合された Entra ID を使用し、すべての構成を Terraform で管理します。

### アクセス戦略{#access-strategy-3}

| レイヤー | 実装 |
| :---- | :---- |
| **組織構造** | テナントごとではなく、環境ごとに 3 つの組織です。Teams と Data Access Control による組織内セグメンテーションが、テナントの分離を実現しています。これにより、200 以上の個別の組織を管理するオーバーヘッドを回避しつつ、厳格な境界を維持できます。|
| **カスタムロール** | 5 つのロール: 読み取り専用 (監査担当者)、標準ユーザー、プラットフォーム管理者、組織管理者、制限付きオブザーバー (単一テナントのデータへの限定的な可視性が必要な関係者向け) です。プラットフォーム管理者ロールには、チームベースのアセット制限をバイパスするオーバーライドが含まれています。|
| **ID** | 複雑な ID チェーン: Entra ID がユーザーグループを ServiceNow CMDB に同期します。CMDB レコードによって、ユーザーの Datadog 組織、チーム、およびロールが決定されます。変更は ServiceNow の承認ワークフローを経てから、Terraform を使用して Datadog に適用されます。SAML 属性マッピングにより、初期ログインのプロビジョニングが行われます。|
| **データ制限** | テナント機関ごとのデータセットを用いた標準 Data Access Control が、`agency` タグによって定義されています。各機関のチームは、自機関のデータにのみアクセスできます。プラットフォームチームは、キャパシティプランニングとインシデント対応のために、すべてのテナントのインフラストラクチャーレベルのデータにアクセスできます。|
| **資産保護** | 各機関のモニターとダッシュボードの編集アクセスはそれぞれのチームに制限されます。重要な共有インフラストラクチャーモニター (ネットワーク、DNS、共有コンピューティング) は、プラットフォームチームに制限されます。ロックアウトを防ぐため、管理者オーバーライドチーム (「プラットフォームガバナンス」) がすべての資産アクセスリストに含まれています。|
| **キーとトークン** | すべての API キーとサービスアカウントは、ServiceNow の承認ゲートを備えた Terraform を通じて管理されます。データ送信のために、各機関につき 1 つの API キーが割り当てられます。共有自動化パイプライン用のサービスアカウントがあります。人間用のアプリケーションキーは許可されません。すべての API アクセスは、SAT を使用するサービスアカウントを経由します。|
| **コードとしての管理** | すべてのロール、チーム、Data Access Control データセット、きめ細かなアクセス権ポリシー、およびキーは Terraform で定義されています。変更は、適用される前にコードレビューと ServiceNow の承認プロセスを経ます。この規模では不可欠であり、200 以上のテナント境界にわたる手動設定では維持できません。|

### 重要なポイント{#key-takeaway-3}

テナントの境界が規制上ではなく組織上の理由である場合、組織内セグメンテーション (Teams と Data Access Control) でマルチ組織分離を代替できます。この規模では、CMDB 主導の ID チェーンと Terraform で管理される構成が必要です。管理者オーバーライドチームは、資産制限を適用する前に確立しておくべき重要なセーフティネットです。
