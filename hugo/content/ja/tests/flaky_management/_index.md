## 概要 {#overview}

[Flaky Tests Management][1] ページでは、組織全体の不安定なテストを追跡、トリアージ、修正するため、一元化された方法でテストを表示する機能を提供しています。パイプラインの失敗数、無駄になった CI 時間、失敗率などの主要なメトリクスとともに、すべてのテストの状態を表示できます。

この UI から、不安定なテストに対してアクションを実行し、その影響を軽減できます。問題のあるテストを隔離または無効にして、既知の不安定なテストがビルドを中断しないようにし、修正に向けた作業を追跡するためのワークアイテムや Jira の問題を作成します。

各不安定なテストには、リポジトリ ID とテストの完全修飾名のハッシュから導出された、安定した一意の識別子があります。Test Optimization Explorer では、これは `@test.fingerprint_fqn` ファセットです。[不安定なテストの管理 API][18] では、これはテストの `id` であり、`fingerprint_fqn` キーを使用して不安定なテストを検索するエンドポイントをフィルタリングできます。この識別子を使用して、API 経由で特定のテストを検索または更新します。

## 不安定なテストの状態を変更する {#change-a-flaky-tests-state}

状態のドロップダウンを使用して、CI パイプラインで不安定なテストをどのように処理するかを変更します。これにより、トレーサビリティとコントロールを維持しながら、CI のノイズを削減できます。利用可能な状態は以下のとおりです。

| 状態     | 説明 |
| ----------- | ----------- |
| {{< ui >}}Active{{< /ui >}} | テストが不安定であることが判明しており、CI で実行されています。|
| {{< ui >}}Quarantined{{< /ui >}} | テストをバックグラウンドで実行し続けますが、失敗しても CI ステータスに影響を与えたりパイプラインを中断させたりすることはありません。これは、マージをブロックせずに不安定なテストを分離する上で役立ちます。Datadog は、隔離されたテスト実行イベントに `@test.test_management.is_quarantined:true` というタグを付けます。|
| {{< ui >}}Disabled{{< /ui >}} | CI でのテストを完全にスキップします。テストが関連性を失った場合やパイプラインから一時的に削除する必要がある場合に使用します。Datadog は、無効化されたテスト実行イベントに `@test.test_management.is_disabled:true` というタグを付けます。無効化されたテストは、{{< ui >}}Fixed{{< /ui >}}への自動的な移動から除外されます。|
| {{< ui >}}Fixed{{< /ui >}} | テストは一貫して合格しており、不安定ではなくなりました。サポートされている場合は、[修復フロー](#confirm-fixes-for-flaky-tests)を使用して修正を確認し、デフォルトブランチにマージされた後にこの状態を自動的に適用します。|

<div class="alert alert-info">状態アクションには、各プログラミング言語のインスツルメンテーションライブラリに対する最小バージョン要件があります。詳細については、<a href="#compatibility">互換性</a>を参照してください。</div>

## ポリシーを構成して、不安定なテストのライフサイクルを自動化する {#configure-policies-to-automate-the-flaky-test-lifecycle}

各リポジトリで不安定なテストをどのように処理するかを管理するために、自動化された不安定なテストポリシーを構成します。たとえば、デフォルトブランチで不安定なテストを自動的に隔離し、30 日経過しても修正されない場合は後で無効にすることができます。

1. Flaky Management ページの右上にある {{< ui >}}Policy Settings{{< /ui >}} ボタンをクリックします。[{{< ui >}}CI/CD Optimization{{< /ui >}} > {{< ui >}}Settings{{< /ui >}} > {{< ui >}}Repositories{{< /ui >}}][13] を開き、{{< ui >}}Flaky Test Policies{{< /ui >}} の行をクリックして組織のデフォルトポリシーを設定したりリポジトリごとに上書きしたりすることもできます。
2. 構成するリポジトリを検索して選択します。これにより、{{< ui >}}Flaky Test Policies{{< /ui >}} サイドパネルが開きます。

## 不安定なテストの推移を追跡する {#track-evolution-of-flaky-tests}

`test_optimization.test_management.flaky_tests` の標準メトリクスを使用して、不安定なテスト数の推移を追跡します。このメトリクスには以下のタグが付与されており、詳細なカウントの調査に役立ちます。

- `repository_id`
- `test_service`
- `branch`
- `flaky_status`
- `test_codeowners`
- `flaky_category`

`branch` タグは、過去 30 日間にリポジトリのデフォルトブランチでテストが不安定になった場合にのみ存在します。これにより、機能ブランチでのみ不安定さを示したテストを除外できます。これらは関連性がない可能性があるためです。リポジトリのデフォルトブランチは、[リポジトリ設定][2]で構成できます。

## 不安定なテストを調査する {#investigate-a-flaky-test}

特定の不安定なテストに関する詳細については、各行の末尾にあるアクションメニューの以下のオプションを使用します。

- {{< ui >}}View Last Failed Test Run{{< /ui >}}: 最新の失敗したテスト実行の詳細を含むサイドパネルを開きます。
- {{< ui >}}View related test executions{{< /ui >}}: 最近のすべてのテスト実行が入力された [Test Optimization エクスプローラー][3]を開きます。

## 不安定なテストのワークアイテムを作成する {#create-work-items-for-flaky-tests}

不安定なテストについては、ワークアイテムを作成し、[Work Management][4] を使用して修復に向けた作業を追跡できます。{{< ui >}}Create Work Item{{< /ui >}} ボタンをクリックするか、行の末尾にあるアクションメニューを使用してください。

## 不安定なテストの修正を確認する {#confirm-fixes-for-flaky-tests}

不安定なテストを修正すると、Test Optimization の修復フローにより、テストを複数回リトライすることで修正を確認できます。修復フローを有効にするには、以下を実行します。

1. 修正しているテストについて、不安定なテスト管理 UI で {{< ui >}}Link commit to Flaky Test fix{{< /ui >}} をクリックします。
1. 表示された一意の不安定なテストキーをコピーします (例: `DD_ABC123`)。
1. 修正の Git コミットタイトルまたはメッセージにテストキーを含めます (例: `git commit -m "DD_ABC123"`)。
1. Datadog がテストキーを検出すると、そのテストの修復フローが自動的にトリガーされます。キーは最新のコミットに含まれている必要はありません。Datadog は直近の先行コミットもチェックするため、複数のコミットをまとめてプッシュした場合や、CI プロバイダーが最新のコミットのみを報告した場合でも、フローはトリガーされます。修復フローは以下のとおりです。
    - 修正しようとしているテストを 20 回 (または[不安定なテストポリシーの設定](#configure-policies-to-automate-the-flaky-test-lifecycle)で指定した再試行回数) 再試行します。
      - テスト実行イベント内のすべての再試行に `@test.test_management.is_attempt_to_fix:true` をタグ付けします。
    - テストが `Disabled` とマークされている場合でも実行します。
    - すべての再試行が成功した場合、不安定なテスト管理 UI で修正を {{< ui >}}in progress{{< /ui >}} とマークし、修正に使用されたブランチに関連付け、そのブランチがマージされるのを待ちます。
      - テスト実行イベント内の最後の再試行に `@test.test_management.attempt_to_fix_passed:true` をタグ付けします。
      - 14 日間の[猶予期間](#grace-period-mechanism)を開始し、修正がリポジトリ全体に反映されるまでの時間を確保します。
    - 再試行が 1 回でも失敗した場合、テストの現在の状態 (`Active`、`Quarantined`、または`Disabled`) を維持します。
      - テスト実行イベント内の最後の再試行に `@test.test_management.attempt_to_fix_passed:false` をタグ付けします。

<div class="alert alert-danger">Cypress の場合、この修復フローでは<a href="https://docs.cypress.io/app/core-concepts/test-isolation">テストの分離</a>が有効になっている必要があります。修正の試行による再試行は <code>testIsolation: false</code>により実行されません。<a href="/tests/setup/javascript/?tab=cypress#retries-require-cypress-test-isolation">再試行には Cypress テスト分離が必要</a>も参照してください。</div>

### 進行中の修正を追跡する {#track-fixes-that-are-in-progress}

正常な修正実行後、不安定なテストの管理は修正を含むブランチを追跡し、修正がリポジトリのデフォルトブランチに到達するまで {{< ui >}}Fix in progress{{< /ui >}} インジケーターを表示します。関連するプルリクエストがマージされると、テストは自動的に `Fixed` に移動し、インジケーターが削除されます。修正がデフォルトブランチに直接プッシュされた場合、テストは直ちに `Fixed` とマークされます。

要件と制限:
- Datadog がプルリクエストのマージ Webhook を受信できるように、サポートされている SCM プロバイダー (GitHub、GitLab、または Azure DevOps) に対してソースコードインテグレーションを構成する必要があります。[ソースコードインテグレーションのセットアップ][17]を参照してください。
- 修正実行後に機能ブランチの名前を変更または削除すると、Datadog はマージを検出できなくなります。
- 3 か月以上前の修正を含むブランチは監視が停止されます。追跡を更新するにはフローを再実行してください。
- SCM プロバイダーがサポートされていない場合、またはソースコードインテグレーションがセットアップされていない場合、Datadog はマージを自動的に検出できません。修正がデプロイされた後、手動でテストを `Fixed` に移行してください。

### 猶予期間メカニズム {#grace-period-mechanism}

不安定なテストを修正した後、その修正がすべてのブランチに反映されるまで時間がかかることがあり、古いブランチでテストが不安定なままになる可能性があります。猶予期間メカニズムは、修正が適用された後に古いブランチで不安定なテストが表示されるのを防ぎます。

[修正フロー](#confirm-fixes-for-flaky-tests)を使用した後に修正が成功したすべての不安定なテストには 14 日間の猶予期間が適用されます。この期間中、Datadog は猶予期間開始前のステータスに基づいてテストを扱います。
- テストが {{< ui >}}Active{{< /ui >}} または {{< ui >}}Quarantined{{< /ui >}} だった場合、Datadog はそのテストを {{< ui >}}Quarantined{{< /ui >}} として扱います。
- テストが {{< ui >}}Disabled{{< /ui >}} だった場合、Datadog はそのテストを {{< ui >}}Disabled{{< /ui >}} として扱います。

このメソッドにより、不要な CI の失敗が回避され、開発者の時間が節約されます。

## Bits AI を活用した不安定なテストの修正 {#bits-ai-powered-flaky-test-fixes}

Test Optimization が不安定なテストを検出すると、[Bits Code][16] が自動的に診断および修正できます。Bits Code はテストの失敗パターンを分析し、本番環境で使用可能なコード変更を生成します。その後、Bits Code の提案から直接 GitHub プルリクエストを作成できます。

Bits Code が修正を作成するには、不安定なテストが以下の基準を満たしている必要があります。
- **失敗率**: 5% 以上
- **無駄な時間**: 2 時間以上
- **失敗したパイプライン**: 2 パイプライン以上
- **ブランチ**: デフォルトブランチで不安定な動作が発生している必要があります
- **失敗した実行**: `@error.message` と `@test.source.file` の両方のタグを含む失敗したテスト実行が少なくとも 1 回なければなりません

{{< img src="tests/bits_ai_flaky_test_fixes-2.png" alt="不安定なテストに対する修正案が表示されている Bits Code" style="width:100%;" >}}

### セットアップ {#setup}

Bits Code が Test Optimization のために不安定なテストの修正を提案できるようにするには、[Bits Code に関するドキュメント][16]のセットアップ手順に従って Test Optimization で Bits Code を有効にしてください。Bits Code は、Test Optimization によって検出された不安定なテストの修正を自動的に作成します。

Bits Code を有効にした後、不安定なテストを表示する際に {{< ui >}}Generate fix{{< /ui >}} をクリックしてください。

## AI を活用した不安定なテストの分類 {#ai-powered-flaky-test-categorization}

不安定なテストの管理は AI を使用して、実行パターンとエラー信号に基づき、各不安定なテストに根本原因のカテゴリーを自動的に割り当てます。これにより、不安定なテストのより効果的なフィルタリング、トリアージ、優先順位付けができるようになります。

<div class="alert alert-info">テストには、少なくとも 1 回の失敗したテスト実行が含まれている必要があり、分類の対象となる <code>@error.message</code> と <code>@error.stack</code> のタグが両方含まれている必要があります。テストが最近検出された場合、カテゴリーの分類が完了するまでに数分かかることがあります。</div>

### カテゴリー {#categories}

| カテゴリー                | 説明 |
|-------------------------|-------------|
| {{< ui >}}Concurrency{{< /ui >}}         | 安全でない、または予期しない方法で相互作用する複数のスレッドを呼び出すテスト。不安定さは、たとえば実行順序に関する暗黙的な前提から生じる競合状態などが原因で発生し、特定のテスト実行においてデッドロックにつながります。|
| {{< ui >}}Randomness{{< /ui >}}          | ランダムデータジェネレーターの結果を使用するテスト。テストがすべての可能なケースを考慮していない場合、たとえばランダムデータジェネレーターの結果がゼロの場合にのみ、テストが断続的に失敗することがあります。|
| {{< ui >}}Floating Point{{< /ui >}}      | 浮動小数点演算の結果を使用するテスト。浮動小数点演算は、精度のオーバーフローやアンダーフロー、非結合的な加算などの影響を受ける可能性があり、適切に考慮されていない場合、一貫性のない結果 (アサーションで浮動小数点の計算結果を正確な実数値と比較するなど) が生じる可能性があります。|
| {{< ui >}}Unordered Collection{{< /ui >}}| 順序が保証されないコレクションオブジェクトに対して、特定の反復順序を想定しているテスト。順序は指定されていないため、固定順序を想定したテストは、さまざまな理由 (コレクションクラスの実装など) で不安定になる可能性があります。|
| {{< ui >}}Too Restrictive Range{{< /ui >}}| 有効な出力範囲の一部のみをアサーションで受け入れるテスト。処理されないコーナーケースで断続的に失敗します。|
| {{< ui >}}Timeout{{< /ui >}}             | 個々のテストレベルまたはスイートの一部として、時間制限が原因で失敗するテスト。これには、実行時間制限 (個々のテストやスイート全体など) を超過し、実行時間の変動によって断続的に失敗するテストが含まれます。|
| {{< ui >}}Order Dependency{{< /ui >}}    | 別のテストによって変更される共有値やリソースに依存するテスト。テスト実行順序を変更すると、それらの依存関係が壊れ、一貫性のない結果が生じる可能性があります。|
| {{< ui >}}Resource Leak{{< /ui >}}       | 外部リソースの処理が不適切なテスト (メモリの解放漏れなど)。そのリソースを再利用する後続のテストが不安定になる可能性があります。|
| {{< ui >}}Asynchronous Wait{{< /ui >}}   | 非同期呼び出しを行うか、要素の読み込み / レンダリングを待機し、完了を明示的に待機していないテスト (多くの場合、固定遅延を使用)。呼び出しやレンダリングに遅延以上の時間がかかると、テストは失敗します。|
| {{< ui >}}IO{{< /ui >}}                  | テストは、入出力の処理 (書き込み中にディスク容量が不足したときに失敗するなど) が原因で不安定になっています。|
| {{< ui >}}Network{{< /ui >}}             | テストはネットワークの可用性 (サーバーへのクエリなど) に依存しています。ネットワークが利用できない、または混雑している場合、テストは失敗する可能性があります。|
| {{< ui >}}Time{{< /ui >}}                | テストはシステム時間に依存しており、精度やタイムゾーンの不一致 (UTC 深夜 0 時を過ぎたときに失敗するなど) が原因で不安定になる可能性があります。|
| {{< ui >}}Environment Dependency{{< /ui >}} | テストは特定の OS、ライブラリのバージョン、またはハードウェアに依存しています。ある環境では合格しても別の環境では失敗する可能性があり、特にマシンが非決定的に変化するクラウド CI 環境ではその傾向が顕著です。|
| {{< ui >}}Unknown{{< /ui >}}             | テストは不明な理由で不安定になっています。|

## 通知を受け取る {#receive-notifications}

不安定なテストの変更を追跡するために通知を設定します。通知は次の場合に送信されます。
- リポジトリのデフォルトブランチで新しい不安定なテストが検出された場合。
- ユーザーまたはポリシーが不安定なテストの状態を変更した場合。
- 不安定なテストの修復フローが成功または失敗した場合。

通知はメールアドレスまたは Slack チャンネルに送信でき ([Datadog Slack インテグレーション][5]を参照)、テストコードの所有者に基づいてメッセージをルーティングできます。複数のコード所有者が指定されている場合、通知ルールが一致するには、不安定なテストが指定されたすべてのコード所有者に所有されている必要があります。コード所有者が指定されていない場合、選択されたすべての受信者にリポジトリ内のすべての不安定なテストの変更が通知されます。各リポジトリの通知は、CI/CD 最適化設定の[{{< ui >}}Flaky Test Policies{{< /ui >}}][13]サイドパネルから構成します。

通知はノイズを減らすために短期間にまとめて送信されます。週のダイジェストの概要は、コード所有者が構成されている通知ルールにのみ送信されます。

### 通知タイプ {#notification-types}

| 通知タイプ | 説明 |
|---|---|
| {{< ui >}}New flaky test detected{{< /ui >}} | リポジトリのデフォルトブランチで新しい不安定なテストが検出されています。|
| {{< ui >}}Test quarantined{{< /ui >}} | 自動化されたポリシールール (時間ベース、ブランチベース、または失敗率) によってテストが隔離されています。|
| {{< ui >}}Test disabled{{< /ui >}} | 自動化されたポリシールール (時間ベース、ブランチベース、または失敗率) によってテストが無効化されています。|
| {{< ui >}}Fix successful{{< /ui >}} | テストが修復フロー内のすべての再試行に合格し、「修正中」とマークされています。|
| {{< ui >}}Fix failed{{< /ui >}} | 修復フロー中にテストが失敗します。|
| {{< ui >}}Manual state change{{< /ui >}} | ユーザーが手動で不安定なテストの状態を変更します。|
| {{< ui >}}Weekly digest summary{{< /ui >}} | **ベータ版**: 毎週月曜日に送信される週次サマリー。不安定なテストの現在の状態と前週からの変更点を、リポジトリおよびコード所有者ごとにグループ化して報告します。コード所有者が設定されている通知ルールにのみ送信されます。ルールごとの通知設定からルール単位でオフにすることができます。|

## トラブルシューティング {#troubleshooting}

### 無効化された不安定なテストが自動的に Fixed に移動されない {#disabled-flaky-tests-are-not-automatically-moved-to-fixed}

Datadog は、テストが 30 日間不安定でなくなった後でも、{{< ui >}}Disabled{{< /ui >}} テストを自動的に {{< ui >}}Fixed{{< /ui >}} 状態に移動することはありません。無効化されたテストは CI でスキップされるため、Datadog はそのテスト実行データを受信できず、依然として不安定かどうかを確認できません。

無効化されたテストを修正するには、次のいずれかを行ってください。

- 修正を試みる[修復フロー](#confirm-fixes-for-flaky-tests)をトリガーします。これにより、テストが無効な間も再試行され、修正が確認されてマージされると {{< ui >}}Fixed{{< /ui >}} に移動されます。
- [状態ドロップダウン](#change-a-flaky-tests-state)を使用して、テストの状態を手動で {{< ui >}}Active{{< /ui >}} または {{< ui >}}Quarantined{{< /ui >}} に変更します。その後、テストが再度不安定にならない限り、次回の自動化実行時に Datadog が自動的にテストを {{< ui >}}Fixed{{< /ui >}} に移動します。

### Slack 通知が配信されない {#slack-notifications-are-not-delivered}

Slack 通知が配信されない場合は、通知ルールで `@slack-ACCOUNT-CHANNEL` 形式が使用されていることを確認してください。

`@slack-CHANNEL` (アカウント名なし) を使用している場合、通知は最初に設定された Slack アカウントにルーティングされます。複数の Slack ワークスペースを持つ組織の場合、これが意図したワークスペースではない可能性があります。

アカウント名を確認するには、[Slack インテグレーションタイル][5]に移動し、使用するワークスペースの
{{< ui >}}Account Name{{< /ui >}} フィールドをチェックします。

### 修正リンク後に修正を試みる修復がトリガーされない {#attempt-to-fix-remediation-does-not-trigger-after-linking-a-fix}

コミットにテストキー (例: `DD_ABC123`) を含めると、Datadog はテスト実行をトリガーしたコミットとその直前の最大 10 件のコミットをスキャンします。修復フローが開始されない場合は、以下をチェックしてください。

- **キーが古いコミットに含まれています。**Datadog は、トリガーとなったコミットとその履歴内の直近 10 件のコミットのみをスキャンします。一度に 10 件を超えるコミットをプッシュする場合は、トリガーとなるコミットまたは直近 10 件のコミットのいずれかにキーを含めてください。
- **修正がスカッシュマージされました。**スカッシュマージは元のコミットを 1 つのコミットに結合するため、Datadog はスカッシュコミットのメッセージのみを読み取ります。スカッシュ前の個々のコミットはスキャンされなくなります。ほとんどのプロバイダーはスカッシュコミットに元のコミットメッセージを含めるため、そのいずれかにキーが含まれていれば保持されます。プロバイダーがそれらを省略する場合は、スカッシュコミットのメッセージにキーを追加してください。
- **キーが期待される形式と一致しません。**不安定なテストの管理 UI に表示されている正確なキー (例: `DD_ABC123`) をコミットタイトルまたはメッセージに使用してください。
