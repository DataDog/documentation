## 概要 {#overview}

タグインデックスルールは、Datadog が取り込み時にメトリクスタグをどのように処理するかを定義する一元化された構成です。これにより、保持または除外するタグを事前に制御でき、不必要なタグを削除することで高いカーディナリティを軽減し、組織全体で一貫したタグ付けを確保することに役立ちます。

タグインデックスルールは、名前またはプレフィックスで識別されるメトリクスのグループに適用されます。定義されたパターンに一致する既存のメトリクスと新たに取り込まれたメトリクスの両方に適用され、リアクティブクリーンアップやコード変更の必要性を減らし、より予測可能なコスト管理を可能にします。

## タグルールを作成する {#create-a-tag-rule}

ルールを作成すると、Datadog は自動的にすべての一致するメトリクスに適用します。

1. [{{< ui >}}Metrics → Settings{{< /ui >}}][3] に移動します。
2. {{< ui >}}\+ Create Rule{{< /ui >}} をクリックします。
3. {{< ui >}}Configure Tag Indexing Rule{{< /ui >}} を選択します。

{{< img src="metrics/guide/tag_indexing_rules/configure_tag_indexing_rule.png" alt="メトリクス設定のルール作成ドロップダウンメニューで、タグインデックスルールを構成するオプションが強調表示されます。" style="width:50%;">}}

### ステップ 1: ルールの詳細を設定する {#step-1-set-rule-details}

ルール名を入力します。ルールの目的を明確に識別できる説明的な名前を使用します。

### ステップ 2: ルールスコープを定義する {#step-2-define-rule-scope}

ルールが適用されるメトリクスを選択します。次の 1 つ以上のオプションを使用してルールスコープを定義します。

メトリクス名またはプレフィックス
: 特定のメトリクス名またはネームスペースにルールを適用します (例: `http.*`、`db.query.*`)

プレフィックスの例外
: 特定のプレフィックスをルールスコープから除外します (例: `http.*` に適用しますが、`http.client.*` は除外します)

{{< img src="metrics/guide/tag_indexing_rules/define_rule_scope.png" alt="http.* にスコープされたルールを示すメトリクスの選択ステップで、http.client.* がサブ接頭辞として除外されます。" style="width:80%;">}}

複数のルールが同じメトリクスに適用される場合、Datadog はそれらを順番に評価します。オプションで {{< ui >}}Override{{< /ui >}} 動作を使用して、選択済みメトリクスの以前に評価されたルールを置き換えます。

### ステップ 3: タグの動作を構成する {#step-3-configure-tag-behavior}

ルールがスコープ内のメトリクスに対するタグをどのように処理するかを定義します。

#### 既存の構成をマージまたは上書きする {#merge-or-override-existing-configurations}

このルールを既存のタグ構成に基づくものにするか置き換えるかを選択します。
- {{< ui >}}Merge{{< /ui >}}(デフォルト) — 既存のタグ構成に追加でこのルールを適用します。以前に構成されていないメトリクスには影響しません。
- {{< ui >}}Override{{< /ui >}} — 同じプレフィックスに適用される他のすべてのルールを無視し、このルールのみを適用します。[{{< ui >}}Override all other rules that apply to these prefixes{{< /ui >}} オプションを選択して、この動作を有効にします。

**注**: より狭いルールで**上書き**の動作を使用して、より広いルールの除外されたタグが重複しないようにします。たとえば、ルール 1 が**マージ**の動作を使用して `dd.*` から `host`を除外し、ルール 2 が `dd.payments.*` から `app_name` を除外するとします。ルール 2 も**マージ**を使用する場合、`host` と `app_name` の両方が `dd.payments.*` メトリクスから削除されます。ルール 2 が**上書き**を使用する場合、`app_name` のみが削除されます (ルール 1 の効果はそのプレフィックスに対して上書きされます)。

#### 新しいメトリクスにのみ適用する {#apply-to-new-metrics-only}

このルールはルールが作成された後に送信されたメトリクスにのみ適用されます。ルールに一致する既存のメトリクスは変更されません。

#### 含めるまたは除外するタグを選択する {#select-tags-to-include-or-exclude}

タグフィルタリングに許可リストまたはブロックリストを使用するかどうかを選択します。
- {{< ui >}}Include tags{{< /ui >}} — クエリ可能なタグの許可リストを使用します。
- [{{< ui >}}Exclude tags{{< /ui >}} — ブロックリストを使用してクエリ不可能なタグを定義するか、タグの使用状況を使用して、過去 30、60、または 90 日間にクエリされておらず、ダッシュボードやその他のアセットで使用されていないタグのインデックスを自動的に解除します。

含めるまたは除外するタグキーを追加します。

{{< img src="metrics/guide/tag_indexing_rules/configure_tag_behavior.png" alt="タグを含めるオプションが選択され、タグキーが入力された、タグの選択ステップ。" style="width:80%;">}}

タグの動作を設定した後、影響を受けるメトリクスのリストがプレビューに表示されます (UI で最大 100 件)。

{{< img src="metrics/guide/tag_indexing_rules/preview_affected_metrics.png" alt="ルールスコープに一致するメトリクスのリストが表示された、影響を受けるメトリクスパネルのプレビュー。" style="width:80%;">}}

> デフォルトでは、新しいルールはすべて現在のルールセットの下部に追加されます。

### 制限事項 {#limitations}

- {{< ui >}}Exclude{{< /ui >}} ルールは、Datadog がメトリクス上のタグを観測した後に適用されます。
- Datadog はルールを順次評価し、各後続のルールを以前の構成に基づくものにするか置き換えます。
- **タグの経過時間**: タグの使用状況を使用するルールの場合、新しいタグには、ルールによって管理されるようになるまで 15 日間の猶予期間が設けられます。

## ルールを修正する {#modify-a-rule}

[{{< ui >}}Metrics → Settings → Rules{{< /ui >}}][1] に移動して、既存のルールを変更します。変更を加えると、Datadog は自動的にそれらをすべての一致するメトリクスに適用します。

### ルールを編集する {#edit-a-rule}

ルールを選択してその詳細パネルを開き、次に {{< ui >}}Edit{{< /ui >}} をクリックして、ルールのスコープ、タグの選択、またはマージと上書きの動作を変更します。

{{< img src="metrics/guide/tag_indexing_rules/edit_rule_configuration.png" alt="ルールのタイプ、スコープ、アクション、タグ、およびオプションが表示された、編集ボタンがあるルールの詳細のサイドパネル。" style="width:80%;">}}

### ルールの順序を変更する {#reorder-rules}

評価順序を変更するためにルールをドラッグします。評価順序は、複数のルールが同じメトリクスに適用される場合のルールの相互作用を決定します。

### ルールを削除する {#delete-a-rule}

不要なルールを削除します。ルールを削除すると、Datadog は残りのルールに基づいて、影響を受けるメトリクスのタグ構成を再計算します。

### 特定のメトリクスに対するルールの上書き {#override-rules-for-a-specific-metric}

メトリクスをタグルールから除外するには、メトリクスの詳細サイドパネルを [Metrics Summary] で開き、[{{< ui >}}Configure This Metric Individually{{< /ui >}} を選択し、メトリクスがすべてのタグを保持するように設定します。すべてのタグを保持すると、そのメトリクスに対するタグルールは適用されなくなり、ルール自体を変更する必要がなくなります。

ルールを再適用するには、同じパネルからメトリクスのデフォルト構成を復元します。

## ルールの優先度 {#rule-precedence}

複数のルールが同じメトリクスに適用される場合、Datadog はそれらを順番に評価します。ルールの順序が重要な理由:

- 評価順序が低いルールは以前のルールの結果を変更する
- {{< ui >}}Override{{< /ui >}} 動作は、一致するメトリクスの以前の構成を上書きします。
- {{< ui >}}Merge{{< /ui >}} 動作は既存の構成に基づいて構築されます。
- 複数のルールが {{< ui >}}Override{{< /ui >}} 動作を使用する場合、最後に適用されたルールによって最終構成が含まれるモードか除外されるモードかが決まります。

[ルールページ][1]でルールの順序を変更して、どのルールを優先するかを変更します。異なる順序が異なる結果を生むことを理解するために、以下の例を参照してください。

## 優先度の例 {#precedence-examples}

### 例 1: マージとオーバーライドの動作 {#example-1-merge-and-override-behavior}

タグルールは、既存の構成を上書きまたはマージすることができます。この選択によって、ルールがタグ構成をリセットするか、すでに存在するものの上に構築するかが決まります。

開始タグ: 
`host`、`env`、`service`、`team`

{{< img src="metrics/guide/tag_indexing_rules/merge_vs_override.png" alt="メトリクスに適用される 2 つのルールが表示された図: ルール 1 は上書きを使用してすべてのメトリクスから env を除外し、ルール 2 はマージを使用して infra メトリクスに env を含めます。" style="width:100%;">}}

**重要なインサイト**: `env` タグは `infra.*` メトリクスにのみ再追加されます。

### 例 2: ルールの順序 {#example-2-rule-order}

複数のルールが同じメトリクスに適用される場合、Datadog はそれらを順番に評価します。後に実行されるルールは、前のルールの効果を洗練したり上書きしたりできます。

開始タグ: 
`host`、`env`、`service`

この例では、ルール 2 が [{{< ui >}}Include{{< /ui >}}] (含める) 構成を使用しており、これは許可リストとして機能します。リストに記載されたタグのみが保持され、リストにないタグは削除されます。

#### 順序 1: 特定のルールが最初 {#order-1-specific-rule-first}

{{< img src="metrics/guide/tag_indexing_rules/rule_order_1.png" alt="最初に評価される特定のルールを示す図: ルール 1 が infra.server メトリクスからホストを除外し、ルール 2 がすべての infra メトリクスにホストを含め、タグを復元します。" style="width:100%;">}}

**重要なインサイト**: ルール 1 が `host` タグを削除した後、ルール 2 が `host` を再追加します。

#### 順序 2: 一般的なルールが最初 {#order-2-general-rule-first}

{{< img src="metrics/guide/tag_indexing_rules/rule_order_2.png" alt="最初に評価される一般的なルールを示す図: ルール 1 がすべての infra メトリクスにホストを含め、ルール 2 が infra.server メトリクスからホストを除外し、タグを削除します。" style="width:100%;">}}

**重要なインサイト**: `host` タグは最後に削除され、削除されたままになります。

### 例 3: 広範なルールの例外 {#example-3-exception-to-a-broad-rule}

広範なルールを {{< ui >}}Override{{< /ui >}} 動作で適用し、タグをグローバルに除外した後、特定のメトリクスに対してタグを復元するために {{< ui >}}Merge{{< /ui >}} 動作を適用するターゲットルールを使用します。

開始タグ:
`node`、`env`、`pod`

{{< img src="metrics/guide/tag_indexing_rules/broad_exclude_narrow_exception.png" alt="すべての kube メトリクスから Pod を除外する幅広い上書きルールと、すべての元のタグを保持して kube.node メトリクスのために Pod を含める狭いマージルールを示す図。" style="width:100%;">}}

**重要なインサイト**: 幅広い除外と狭い包含がメトリクスに対して互いに打ち消し合うと、タグの制限は適用されず、すべての元のタグが保持されます。

### 例 4: 幅広いルールの複数の例外 {#example-4-multiple-exceptions-to-a-broad-rule}

{{< ui >}}Override{{< /ui >}} 動作を持つ広範なルールに、{{< ui >}}Merge{{< /ui >}} 動作を持つ複数のルールを重ねて適用することで、異なるメトリクスプレフィックスの異なるタグを復元します。より具体的プレフィックスに一致するメトリクスは、より多くの復元を蓄積します。

開始タグ:
`team`、`pod`、`env`

{{< img src="metrics/guide/tag_indexing_rules/multiple_exceptions.png" alt="すべてのタグを除外する幅広い上書きルールと、異なるプレフィックスに対して異なるタグを復元する 2 つのマージルールを示す図。両方のプレフィックスに一致するメトリクスは両方のセットのタグが復元されます。" style="width:100%;">}}

**重要なインサイト**: {{< ui >}}Merge{{< /ui >}} 動作を持つ複数の含有ルールが、{{< ui >}}Override{{< /ui >}} 動作を持つ除外ルールの後に適用された場合、含有ルールは加算的影響を持ちます (2 つの例外プレフィックスに一致するメトリクスでは、両方のセットのタグが復元されます)。

## Metrics without Limits™ の互換性 {#metrics-without-limits-compatibility}

既存の [Metrics without Limits™][2] (WML) のメトリクスごとの構成は、タグインデックスルールよりも優先され、除外として機能します。除外が有効な間、そのメトリクスに対してはどのタグインデックスルールも適用できません。

これらの除外は、Tag Indexing Rules ページから確認し、解除することができます。Datadog では、各除外を次のように分類しています。

- **解除可能**: アカウントのタグインデックスルールに関する Datadog の分析に基づき、除外を解除するとカスタムメトリクスの使用量が削減されると予想されます。
- **要確認**: 除外を解除するとカスタムメトリクスの使用量に影響を与える可能性があるか、またはタグインデックスルールが既存の MWL 構成に含まれるすべてのタグを保持できなくなる可能性があります。これらのタグを利用しているダッシュボード、モニター、またはその他のアセットの機能が損なわれないように、これらの除外を慎重に確認してください。

除外は個々のタグインデックスルールではなく、アカウント全体に適用されます。メトリクスの除外を 1 つのルールから解除すると、アカウント内のすべてのタグインデックスルールからその除外が自動的に解除されます。その後、そのメトリクスはタグインデックスルールに対し、ルールの現在の順序に基づいて評価されます。

## ベストプラクティス {#best-practices}

タグインデックスルールを使用して、カスタムメトリクスのグループ全体でインデックス付きタグをタグ付けすることをデフォルトの方法としてください。個別のメトリクスがより広範なポリシーに対して意図的な例外を必要とする場合は、Metrics without Limits™ を使用してください。

### 最初にゴールデンルールを作成する {#create-the-golden-rule-first}

ゴールデンルールは、最初に作成されるタグインデックスルールであり、ルールの順序で常に最初に位置する必要があります。これにより、よりターゲットを絞ったルールやメトリクスレベルの例外を追加する前のベースラインポリシーとして確立されます。

ゴールデンルールは以下の通りです。
> 過去 30 日、60 日、または 90 日間にクエリされておらず、ダッシュボード、モニター、SLO、ノートブックなどの Datadog アセットで使用されていないすべてのタグキーのインデックスを解除します。


ゴールデンルールを構成するには、以下の手順を実行します。

1. 他のタグインデックスルールを作成する前にこのルールを作成します。ルールがすでに存在する場合は、ゴールデンルールを最初の位置に移動します。
2. {{< ui >}}Exclude tags{{< /ui >}} を選択し、次に {{< ui >}}By tag usage{{< /ui >}} を選択します。
3. クエリ期間を 30 日、60 日、または 90 日に設定します。
4. Datadog アセットで使用されていないタグキーが必要です。
5. `*` を使用して、すべてのカスタムメトリクスにルールを適用します。

新しく送信されたタグキーには、ルールが使用状況を評価する前に 15 日間の猶予期間が与えられます。これにより、チームは新しいタグをクエリしたり Datadog アセットで使用したりする時間を確保でき、インデックスが解除されるのを防ぐことができます。

ゴールデンルールを設定した後、このデフォルトとは異なるメトリクスに対して、より限定的なルールを作成します。

{{< img src="metrics/guide/tag_indexing_rules/golden_rule.png" alt="すべてのカスタムメトリクスにわたってクエリされていないタグキーを除外する、ゴールデンルールとして構成されたタグインデックスルール。" style="width:100%;">}}

### タグインデックスルールと Metrics without Limits™ のどちらかを選択する {#choose-between-tag-indexing-rules-and-metrics-without-limits}

タグインデックスルールは、単一のメトリクス、ネームスペース、複数のプレフィックス、またはすべてのカスタムメトリクスに適用できる動的なポリシーです。新しいカスタムメトリクスは、到着時に既存のルールに対して自動的に評価されます。ルールに一致するメトリクスは、個別の構成を必要とすることなく管理されます。

Metrics without Limits の構成は静的であり、一度に 1 つのメトリクスに適用されます。特定のメトリクスに異なるインデックス付きタグセットが必要な場合に使用してください。

既存の Metrics without Limits™ の構成は、タグインデックスルールよりも優先されます。Metrics without Limits™ の構成がアクティブな間、そのメトリクスは例外として扱われ、タグインデックスルールによって管理されません。

| ユースケース | 推奨コントロール |
|---|---|
| すべてのカスタムメトリクスのデフォルトのインデックス作成ポリシーを確立する | タグインデックスルール: ゴールデンルール |
| ネームスペースまたは一連のプレフィックス全体に同じタグポリシーを適用する | タグインデックスルール |
| 既存のポリシーに一致する新しいメトリクスとタグキーを自動的に管理する | タグインデックスルール |
| クエリされず、Datadog アセットで使用されていないタグのインデックスを解除する | タグインデックスルール |
| 複数のメトリクスにわたる既知の高カーディナリティタグを削除する | タグインデックスルール |
| 複数のメトリクスにわたる承認済みのタグセットのみを保持する | タグインデックスルール |
| 1 つのメトリクスに対して異なるインデックス付きタグセットを構成する | Metrics without Limits™ |

### 追加ルールのスコープを意図的に設定する {#scope-additional-rules-intentionally}

ゴールデンルールを作成した後、メトリクスのグループがデフォルトとは異なる要件を持つ場合にのみ、より限定的なルールを追加します。

- 同じサービス、アプリケーション、またはチームが所有するメトリクスには、ネームスペースまたはプレフィックスを使用します。
- 同じポリシーが関連するメトリクスのグループに適用される場合は、複数のプレフィックスを使用します。
- ポリシーをすべてのカスタムメトリクスに適用する必要がある場合にのみ、`*` を使用します。

明確なルールスコープを定義し、不要な重複を避けてください。これにより、どのポリシーが各メトリクスを管理し、誰がその変更を所有しているのかを把握しやすくなります。

新しいルールを追加する際は、ゴールデンルールが常に最初の位置にあることを確認してください。
