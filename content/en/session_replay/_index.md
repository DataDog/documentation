Session Replay is available in both <a href="/real_user_monitoring/">RUM</a> and <a href="/product_analytics/">Product Analytics</a>, helping you identify and reproduce errors, understand user journeys, and gain insights into your application's usage patterns and design pitfalls.</p><div class="cdoc__toggleable" data-description="SDK is Browser" data-if=cdocs-ref-3><h2 id="browser-session-replay">Browser Session Replay</h2><p>Browser Session Replay expands your user experience monitoring by allowing you to capture and visually replay the web browsing experience of your users. Combined with RUM performance data, Session Replay is beneficial for error identification, reproduction, and resolution, and provides insights into your web application's usage patterns and design pitfalls.</p><p>The RUM Browser SDK is <a href="https://github.com/DataDog/browser-sdk">open source</a> and uses the open source <a href="https://www.rrweb.io/">rrweb</a> project.</p><h3 id="how-the-session-replay-recorder-works">How the Session Replay recorder works</h3><p>The Session Replay recorder is part of the RUM Browser SDK. The recorder takes a snapshot of the browser's DOM and CSS by tailing and recording events happening on a web page (such as DOM modification, mouse move, clicks, and input events) along with these events' timestamps.</p><p>Datadog then rebuilds the web page and re-applies the recorded events at the appropriate time in the replay view.</p><p>The Session Replay recorder supports all browsers supported by the RUM Browser SDK. For more information, see the <a href="https://github.com/DataDog/browser-sdk/blob/main/packages/rum/BROWSER_SUPPORT.md">browser support table</a>.</p><p>To reduce Session Replay's network impact and keep the recorder's overhead on your application's performance to a minimum, Datadog compresses the data before sending it.</p><p>Datadog also reduces the load on a browser's UI thread by delegating most of the CPU-intensive work (such as compression) to a dedicated web worker. The expected network bandwidth impact is less than 100kB/min.</p><h3 id="heatmaps">Heatmaps</h3><p>Heatmaps overlay click, top elements, and scroll data on top of your Session Replay recordings, helping you understand how users interact with your pages. Learn more about <a href="/session_replay/heatmaps">Heatmaps</a>.</p><p><strong>Note</strong>: Heatmaps are only supported for Browser Session Replay.</p></div><div class="cdoc__toggleable cdoc__hidden" data-description="The selected value for SDK is included in the given list: 'Android, iOS, Kotlin Multiplatform, React Native, Flutter'" data-if=cdocs-ref-4><h2 id="mobile-session-replay">Mobile Session Replay</h2><p>Mobile Session Replay expands visibility into your mobile applications by visually replaying each user interaction, such as taps, swipes, and scrolls. It is available for native apps on both Android and iOS. Visually replaying user interactions on your applications makes it easier to reproduce crashes and errors, as well as understand the user journey for making UI improvements.</p><div class="shortcode-wrapper shortcode-img expand"><figure class="text-center"><video width="100%" height="auto" muted="" playsinline="" autoplay="" loop="" controls=""><source src="http://localhost:1313/images/real_user_monitoring/session_replay/mobile/mobile_replay.mp4" type="video/mp4" media="(min-width: 0px)"/><div class="play"></div><div class="pause"></div></video></figure></div><h3 id="how-the-session-replay-recorder-works-2">How the Session Replay recorder works</h3><p>The Session Replay recorder is built into the RUM Mobile SDK. Unlike web browsers, mobile apps don't use HTML or CSS. Instead, the recorder takes a &quot;snapshot&quot; of your app's screen by breaking it into rectangles called &quot;wireframes.&quot; It then keeps track of changes by only updating the wireframes that have changed, making the process efficient and fast.</p><h4 id="wireframe-concept">Wireframe concept</h4><p>A <em>wireframe</em> is like a digital sticky note marking a specific area of your app's screen, such as a button, image, or background. Each wireframe is a rectangle that helps the recorder keep track of what's on the screen.</p><p><strong>Examples of wireframes:</strong></p><ul><li>A text label becomes a &quot;text&quot; wireframe, defined by its position and size.</li><li>The app's background is a &quot;shape&quot; wireframe—a rectangle that covers the whole screen.</li><li>Any container with a solid background is also a &quot;shape&quot; wireframe.</li><li>Images or icons are &quot;image&quot; wireframes, which can include style details like transparency.</li><li>Even complex elements, like a map with many parts, can be combined into a single &quot;image&quot; wireframe.</li></ul><h4 id="recording-algorithm">Recording algorithm</h4><p>The recorder scans your app's screen from the background to the front, looking for all the visible parts. It creates a wireframe for each one. For example, a screen with 78 different elements can be simplified into 25 wireframes:</p><a href="http://localhost:1313/images/real_user_monitoring/session_replay/mobile/how-it-works/recording-algorithm-3.15e4bd583b4f6703092f62627f10767b.png?fit=max&amp;auto=format" class="pop" data-bs-toggle="modal" data-bs-target="#popupImageModal"><div class="shortcode-wrapper shortcode-img expand"><figure class="text-center"><picture style="width:70%"><img srcSet="http://localhost:1313/images/real_user_monitoring/session_replay/mobile/how-it-works/recording-algorithm-3.15e4bd583b4f6703092f62627f10767b.png?auto=format" class="img-fluid" style="width:70%" alt="An example of how the Shopist app screen contains 78 native views, but is made up of 25 wireframes."/></picture></figure></div></a><p>Wireframes are recorded in the order they appear on the screen (from back to front) and are placed using exact screen positions. There's no complicated tree structure, only a flat list of rectangles.</p><h4 id="rendering-algorithm">Rendering algorithm</h4><p>When you watch a replay, Datadog's player rebuilds the screen by drawing each wireframe in order. It uses the position and size of each rectangle to put everything in the right place. The first wireframe sets the screen size and orientation (portrait or landscape).</p><p>Each new wireframe is drawn on top of the previous ones, like stacking transparent sheets. But to save time and data, the recorder usually sends &quot;incremental snapshots&quot;, which are updates that include only the wireframes that have changed.</p><p>Each wireframe has a unique ID (like a name tag), so the recorder knows exactly which ones to update. For example:</p><ul><li>If a wireframe moves, only its new position and ID are sent.</li><li>If a wireframe disappears, the update says which ID was removed.</li><li>If only the content changes (like new text), the update includes the new content and the wireframe's ID.</li></ul><p>Below are examples showing how incremental snapshots only send updates for impacted wireframes.</p><table><thead><tr><th>Example</th><th>Description</th></tr></thead><tbody><tr><td><div class="shortcode-wrapper shortcode-img expand"><figure class="text-center"><video width="100%" height="auto" muted="" playsinline="" autoplay="" loop="" controls=""><source src="http://localhost:1313/images/real_user_monitoring/session_replay/mobile/how-it-works/incremental-snapshots-change-position.mp4" type="video/mp4" media="(min-width: 0px)"/><div class="play"></div><div class="pause"></div></video></figure></div></td><td>If a wireframe position changes, but its content and appearance aren't altered, the incremental snapshot only needs to include new positions for impacted wireframes and their <code>UUIDs</code>.
